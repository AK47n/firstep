# 一键全量下载（full-download）spec：无基线也能在窗口里下完整 firstep

## 问题陈述

现状（`materials-update` 已落地）解决了「有基线的用户只下增量」，但**全量这一档仍然是死路**：

- 用户点「检查更新」若本地缺 `sources/materials/.materials-manifest.json`（**当前所有用户都缺**——资料库基线清单从未随任何 Release 分发过），得到的只有一句中文指引「请下载完整包，或联系发布者提供初始基线」，**没有任何下载按钮**。
- 想真装完整包的用户，得自己去 GitHub Releases 手动下 4 个 7z 分卷（`firstep-full.7z.001~004`，约 6.2 GB）→ 装 7-Zip → 解压 → 跑 install.bat。全程无进度、无断点续传，弱网下一次失败就得从头再来。
- 想修损坏 / 换机器 / 拿一份干净副本的用户，同样没有工具内入口。

也就是说：**「窗口 + 进度 + 断点续传」这套体验只覆盖了增量路径，全量路径一点没沾**。

## 方案

在现有下载窗口之外，把「完整 firstep」也做成**同一个窗口里的一键下载**，并按智能双轨自动选路：

- **智能双轨**：检查更新时若本地**有**资料库基线 → 走既有增量路径（几十 MB 级）；若**无**基线（无从算差异）或用户主动点「下载完整 firstep」→ 走全量路径。用户不需要理解区别，只要点一个按钮。
- **全量包内容**：工具本体 + 五个库（modules / masters / topics / references / 母版）+ `sources/contest`、`sources/car` + 资料库**内容文件**（手册 / 真题 / 例程 / 移植手册）。**不含**那批第三方安装包与视觉 SDK 打包件（CCS 安装包 1.28 GB、`tsp-xbhdcc` 视觉 SDK 1.4 GB、K230 固件镜像与 CanMV IDE、VSCode / LCEDA / 嘉立创 EDA 安装程序、Arduino IDE、openmv IDE、K230 dataset 等，合计 5.4 GB）——它们几乎不变，本机已有一份就一直在，不进包也就不进每次全量重下。
  **实测（2026-09-13 本机，规则定稿后）**：包内 **8764 个文件 / 原始 1069.9 MB**（其中资料库内容文件 5087 个 / 688.3 MB），最大单文件 51 MB（一个教程视频），扫描耗时约 6 s；zip 后约 1.0 GB，按 1.9 GB 单卷上限 = **1~2 卷**。
- **分发形态**：zip 分卷（每卷 < 1.9 GB，遵守 GitHub 单资产 2 GB 上限），**不再要求用户装 7-Zip**（`zipfile` 标准库可解）。
- **下载体验**（与增量窗口同构）：总进度条 + 已下/总量 + 当前卷 + 速度 + 剩余时间 + 后台继续 / 取消；**卷级断点续传**（校验通过的卷持久化，取消 / 失败 / 重启只补未下的卷）；磁盘空间预检；全程中文提示。
- **应用体验（全自动）**：全部卷下好并校验 → 停服 → 安全解压（zip slip 整体拒绝）→ 备份将被覆盖的文件 → 覆盖落位 → 按删除清单清理废弃文件 → 按需装依赖 → 重启回更新后的工具。配置（DeepSeek key、任务状态、对话记录，都在工具目录外的 `%USERPROFILE%\.contest_generator\`）原样保留。
- **全量之后自动转增量**：完整包内带一份资料库基线清单，落位时写进 `sources/materials/.materials-manifest.json`——于是「无基线」这个状态只出现一次，之后所有用户都走增量。

## 用户故事

1. 作为无基线的用户，我想要在弹窗里看到「一键下载完整 firstep（约 1.0 GB + 当前版本）」，以便不用去 Releases 手动找 4 个分卷。
2. 作为用户，我想要设置页常驻一个「下载完整 firstep」入口，以便主动修损坏 / 换机器 / 只想重下一份干净副本。
3. 作为用户，我想要下载时看到总进度、当前卷、速度与剩余时间，以便几 GB 的过程心里有数、页面不假死。
4. 作为用户，我想要取消 / 失败 / 关掉页面 / 重启工具后已经下好并校验通过的卷不再重下，以便弱网环境不必从头再来。
5. 作为用户，我想要下载完自动完成替换并重启工具，以便不用手动解压、不用装 7-Zip、不用跑 install.bat。
6. 作为用户，我想要全量替换时我的 DeepSeek key、任务状态、对话记录、生成的工程与资料库原样保留，以便更新不等于重装。
7. 作为用户，我想要替换前有备份、失败时有中文错误与备份位置，以便一次失败的更新不毁掉工具。
8. 作为用户，我想要全量完成后下次检查更新就只提示我变化的部分（增量），以便再也不需要重下完整包。
9. 作为用户/发布者，我想要完整包与增量包用同一套资产命名与校验规则（清单 + 分卷 + SHA256），以便两边行为一致、可复现。
10. 作为发布者，我想要一条命令打出完整包（zip 分卷 + 清单 + 校验和 + 资料库基线清单），以便发版流程自动、可复现。
11. 作为发布者，我想要完整包**只含真正会变的内容**（不含第三方安装包 / SDK 打包件），以便每次全量的传输量从 6.2 GB 降到约 1.0 GB。
12. 作为用 git 克隆 / 旧 7z 完整包的用户，我想要原有 `git pull` 与 7z 完整包路径继续可用，以便不受影响。

## 实现决策

### 发布侧（新增 `pack-full` 打包脚本；Python 核心逻辑进现有打包模块）

- **产出资产（ASCII 文件名，4 类）**：
  - `firstep-full-<tag>.zip`（单卷装得下时）/ `firstep-full-<tag>.part<N>.zip`（超 1.9 GB 自动拆卷，每卷独立 SHA256）；
  - `firstep-full-<tag>.manifest.json`（**完整包清单**，用户侧检查与下载的数据源）；
  - `firstep-full-<tag>.removed.txt`（相对上一版**完整包基线**删除的文件，供覆盖后清理废弃文件；无基线 = 空）；
  - `firstep-full-<tag>.sha256.txt`（zip/分卷校验和汇总，供人工核对）。
- **完整包清单契约**：
  `{version, published_at, total_bytes, parts: [{zip_name, size, sha256}], files: [{path, size, sha256}], materials_manifest: {...}}`
  - `version` = 软件版本 tag（完整包随软件版本走，不单独设版本号）；
  - `files` = 包内**全部**文件的相对路径 / 大小 / SHA256（工具本体 + 库 + 资料库），既是删除清单基线，也是**资料库基线**的来源；
  - `materials_manifest` = 该版本的资料库清单（批次 / 文件集 / 版本），落位后写入 `sources/materials/.materials-manifest.json`，使全量用户当场获得增量能力。
- **包内布局**：zip 内顶层 = 仓库根（`src/`、`library/`、`sources/`、根级脚本与配置…），解压即覆盖。
- **排除规则（内容边界，单源登记）**：`.git`、`.scratch`、`.venv`、`node_modules`、各类缓存（`__pycache__` / `.pytest_cache` / `.mypy_cache`）、日志、`library/**/Debug|Release|Objects|Listings`、`library/fix-backups`、`library/revise-backups`、`sources/.trash-pdf`、以及资料库内的第三方安装包 / SDK 打包件（沿用 `sources/.gitignore` 的 ASCII 特征模式：`*CCS_20.5*`、`*tsp-xbhdcc*`、`*ubuntu-20.04*`、`*dataset.zip*`、`*05_SPI*.zip`、`*.exe`、`*.img.gz`、`*.img.xz`、`*.z01`）。
- **删除清单基线**：以上一版完整包的 `manifest.json` 为基线算「有而当前无」；首次发布无基线 = 空清单，更新器跳过删除。
- **7z 完整包路线保留**：作为历史渠道继续可用，文档改为「推荐 zip 完整包；7z 保留给需要第三方安装包的用户」。

### 用户侧入口与检查

- 既有增量链路（`GET/POST /api/update/materials/*`）**不动**。
- 新增全量链路（与增量对称）：
  - `GET /api/update/full/check`：读本地已装完整包版本（`updates/full-installed.json`，缺失 = 未知）→ 拉线上最新 `v*` Release 的完整包清单 → 返回
    `{current_version, latest_version, update_available, total_bytes, parts: [{name, size, sha256, url}], reason, error, message}`。
    网络 / 无 `v*` Release / 无完整包资产 / 清单解析失败 / 已装标记缺失或损坏 = 一律 200 级 + 中文 `message`（沿既有契约，不 500）。
- **智能双轨选路**：检查资料库更新时若缺基线 → 响应带「需要完整包」标记，前端弹窗主按钮直接变成「一键下载完整 firstep（约 1.0 GB）」，不再只给一句文字指引。

### 下载与应用（后端）

- `POST /api/update/full/apply`：校验分卷集合（白名单 = check 返回的分卷，防注入）→ 磁盘空间预检（下载总量 + 备份余量）→ 起后台线程流式下载（256 KB 分块 + 每卷 SHA256 校验 + 卷级持久化标记）→ 返回 `started`。
- `GET /api/update/full/status`：内存态 + 节流落盘快照（`updates/full-task.json`，重启可恢复）→ `{state: idle|downloading|applying|done|failed, parts: [{name, downloaded_bytes, total_bytes, ok}], total_downloaded_bytes, total_bytes, speed_bps, error, message}`。
- `POST /api/update/full/cancel`：置取消标记，任务在分卷边界停止，已完成卷标记保留。
- 全部卷就绪 → 写「待更新标记」→ **以独立进程**拉起更新器（替换动作绝不在运行中的 webapp 进程内做，沿小发版决策）。

### 更新器扩展（`tools/update-app.py`）

- 新增全量模式：多分卷顺序解压 → **zip 条目路径安全校验**（`..` / 绝对路径 / 盘符前缀 / 反斜杠一律整体拒绝，规则同小发版）→ 停服（先确认 `/api/health` 的 `app` 标识再 kill，避免误杀）→ 备份将被覆盖的文件到 `updates\backup\<时间戳>\` → 覆盖工具根 → 写回资料库基线清单 → 按删除清单清理 → 依赖变更检测（覆盖前后 `pyproject.toml` 哈希差异）→ 全流程日志 `updates\updater.log` → 清标记 → 重启应用。
- 「更新中」保护：`updates\updating.lock` 存在时启动器提示「更新进行中，请稍候」，不拉起半更新状态。

### 前端（与增量窗口同构：`fx/` 纯函数 + `ui/` 胶水）

- 设置页「资料库更新」区旁新增「完整包」行：当前版本 + 「下载完整 firstep」常驻按钮；无基线时该入口升为主推。
- 全量弹窗：版本头（当前 → 最新）+ 下载总量 + 分卷数 + 「开始下载 / 稍后」；下载中改进度视图（总进度条 / 当前卷 / 速度 / 剩余时间 / 后台继续 / 取消）；完成 → 「已更新到 vX，工具即将重启」；失败 → 中文原因 + 重试（已完成卷跳过）。
- 无基线弹窗（增量侧）：主按钮从「去下完整包」改为「一键下载完整 firstep」。

## 测试决策

沿用最高既有缝，**不新增跨层新缝**（唯一新增是一个测试专用的临时 HTTP 资产服务小工具，`materials-update` e2e 已有同款先例）：

- **发布侧纯函数**：完整包扫描 / 排除规则（第三方安装包与 SDK 打包件、缓存、备份目录都不进包）与完整包清单构建，用临时目录造迷你仓库树（含中文目录名 + 一个 `.exe` + 一个 `08_*.zip` 干扰件）断言「不进包 + `files` 与 zip 内容一一对应 + `materials_manifest` 与资料库扫描一致」；分卷切分与 SHA256 可复算。
- **检查端点**：注入假 fetch（Release 列表 + 清单文本）断言四态（有新完整包 / 已是最新 / 无完整包资产 / 网络失败）+ 已装版本缺失降级；monkeypatch 沿用 `tests/test_update_check.py` 先例。
- **下载任务与端点**：monkeypatch 下载函数断言卷级断点（第 1 卷成功、第 2 卷失败后重试只下第 2 卷）、取消、空间不足 400、非法分卷名 400、status 各状态（先例 `tests/test_update_apply.py`）。
- **更新器集成测试**：临时目录构造迷你完整包（zip 分卷 + 清单 + 删除清单）→ 断言覆盖落位、备份生成、删除清单生效、包外文件原样、资料库基线清单写回、`pyproject.toml` 变更触发依赖判定；另测 zip slip 整体拒绝、多分卷顺序、`updating.lock` 生命周期。
- **前端纯函数**（`tests/js/`，node）：全量弹窗 HTML / 进度文案 / 结果文案 / 双轨选路（有基线 → 增量，无基线 → 全量）/ XSS 转义。
- **端到端冒烟**：本机临时 HTTP 服务模拟 Release + 分卷资产 → check → apply → 落位断言（沿 `materials-update/e2e` 与 `auto-update/e2e` 先例）。
- **不做**：真造 GB 级资产进测试。

## 范围外

- 单卷内部的 HTTP Range 断点续传（只做**卷级**断点；分卷 ≤ 1.9 GB 已控制单卷重下代价）。
- 第三方安装包 / 视觉 SDK 的自动下载与更新（它们不进包，也不做单独更新入口）。
- 全量包与增量包的差量互转（有基线走增量、无基线走全量，不做「部分文件补齐」）。
- 自动 / 静默下载（必须用户显式点击，与既有两个更新机制一致）。
- macOS / Linux；安装器 / 自解压（SFX / Inno）本身。
- 自动回滚 UI（失败仅保留备份 + 中文提示备份位置）。
- 旧 7z 完整包路线的下线（继续保留）。

## 补充说明

- **为什么全量包不含第三方安装包**：那批文件占 5.4 GB（CCS 安装包 1.28 GB、视觉 SDK 1.4 GB、VSCode / LCEDA / 嘉立创 EDA 安装程序、K230 dataset），几乎不变且只在装机时用一次；把它们放进每次全量重下，等于让「修损坏 / 换机器」多付 5 倍体积。已装用户本机那几个文件**原地不动**（删除清单只以完整包清单为基线，不会误删）。
- **为什么仍要保留全量路径**：增量以基线为前提，而基线只可能来自一次「全量」或一次「初始基线分发」；另外更换机器、资料库损坏、只想拿干净副本这三种真实场景只有全量能解。
- **「无基线」是一次性状态**：完整包内带资料库基线清单，落位即写入，之后检查更新只走增量。
- **磁盘占用**：下载产物落在用户数据目录 `updates\`（与配置同级，工具目录之外），应用完成后可清理；备份保留在 `updates\backup\<时间戳>\`。
- **与既有机制的关系**：三条路径平级且互不干扰——`git pull`（克隆用户）、小发版一键更新（代码 + 四库，几百 MB）、资料库增量（有基线时）、完整包全量（无基线 / 主动重下）。
