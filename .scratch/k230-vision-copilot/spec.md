## Problem Statement

电赛视觉类题目（找球、识别数字、色块追踪等）需要 K230 负责「看」，通过串口把识别结果发给主控（STM32 最小系统板 或 地猛星 MSPM0），由主控「动」。现在生成器只生成主控 C 工程：主控侧的串口解析模块（`ball_detect`、`digit_uart`）已经入库且双平台真机编译验证，但 K230 侧的 `.py` 发送脚本（sensor 采图 → 视觉识别 → 按约定帧格式串口发出）全靠用户手写。手写导致两个问题：① 协议容易跟主控解析对不齐（帧格式、字段顺序、校验不一致则解析失败）；② 每个赛题都要重写一遍 sensor 初始化 + 串口发送的样板，重复劳动。

## Solution

把「K230 视觉副控」做成一个可勾选的**模块**（不是独立平台线）。选中它后，生成器照常生成主控工程（挂上串口解析），并**额外生成一个 CanMV `main.py`**（开机自启动，烧进 TF 卡 K230 上电即跑）。主控解析与 K230 发送使用同一套 CSV 帧契约，两侧协议由生成器单源保证对齐，不再靠用户手写对齐。

## User Stories

1. 作为参赛选手，我想要在生成器里勾选「K230 视觉副控」这个模块，就能同时得到主控工程里的串口解析代码和一个 K230 用的 `.py` 脚本，这样我不需要手写 K230 侧代码。
2. 作为参赛选手，我想要给 K230 模块的串口指定主控侧的 TX/RX 引脚（跟选其它串口模块一样在配置里配），这样我能把 K230 接在主控的任意可用串口上。
3. 作为参赛选手，我想要生成的 `.py` 里的串口帧格式跟主控解析严格一致，这样接上线就能解析出结果，不会因为协议不一致而反复对线。
4. 作为参赛选手，我想要生成的 `.py` 是「开机自启动」的（拷进 TF 卡、K230 上电自动跑），这样我不需要每次用 IDE 手动运行脚本。
5. 作为参赛选手，我想要生成的 `.py` 里包含摄像头初始化、视觉识别、结果组帧、串口发送的完整闭环，这样它是一个「打开就能跑」的脚本。
6. 作为参赛选手，我想要 K230 模块跟现有的 `ball_detect`（球检测）或 `digit_uart`（数字识别）解析配套，这样主控侧不用为 K230 另写解析。
7. 作为参赛选手，我想要在不选 K230 模块时，生成结果跟现在完全一致（不出现多余的 `.py` 文件），这样已有题目不受影响。
8. 作为参赛选手，我想要 K230 模块支持对端可配（STM32 或 地猛星），这样无论主控是哪块板都能用。
9. 作为参赛选手，我想要生成的 `.py` 里串口波特率等参数跟主控解析的约定一致（115200），这样两侧无需额外对齐。
10. 作为参赛选手，我想要 K230 视觉能力（色块追踪 / 数字识别等）后续能逐步扩充，这样不同视觉题型都能覆盖。

## Implementation Decisions

- **K230 是模块，不是平台线**：在模块库里新增一个「K230 视觉副控」模块，走现有模块系统（manifest + 平台条目 + 引脚角色），不新增第三平台，不动生成主流程的平台分派。
- **模块新增「Python 副产物」能力**：现有模块只产出进主控工程的 C 代码；本特性为模块 manifest 引入一种「额外生成 K230 侧 `.py` 脚本」的声明能力。生成器在写盘阶段识别该声明，除主控工程外额外写出 `.py` 文件。默认（无该声明的模块）行为与现在逐字节一致。
- **主控侧解析复用，不新写**：K230 模块的视觉能力与主控侧现有解析一一对应——色块追踪/球检测对应 `ball_detect`（CSV 帧 `B,<cx>,<cy>,<confidence>,<x1>,<y1>,<x2>,<y2>` / `N` 无检测），数字识别对应 `digit_uart`（CSV 数字识别帧）。主控侧解析通过模块依赖复用现有模块，K230 侧负责补齐发送端。协议契约单源：帧格式只定义一处，两侧渲染同源，避免再漂移。
- **首批视觉能力**：只做「色块追踪 / 球检测」一种（对齐 `ball_detect`），跑通「模块声明 `.py` 副产物」这条新机制；数字识别（对齐 `digit_uart`）作为紧随其后的第二个能力，复用同一机制（加一份 `.py` 模板 + 一个依赖即可）。
- **`.py` 自启动与运行环境**：CanMV MicroPython，脚本落地为 SD 卡根目录 `main.py`（CanMV 开机自动运行）；内容 = sensor 初始化 → 视觉识别 → 组 CSV 帧 → UART 发送 的完整闭环。
- **串口参数与引脚**：波特率 115200（与 `ball_detect`/`digit_uart` 约定一致）；主控侧串口引脚走现有 pins 角色机制（uart_tx / uart_rx），对端可配（stm32 / mspm0 平台条目各自声明）。
- **K230 脚本素材来源**：`.py` 模板从参考库提取——`k230资料/code/05色块追踪与线段识别.py`（find_blobs 色块追踪）与 `k230资料/code/13_与天猛星串口通信.py`（FPIOA 串口映射 + UART 发送）等现成例程；识别结果组帧格式与 `ball_detect` 解析契约对齐。

## Testing Decisions

- **最高测试接缝**：沿用 `generator.generate_project`（现有生成链路测试已在此缝）。新增断言：选中 K230 模块后，生成产物里包含 `.py` 副产物文件，且内容满足契约（含 sensor 初始化、find_blobs 视觉调用、CSV 帧组装、UART 发送）；未选中时产物与现在逐字节一致。
- **`.py` 拼装为纯函数、直接断言输出文本**：`.py` 是 Python 文本，可静态断言（字符串包含 / 结构契约 / 帧格式正则），无需真机，不需要新增 C 编译矩阵。
- **协议契约单测**：帧格式（字段顺序、分隔符、`N` 无检测分支、115200）作为独立契约断言，主控侧解析与 K230 侧发送都从该契约派生，测试断言两侧一致。
- **主控侧解析零改动**：`ball_detect`/`digit_uart` 不因本特性改动，沿用其既有测试与编译验证；本特性只新增 K230 侧 `.py` 与生成器写盘逻辑的测试。
- 不新增「真机 / 烧录」测试——`.py` 内容的正确性靠文本契约断言，真机验证属人工验收。

## Out of Scope

- 「双板联动一次生成」体验（本版 K230 作为模块独立勾选，不自动联动主控平台判断视觉需求）。
- `13_与天猛星串口通信.py` 的二进制指令帧协议（K230 发指令控主控步进电机）——那是 K230→主控「控制」方向的另一套协议，本版只做 K230→主控「视觉结果」的 CSV 帧。
- 视觉模型训练 / AI_cube 数据集 / 阈值自动标定。
- K230 作为独立平台线（视觉 + 控制全在 K230 上）。
- 除「色块追踪/球检测」外的视觉能力（数字识别、线段巡线、二维码、AprilTag 等）——留作后续能力，复用本特性的 `.py` 副产物机制。
