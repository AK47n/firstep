# 新问题 01 — 板图判据与「累积绑定」口径不一致：槽位互斥漏判（同型假绿）

**状态：** resolved（2026-08-xx；spec `spec-slot-model.md` → 工单 02（模型补 slot 谓词）
+ 03（parity 补累积态相），修法与「附带结论」的去向见两份工单的完工段）

**发现**：2026-08-xx（工单 `.scratch/gen-chain-audit/03` 修完之后复侦时顺线查出）
**性质**：与工单 03 同型——板图上点得下去、点完那一组必 400；只是换了一条门禁
（`_check_slot_conflicts`），且暴露的是**口径**问题（per-binding vs 整份 bindings），
不是「漏了一条规则」。

## 复现（一条命令）

```
python -m pytest .scratch/mspm0-slot-conflict/repro_slot_conflict.py -q -s
```

实测输出（真板定义 + 真 `resolve_bindings`，无浏览器 / 无 LLM）：

```
① 单绑定口径：huidu.R3=PA0                      → 后端收
② 累积态口径：huidu.R3=PA0 + pid.GRAY_D7=PB6     → 后端拒：
   「绑定冲突：huidu.R3 与 pid.GRAY_D7 共用同一槽位（默认引脚 PB6）
     却绑到不同引脚 PA0、PB6 —— 请绑到同一引脚」
③ 模型判定 pinModelVerdict(huidu.R3, PA0) = True（selectable 含 PA0，constraint = None）
④ 点下去之后的模型：pid.GRAY_D7 / huidu.R3 约束都还是 None → 不会纠正
```

`huidu.R3` 与 `pid.GRAY_D7` **默认同为 PB6**（八路灰度族刻意重叠），槽位互斥要求
两脚同绑或都不动；用户把其中一脚改到别处就撞门禁。

## 根因（口径问题，两层）

1. **模型只表达「per-binding 判据」**：端口组（组内其余角色有效脚）与 pwm 两通道
   （对脚有效实例）都是「候选脚 vs 其余角色**当前有效脚**」——天然按累积态算；
   而槽位互斥是「候选绑定 vs 其余**已绑定**绑定的引脚」，是同一形状但**没进模型**。
2. **parity 用例的对照口径太窄**（工单 06 的用例自身缺陷）：它比的是
   `模型判定 × resolve_bindings({role: pin})`——**单绑定**。用户点下去时发出去的是
   整份 bindings，所以「单绑定收、累积态拒」这类分歧用例照不出来
   （本轮该洞就是这么漏过去的：对拍全绿，实际仍有一条 400 通路）。

## 修法（建议，待拍板）

- **A. 模型加一条跨角色谓词** `{kind: "pin", pair_role, pin, reason}` 或
  `{kind: "slot", ...}`：候选脚必须与同槽位其余角色**当前有效脚**一致
  （后端用 `_mspm0_same_slot` + 默认脚分组算，与 `_check_slot_conflicts` 同源）；
  前端求值同 `port` 谓词一样简单（比引脚名相等）。
- **B. 不去建模，改口径**：把 parity/验收判据从「单绑定」改成「累积态」
  （模型允许 → 加进累积 → 后端必须收），并把槽位互斥做成**绑定时**的即时校验
  （绑定动作前问一次 `/api/bindings/validate`）——改动小但引入一次网络往返。
- 无论 A/B：**parity 用例必须补「累积态」相**（现有 `test_greedy_user_walk_…`
  只走贪心第一条可选脚，覆盖不到这种跨模块同默认脚组合）。

## 附带结论（同批查清，不需要修）

- 工单 03 记的「组内混端口松弛」（模型对混端口观测不给约束）：**从默认态不可达**——
  BFS 枚举 14641 个「模型允许的绑定序列」可达态，组内混端口态 **0 个**；
  单脚 0 条、两脚组合 0 条「模型允许但后端拒」。所以它是潜在洞（若模型被喂进
  混端口观测，会出现 93 条假绿），不是当前活洞；修 A/B 时顺手加一条守卫即可
  （模型收到混端口观测时给出「该组无解」的显式状态，而不是静默 `null`）。
