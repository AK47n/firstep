## 为什么把「校验失败」拆成两支（工单原文与 spec 冲突，以 spec 为准）

工单原文预期「校验失败 → 终态失败 + 中文」。真机第一版 fixture（服务器持久改坏字节）跑出来的是
**永远 `downloading`**：150.1 s 内重试 7 次、台账 7 次请求起始偏移全 0、无终态、`error_kind=verify`，
摘要「下载内容与清单不符（3961701 字节），已删除重下，会重新下载整卷」。

查 spec 才发现这不是实现 bug：`.scratch/resumable-download/spec.md` 第 122 行**明文**规定
「内容与清单 SHA256 不符 → 删半成品 + 走退避重试（从 0 整卷重来，**直到对上或用户取消**）」
（代码侧对得上：`DownloadContentMismatchError` 不在 `_NOT_RETRYABLE` 里）。
于是本单把它当**观察格**，并把后果量下来（线上 765 MB/轮 + 退避封顶 60 s → 约 45 GB/小时量级），
开了**决策单** `update-content-mismatch-retry-cap/01`（建议加「连续 N 次转终态」）。
**工单原文那句预期，按 spec 更正**——不把「按设计行为」记成「产品没做到」。

## 演练自身踩的坑（两条，都值得写下来）

1. **产品的下载态跟着配置走**：`updates/` = `context.config_path.parent / "updates"`。第一版 harness
   把一次性配置放在演练目录**根**，于是半成品/边车/快照全落在演练目录，而断言去沙箱数据目录找 →
   「取消后半成品在不在」量出 0 字节、「断线重试」直接命中一份已下完的文件（0 次请求）——
   **整轮证据作废，白跑 6 分钟**。现在配置放进 `<work>/profile/.contest_generator/config.json`
   （与真机用户目录同构），并给每格加了「夹具起点干净」自检。
2. **别在文案里找词**：第一版断言 `message` 里含「正在自动重试 / 从 X% 接着下」，红了。
   查前端才发现那句话是**前端拼的**（`static/js/fx/core.js:96-97`：`retry_count` + `message` +
   `resume_percent`），产品的 `message` 只放原因——`core.js` 的注释自己写着「第一版拿正则从
   message 里摘百分比 = 把文案当接口，已改」。判据已改为**结构化字段 + 模板静态出处**。
