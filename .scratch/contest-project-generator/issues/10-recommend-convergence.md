# 10 — 模块推荐改造：题面驱动 + 收敛循环 + 库外建议

**What to build:** 现有 AI 推荐只能从库内模块里挑（提示词限定"在给定的模块库中选择合适的现成模块"，解析器对库外 slug 直接报错），对"送药小车显然需要视觉模块"这类题无解。改造为：AI 以题面为依据逐句对照出功能需求层，逐条做实现覆盖检查——库内命中给可勾选模块，无命中给库外建议（类别名 + 常识举例，仅展示不进工程）；以题面为裁判反复自检收敛（连续两轮一致即停，上限 4 轮），拿不准向用户补问。

**Status:** open

## 现状事实（2026-08-08 调研）

- 提示词 SELECT_SYSTEM_PROMPT（llm.py:43-48）限定"在给定的模块库中选择合适的现成模块"
- 输出契约 `{"modules":[{"slug","reason"}]}`；parse_module_selection（llm.py:1100-1156）对库中不存在的 slug 抛 LLMError——库外推荐被三重闸门（提示词 / schema / 校验）禁止
- 真实库 7 个模块（filter / lock_control / zone / pid / uwb_uart / ml_mpu6050 / motor），无任何视觉/声光类
- 两级注入协议（select_modules_two_level，llm.py:1346-1368，参考文件先清单后全文重选）需兼容
- 收敛解缓存涉及 topic_library.py 赛题条目——v2 拆分候选

## 设计共识（2026-08-08 grilling 会话，同源 ADR 0007）

- **功能需求层**：能力/外设级（声光提示 → LED/蜂鸣器），粒度贴题面关键词；每条必须挂题面对应句，禁止题外联想（"送药小车所以需要视觉"是脑补；题面要求识别数字才需要视觉）
- **逐句对照**：题面按句编号，每句对应功能或"无功能"——机械防漏，不靠 AI 自觉
- **实现覆盖检查**：功能逐条查库内命中；无命中 → 库外建议（机械判定，不是 AI 主观推荐）
- **库外建议**：类别名 + 常识举例（视觉模块 → K230 / OpenMV）；name 必须命中硬件词表（型号/类别条目），词表外型号降级为类别或拒收，examples 自由（用户自行核实）；仅展示、不进 selectedSlugs / expand / generate
- **收敛循环**：AI 以题面为裁判自检修订（删脑补 / 补遗漏 / 重查覆盖），连续两轮功能需求层一致即收敛；上限 4 轮防死循环；拿不准暂停向用户补问（复用提炼补问轮机制）；轮次经 SSE 进度事件推送
- **硬件词表**：两条目型（类别 / 具体型号），进 prompt 作科普素材；初始清单覆盖视觉（K230/OpenMV/摄像头）、声光（LED/蜂鸣器）、感知（编码器/MPU6050/九轴/红外/超声）、执行（电机/舵机）、通信（ESP8266/蓝牙/NRF24L01）、显示（OLED/数码管）等；可手补
- **缓存（v2）**：收敛解存赛题条目，选历史题直接复用；库内命中每次现算（库会变）

## 验收清单

- [ ] 提示词改造：题面逐句编号 + 功能需求层输出 + 收敛自检指令 + 词表科普段（截断标注沿用，以所见内容为准不脑补）
- [ ] 输出契约：新增功能需求层字段（需求 / 对照句 / 库内命中 modules[] / 库外建议 suggestions[name, examples]），顶层 modules[] 保持（下游 selectedSlugs / expand / generate 零改动）；解析器新校验：name 词表命中 → 显示、词表外 → 降级类别或拒收
- [ ] 收敛循环：多轮调用，功能需求层两轮一致即停，上限 4 轮；轮次经 SSE 推送；补问路径打通
- [ ] 库外建议隔离不变量：不进 selectedSlugs / expand / generate；现有严格校验（库外 slug 报错）保留
- [ ] 硬件词表：文件 + 初始词表 + 手补入口
- [ ] UI：推荐卡片按功能分组渲染（库内 chips 可勾选/移除；库外建议灰色 + 「需自备」标注）
- [ ] 两级注入协议兼容：第一级清单 / 第二级全文重选在新契约下工作
- [ ] 契约/解析单测：收敛命中、轮数上限、name 降级/拒收、补问、两级注入各路径
- [ ] 真机验收：2025 智能送药小车题 → 功能层含「识别数字」且库外建议出「视觉模块」（K230/OpenMV 举例）；2026C → 命中 zone / lock_control / filter 正常且不重复

## v2（拆分候选）

- 收敛解缓存进赛题条目（topic_library.py），库内命中每次现算
- 功能层手改（用户补功能 + 手动填建议硬件）

## Comments

- 2026-08-08: grilling 会话（grill-with-docs + domain-modeling）产出设计共识，与 ADR 0007 同源。关键反转：① 库外建议不是"AI 主观推荐"而是实现覆盖检查的机械产物；② 防漂移不靠缓存靠收敛（用户明确反对"送药小车永远需要视觉"的品类铁律）；③ 收敛的自检盲区（两轮一起漏）用逐句对照表机械兜底；④ 库外建议 name "不懂不要编造"——词表外型号降级为类别。
- 2026-08-08 真机验收（2021F 送药小车）：修复 "requirements[0] 的 sentence 必须是正整数"——真实 DeepSeek json_object 模式把数字标量全部序列化为字符串（24/24 条需求 sentence 都是 "1" 形状），严格类型校验让整轮收敛当场失败。根因是输出契约示例 `"sentence": 对应题面句子编号` 没有具体整数样例，模型照字面输出字符串。修复两层：① 契约示例改为显式整数（`"sentence": 1（整数…不是字符串"1"）`）——真机复测 30/30 条全是 int；② 解析器对数字字符串无损强转（"1" 语义上就是正整数，形状不是语义；非数字字符串 / 布尔 / 浮点照旧大声失败）——防未来模型/版本再犯。回归测试：数字字符串强转 + 新增拒绝用例（"0"/"abc"/"1.5"/1.0）。全量 712 绿；真机收敛循环端到端通过（2021F → 8 条需求收敛，库内命中 pid/motor，库外建议 OpenMV/K230/红外/LED）。教训：LLM JSON 契约的数字字段必须给具体整数样例；解析器对无损形状归一（digit 字符串→int）是卫生层，大声失败留给语义违规。
