## 验收记录（2026-09-13）

### 档① 本地可控：五用例全绿（`verify-06-local.json`）

**这份 JSON 的读法要说清两件事**（评审指出，免得读大）：

1. **重试次数不在它里面如实分列**：探针**不自己重试**（重试住在产品代码里），所以每次
   「探针重试 1 次」而「网络请求 N 次」——`N` 才是断流次数（`cut` 例 4 次 = 1 首发 + 3 次
   自动重连）。`network_requests` / `request_starts` 是判据，`probe_attempts` 不是。
2. **`ignore-range` 这一例在档① 里是空转**：本地没有半成品 ⇒ 第一次请求就不带 `Range`
   （`ranges_seen: [""]`），于是 spec 断点契约里「收到 200 → **丢弃半成品从 0 重下**」
   那条分支**没被这一例覆盖到**。补这条判据的是**工单 03 的 `probe-03-corridor.py`**
   （它的 `ignore-range` 例子先铺一份带边车的半成品，因此真的发了 `Range` 并被忽略，
   服务器台账记到起始偏移 `1048576`，最终哈希仍正确）——**别把两处混为一谈**。
   本单没有把探针 01 改成覆盖那条分支，如实记在这里。
```
stable        起始偏移 [0]                     1 次请求  哈希一致
cut           起始偏移 [0, 838860, 1342176, 1644166]  4 次请求（连断 3 次，每次接着下）
stall         起始偏移 [0, 786432]             2 次请求（零字节卡死 30 秒判出 → 从断点接上）
ignore-range  起始偏移 [0]                     1 次请求（恒 200，最终哈希仍正确）
slow          起始偏移 [0]                     1 次请求（384 KB/s，5.3 秒下完）
总判：PASS
```

### 反证：判据仍会红（`verify-01-negative.txt`）

对照实现 = 「每次尝试前丢弃半成品」→ 复跑**总判 FAIL、退出码 1**，红的理由正是
「cut / stall **被截断却自称成功**」，起始偏移序列全是 0。
→ 「续传」与「截断必须失败」两条判据都还在工作（判据没被调软）。

### 档② 线上真资产：GitHub Releases 支持分段（`verify-06-online.txt`）

在 `AK47n/firstep` 的 v1.1.1 上取**小资产**（`firstep-full-v1.1.1.removed.txt`，30 字节）：

| 请求 | 结果 |
|---|---|
| `HEAD` | `Accept-Ranges: bytes` |
| `Range: bytes=10-19` | **`206`** + `Content-Range: bytes 10-19/30` + 正文 10 字节 |
| `Range: bytes=10-` | `206` + `Content-Range: bytes 10-29/30` + 正文 20 字节（续取语义） |
| 用**产品自己的 `resumable_download`** 真下一次 | 落盘 30/30 字节，`attempts=1 / resumed_from=0`，自报 SHA256 == 实际 SHA256 |

→ 「线上服务器肯不肯给分段」这条前提**成立**，且产品下载器在真资产上下得完。
**别读大了**：这一次是**一次成功**（没走过续传拼接那条路），而「自校验通过」在这里只是
「下载器自报哈希 == 它落盘内容的哈希」——那个 30 字节资产是**被删除文件清单**，不含自己的
哈希，拿不到独立参考值。**这些都不等于「783 MB 完整包也能续传」**（那是档③ 的事，本轮没跑）。

### 档③ 真实完整包端到端：**部分完成**（`verify-06-tier3.txt` / `.json` / `-resume.txt`）

**用户点了「现在就跑」**，于是在**一次性工具根**（`%TEMP%`，不动 8020 沙箱）上真跑了一遍。

**成立的两条**：

| 判据 | 证据 |
|---|---|
| 真下载：真检查 → 真下载 **783 MB 下完并校验通过** | `full-task.json` 快照 `ok: true` / `downloaded_bytes=821352026`（= 清单 size） |
| **从中断处接着下** | 确定性复检：真 `Range` 铺 32 MB 半成品 + 边车 → 真 `FullDownloadTask` 第一次尝试起始偏移 **33554432**（不是 0）→ 最终 `ok=True`，用时 78 秒 |

**没验到的两条（别读大）**：① 替换 → 重启后的版本号（那次替换环节没走完：
写了 `pending-update.json` 并拉起更新器，但任务终态 `failed`、工具根没被替换）；
② 真资产上的「网还在但传输断了」（本轮用的是**杀进程** + 确定性铺半成品；
`cut`/`stall` 形态由档① 的本地可控服务器覆盖）。

**本单验出来的真缺陷（已修 + 钉判据）**：**硬杀进程留下的半成品没有边车**。
第一次真跑下到 210 MB 时杀掉服务进程，盘上是「210 MB 半成品 + **无**边车」——重启后点重试，
任务把这份半成品当来路不明的东西清掉，**从 0 重下（白下 210 MB）**。根因：边车原来只在
「取消 / 失败」两处写，硬杀（结束进程 / 崩溃 / 断电）两条路都不走。
修法：`resumable_download` **开跑就写边车**（成功路径照旧清掉）。
判据：`test_download_start_writes_sidecar_so_a_killed_process_can_resume` +
`test_success_clears_the_early_sidecar`。
> 这是本单**唯一**改产品代码的地方（工单写着「只验、只记」）；如实记账，若评审要求可摘成独立工单。

**脚本自身的两个坑（都写进证据文件，供下次复用）**：① 只重定向 `USERPROFILE` 隔离不住数据目录
（`DEFAULT_CONFIG_PATH` 在导入时就求值了）→ 必须显式传 `config_path`；② 「下到 25% 就杀」在快网上
不可控（783 MB 只要 ~80 秒）→ 判据改成「铺半成品 + 边车」的确定性复检。
**隔离边界按保守写**：不能声称「真身数据目录全程零触碰」（第一版脚本那次无法事后判定）；
能证实的是此刻真身目录 mtime 早于演练、`updates\` 为空。
