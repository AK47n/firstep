**本单踩到并修掉的两处**（都在目视那一层才看得出来）：

1. **同一件事说两遍**：状态面的 `message` 自带「，第 N 次自动重试，从 39% 接着下」，
   而进度区又加了「正在自动重试（第 N 次）：」前缀 → 读出
   「正在自动重试（第 1 次）：…，第 1 次自动重试，从 39% 接着下」。
   修法 = `core.retryProgressText(message, retry_count)` 单源摘掉重复段（**保留原因与
   「从多少接着下」**——用户要知道自己在等什么）。两条链路共用，不许各写一套。
2. **`speed_bps` 是瞬时估算**：第一次 `status` 调用永远返回 0（窗口 = 上次调用至今），
   所以「慢」那一态的载荷不能靠「跑一秒再读一次」拿到（实测 `total_downloaded_bytes` 还是 0）。
   证据脚本里这条**只人工指定 `speed_bps`**，其余字段照真任务——并在脚本注释里写明
   这一点（免得下一个人以为它是真速度）。

**同源纪律**：`fmtEta` / `SLOW_SPEED_BPS` / `downloadFailureText` / `retryProgressText` /
`retryNoteText` / `downloadedPercent` 六个共用件都住 `fx/core.js`——两条链路都要用，放任一侧
都会让两个同域模块互相依赖（与后端的做法一致：共用件下沉，见 `download_resume.py` 的模块说明）。
`fx-guard.test.mjs` 的已搬名称表同步登记（防双源回退）。

## 双轴评审结论（2026-09-13）

两条轴**同时**指出了同一处最重的问题（这在本项目里是第一次，值得记）：

**① 前端在解析后端拼的文案（硬违规 → 已结构性修掉）**

第一版让后端把「原因 + 第 N 次 + 从 X% 接着下」拼成一句话（`message`），前端再用正则
把「从 X% 接着下」抠回来拼到自己的前缀后面。两个轴各自独立判了它：那等于**把文案当接口**
——后端改一个词，前端静默失配，而且没有任何用例守得住。

修法（改数据形状，不是改文案）：后端把三件事拆成**三个字段**——
`message`（只说原因）/ `retry_count`（第几次）/ **`resume_percent`（从多少接着下；-1 = 总量未知，
0 = 服务器没让我们接上、真的从 0 重下）**；前端零解析，直接拼。前端多写了一条判据：
**文案里塞什么数字都撼不动次数与百分比**（判据是字段）。`probe-03` 与工单 03 的
「从 0 重新下」用例随之改为读字段（`resume_percent == 0`），比字符串断言更结实。

**② verify 话术与「重试」按钮自相矛盾（Spec 轴）**

文案说「重新下载也不会有变化」，同一屏却摆着「重试（已完成卷跳过）」——用户会一直点。
修法：`error_kind == "verify"` 时**不给重试按钮**（仍可点「检查更新」重走一遍）。用例钉住。

**③ 资料库链路的完成行没留痕（Spec 轴）+ 目视证据里资料库载荷是手写的（Spec 轴）**

- `materialsProgressHTML` 补 done 行「（下载中自动重试 N 次）」，与完整包同源（`retryNoteText`）；
- 取证脚本改为**真跑 `ApplyTask`**（三条资料库 case：重试 / 网络失败 / 校验失败），
  渲染脚本不再手写任何字段——「载荷来自真任务」这句话现在对两条链路都成立。

**④ 顺手扩界已撤回**：第一版把 `fullResultText` 的取消文案改成带百分比（本单没要求），
已改回原样。

**未采纳的两条**（判定为「不是问题」）：`fmtEta` 内部用「分钟」而 `fmtDuration` 用「分」
——spec 要的是「复用词形（小时 / 分）不另起一套」，「约 12 分钟」正是 spec 自己给的样例；
非法输入兜底「不到 1 分钟」与旧的「…」占位同义（都是「算不出来」），但它更一致、可断言。

- 前端**不许解析 `error` 文案**来分类（分类只认 `error_kind`）——这条写成断言。
