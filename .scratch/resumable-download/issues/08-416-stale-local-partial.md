# 08 — 服务器 416 与本地坏半成品：别再卡死那一卷

**要做什么：** 让「本地半成品与远端对不上」这件事**能自愈**，而不是把用户卡在一个
反复失败、且界面归因话术还错的死胡同里。

**被谁阻塞：** 无——可立即开始（工单 07 的双轴评审翻出来并留作显式决策点，本单接手）。

**状态：** resolved

- [x] **先红**：探针（`probe-08-416.py`，真 HTTP）在实现之前必须判红——现状是
      416 直接冒泡、任务 failed、坏半成品留在盘上；用户点重试仍带同样的 Range、仍 416。
- [x] 服务器回 `416` → **清掉本地那份、从 0 重下**（spec 断点契约表原话）。
      一次性的 416（服务器上文件变小过）应当自愈；恒 416 也不许无限重试。
- [x] 本地半成品**比远端还大** → 同样「清掉、从 0 重下」，不再直接判死。
- [x] 单测覆盖上面两条 + `is_retryable(416)` 的分类；**反向验证**：拿掉修复必须转红。
- [x] 回归：全套测试 + 工单 01/02/03/07 的探针复跑全绿。
- [x] 如实记账：哪些形态验到了、哪些没验到。

## 为什么这不是「顺手加的边角」

`416 Range Not Satisfiable` 是**本地状态与远端不一致**的唯一网络信号。现状把它当普通
HTTP 错误抛出去，于是：

| 环节 | 现状 | 用户看到 |
|---|---|---|
| 下载 | `HTTPError(416)` 冒泡 → 任务 `failed` | 「下载失败（卷 xxx）」 |
| 归因 | `error_kind="network"` | 「点重试会从这里接着下」（**错的**：重试仍是 416） |
| 盘上 | 坏半成品留着 | 用户得手工去 `updates/full/` 删文件才能恢复 |
| 重试 | 不可重试，一次就判死 | 反复失败，且看不出为什么 |

spec 的断点契约表对这两种情形写得很清楚（「服务器返回 `416`」与「已下字节 > 卷大小」
两行都是「删掉从 0 重下」），实现里只做了一半：**清了**（`_attempt` 前置判据与
`clear_partial` 都在），但**没重下**。

> 命名口径：本仓库的「清掉」= `download_resume.clear_partial(dest)`（半成品 + 边车
> 一起删）。工单 03 立的规矩仍然有效——**删不删是任务层的策略，下载域只给判据**；
> 本单改的是下载域内部的「一次尝试」语义，不碰任务层的保留/删除分界。

## 备注

- 改的是 `download_resume.py` 的**一次尝试**与**重试循环**，不动任务层、
  不动状态面字段（`error_kind` 词表仍是 `"" | network | verify`）。
- 恒 416 的收敛性必须**有界**：不许变成「每 60 秒重试一次的安静死循环」。
  本单的取法见验收记录（思路：清掉之后**同一次尝试内**接着用新起点重来，
  只有再次拿到 416 才算失败）。
- 判据语气沿用本仓库纪律：**先证明判据会红，再用它判绿**（工单 01 立的规矩）。

## 验收记录（2026-09-13）

### 一、先红：同一支探针，实现前后结论相反

证据：`verify-08-416-baseline.txt`（**实现之前**跑的）/ `verify-08-416.txt`（实现后），
同一支 `probe-08-416.py`、同一批用例、真 HTTP 本地线程服务器。

| 用例 | 剧本 | 实现前 | 实现后 |
|---|---|---|---|
| 恒 416 | 铺 102400 字节；**带 Range 恒 416**，不带 Range 正常 | **卡死**：`HTTPError 416` 冒泡，请求数 1，半成品 102400 留在盘上 | **自愈**：请求数 2（`bytes=102400-` → 不带 Range），落盘 307200，哈希一致，边车已清 |
| 一次性 416 | 第一次带 Range 416，之后正常 | **判死**：请求数 1，失败 | **自愈**：请求数 2，哈希一致 |
| 本地比清单还大 | 铺 307200+4096 字节 | **判死**：请求数 0，抛 `DownloadLocalCorruptError` | **自愈**：请求数 1，从 0 重下，哈希一致 |
| `416` 不该是可重试的网络错误 | — | 成立（非回归守卫，两态都 ✓） | 成立 |

**这一格是本单的全部意义**：同一份数据、同一套判据，实现前是「坏半成品把这一卷永久卡住」，
实现后是「自己清掉重下、一次就好」。

> ⚠️ **修正一处本单自己造的假绿（评审翻出来的）**：探针第一版的用例三写的是
> `dest.write_bytes(PAYLOAD[:seed])`，而 `seed = len(PAYLOAD) + 4096` —— **切片会静默截到
> 载荷长度**，于是它铺的其实是「正好一整卷」，走的是「已下完直接进校验」那条早返回：
> 请求数 0、`sha_ok=True`，**在修与不修两种实现下都报 ✓**。
> 也就是说本单第一版证据里「本地比远端大」这一格**从来没有红过**（红基线里它是绿的），
> 而「请求数=0」那句写在一个自称「删掉坏的、从 0 重下」的用例下本来就自相矛盾。
> 现已改成「超出载荷长度就补零字节」，红基线里它**如实转红**。

### 二、改动不止 416——顺着它翻出了**同一类病的另外两处**

评审（工单 07）只报了 416。实现时按「还有哪些地方自称『删掉重下』却没重下」逐个查，
又找出两处，**三处是同一个病**：

| # | 位置 | 原行为 | 现在 |
|---|---|---|---|
| 1 | `_attempt` 的 `416` 分支 | HTTPError 冒泡 → 判死 | 就地清掉、去掉 Range 重来；**仍 416 则不可重试**（见第四节） |
| 2 | `_attempt` 开头的「本地比清单还大」 | `clear_partial` 之后**抛** `DownloadLocalCorruptError`（在 `_NOT_RETRYABLE` 里）→ 清了却没人重下 | 就地清掉、`offset = 0` 接着下 |
| 3 | 重试循环里的「长度对了但内容不符」 | `clear_partial` + `need_clean_slate = True` 之后**抛**同一个不可重试异常——而它的文案写着「已丢弃整份重新下载」 | 真清 + 退避重试；下一轮从 0 整卷重下 |

三处的共同病灶：**「清掉」这一步做了，「重下」那一步没做**，而抛的那个异常在
`_NOT_RETRYABLE` 里，于是流程在「已经清干净了」的状态上直接失败。

第 3 处另外修掉一个**会毁掉已下字节的坑**：原写法把 `need_clean_slate` 置真再抛，
而循环开头会「看到标记就先清一遍」——若哪天有人把那个异常改成可重试，标记就会把
**刚下好的字节**在下一轮开头删掉，永远收敛不了。现在清掉这一步就地做，旗标**已删**
（它再没人置真，是死代码）。

第 3 处还带来一个分类问题，单列了一支异常：内容不符原先复用
`DownloadTruncatedError`（归 `network`、文案承诺「会自动重连接着下」），而它的实际动作是
**整卷重下**、归因是**内容**不是网络。现改为 `DownloadContentMismatchError` →
`error_kind="verify"` + 文案「会重新下载整卷」。

### 三、反向验证：拿掉修复，判据如实转红

```
git stash push -- src/contest_generator/download_resume.py
→ 探针：relentless_416 / transient_416 / local_bigger 三格全红，总判 FAIL
→ 单测：4 failed（+1 skipped，见下）
git stash pop → 全绿
```

**关于那条 skip**：内容不符的用例引用了工单 08 新增的异常类型，若把实现回退一版，
导入期就会 `ImportError` —— 那是 **ERROR 不是 FAILED**，看起来像测试坏了而不是判据发现了回归。
现改成 `getattr` + `skipif`：旧实现上该判据「无从谈起」，skip 才如实。

### 四、收敛性（本单最需要交代的一条，**评审纠正过一次**）

产品的重试策略是**无上限 + 退避封顶 60 秒 + 随时可取消**（spec 定的，不改）。
本单新增的重下会不会变成「安静的无限转圈」？逐条说：

- **带 Range 被 416**：`_attempt` 内**只让步一次**（清掉本地那份、去掉 Range 重来）。
- **本地比清单还大**：清掉之后 `offset = 0`，这一次请求不带 Range，不会再触发同一条。
- **内容不符**：清掉 + 走外层退避，下一轮从 0 整卷重下；若服务器上那份永远与清单不符，
  就一直重试——这是**既定的产品口径**（spec：「无次数上限，随时可取消」），与「截断」同构。
- **清干净后仍 416**：**不可重试，如实抛**。

> **最后一条是本单的评审纠正**：第一版把 `416` 设成可重试的网络错误（`is_retryable → True`），
> 于是「恒 416」的服务器会变成**每 60 秒撞一次墙的安静死循环**——只有用户取消才停。
> 那正是本单要消灭的东西，却差点被本单引入。现在 416 走
> `DownloadRangeNotSatisfiableError`（不可重试，归 `verify`，文案说「请重新点一次下载」）：
> 本地的补救手段只用一次，用尽就如实失败。

> 一句话：**本单消灭的是「不重试的失败」，不是「重试没有上限」。** 前者是 bug，
> 后者是 spec 明确要的行为。

### 五、评审发现的三处「我的实现没说真话」（已全修）

| # | 问题 | 修法 |
|---|---|---|
| 1 | `need_clean_slate` 成了死旗标（再无处置真），而注释仍把它当活机制描述 | 删掉旗标与那个分支，注释改成如实说明「清掉这一步已就地做」 |
| 2 | 异常谱系与 `CONTEXT.md` 里「不可重试只有三种…本地比远端大…」与实现相反；`DownloadLocalCorruptError` 已无人抛 | 谱系表、`is_retryable` docstring、该类型的 docstring、`CONTEXT.md` 全部改成现状（含「⚠️ 无人抛」标注） |
| 3 | `_attempt` 里一句「如实抛（不可重试）」写错（那时 416 是可重试的） | 随第四节的重做一并改对 |

外加两处测试侧卫生问题也一并修了（`_Server416` 的 `always=False` 分支无人用、
`starts()` 与 `_FakeServer.starts()` 重复）——工单 07 的双轴评审也报过同类项。

### 六、本单没做的事（别读大）

- **没改任务层与状态面契约**：`error_kind` 词表仍是 `"" | network | verify`；
  半成品「保留还是删除」的分界（工单 03 立的规矩）一行未动。
- **没改「服务器上那份与清单永久不符」的策略**：仍然无上限重试、靠用户取消（第四节）。
- **`_attempt` 里新增的「本地比清单还大」分支在产品主路径上够不到**（评审指出，属实）：
  两条任务链路在调下载器**之前**就已经 `clear_partial` 掉「长度 ≥ 卷大小」的半成品
  （`is_resumable_partial` 的判据），所以它只在**直接调用下载器**、或**重试轮次里服务器多发**
  时才会走到。留着它是防御性的（下载域不该假设调用方一定先清过），判据也覆盖到了；
  但**别把它当成用户可见的修复**——用户那条路上真正修好的是第 1、3 处。
- **没在真资产上造过 416**：本单的 416 全部来自本地可控服务器（真 HTTP、真 Range 协议）。
  真机三档（工单 06/07）跑的是正常服务器，**没撞到过 416**——这个工况本来就是异常路径。
- **`DownloadLocalCorruptError` 保留但已无人抛**：类型、文案映射、分类都留着
  （任务层与 `error_kind` 仍认它），docstring 里已标「⚠️ 工单 08 起无人抛」。
  若评审认为该连类型一起删，那是另一单的事。

## 双轴评审结论（2026-09-13）

两条轴各自独立跑（评审对象 = 本单未提交改动）。**两轴各翻出一处我自己造的假象**，
都当场修掉并复跑：

**Spec 轴**——两处，都是「我的判据在骗我」：

| # | 问题 | 性质 | 修法 |
|---|---|---|---|
| 1 | 探针用例三（本地比远端大）写 `PAYLOAD[:seed]`，`seed > 载荷长度` 时**切片静默截断** → 铺的是「正好一整卷」→ **两态都报 ✓**，红基线里本该红的格子是绿的 | **判据假绿**（最坏的一类：它声称验了、其实没验） | 改成超长补零字节；红基线如实转红（见第一节的 ⚠️ 注） |
| 2 | `416` 被设成可重试的网络错误 → 恒 416 的服务器变成**每 60 秒撞一次墙的安静死循环**（只有用户取消才停）；而钉住它的用例自带 `max_attempts=1`，等于**自己给自己设了界** | 收敛性缺陷 + 判据自带答案 | 416 改不可重试（`DownloadRangeNotSatisfiableError`，归 `verify`）；用例去掉 `max_attempts`、不传上限仍须立刻抛 |

同轴另两条经核实**成立且无需改**：三处重下都真的可达（唯一例外见第六节：产品主路径够不到
「本地比清单大」那条，属实、已如实记账）；测试在忠实回退下会红（回退版实测 6 failed）。

**Standards 轴**——1 处死代码 + 1 组自相矛盾的文档：

| # | 问题 | 修法 |
|---|---|---|
| 1 | `need_clean_slate` 成了死旗标（全仓再无处置真），而注释仍把它当活机制、同一 hunk 里还写着「不能只 clear 不清它」 | 删旗标与死分支，注释如实说明清掉已就地做 |
| 2 | 异常谱系 / `CONTEXT.md` 仍写「不可重试只有三种…本地比远端大…」与实现相反；`DownloadLocalCorruptError` 已无人抛却仍被描述成在用 | 四处文档改成现状 + `⚠️ 无人抛` 标注 |
| 3 | 内容不符复用 `DownloadTruncatedError` → 归 `network`、文案承诺「自动重连」，与实际动作（整卷重下）和归因（内容）不符 | 单列 `DownloadContentMismatchError` → `verify` + 文案「会重新下载整卷」 |

另有两条测试侧卫生问题（`_Server416` 的 `always=False` 分支无人用、`starts()` 与
`_FakeServer` 重复）一并清理。

**为什么这轮评审特别值**：Spec 轴翻出的第 1 条是**判据自己假绿**——如果不查，
本单会带着一个「验过了」的假象入库，而它从来没有红过。这正是本仓库反复记过的那个坑
（工单 01 的「判据自己也会错」），这次是它自己撞上来的。
