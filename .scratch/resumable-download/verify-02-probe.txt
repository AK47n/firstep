**怎么读这两条关键证据**（都不是"跑绿了"，而是数字本身在说话）：

| 用例 | 证据 | 说明 |
|---|---|---|
| `cut` | 起始偏移 `[0, 838860, 1342176, 1644166]` | 连断 3 次，每次都从**上一次断掉的那个字节**接着下；最终哈希与载荷逐字节一致 |

对照工单 01 的红基线（同一套判据、同一个载荷）：那时 `cut`/`stall` 都是
**「被截断却自称成功」**、起始偏移恒为 `[0]`。同一判据由红转绿。

## 三、单测覆盖（`tests/test_download_resume.py`，25 条）

| 组 | 覆盖 |
|---|---|
| 策略与文案 | 退避序列 2/4/8/16/32/60；`is_retryable`（5xx/429 可重试，404/403 与两类领域错误不可重试）；中文文案；`error_kind` 单源 |
| 偏移判定 | 全新下载；本地 100 KB → 只请求尾部；连断后按偏移接续并如实报重试；服务器忽略 Range → 从 0 重下降级 |
| 截断与矛盾 | **截断必须失败**（归因是「连接中断」，不许扣「发布信息不一致」）；响应声明比清单短 = 不可重试；清单写错 = 不可重试 |
| 本地坏 | 本地比远端大 → 清掉 + 不可重试；本地已完整且哈希相符 → 零字节零请求 |
| 阈值 | 小卷（低于 `min_resume_bytes`）整卷重下，请求不带 Range |
| 取消 | 退避中置位 → 不再发起下一次；开跑前置位 → 不碰网络；半成品与边车保留 |
| 观测面 | `before_retry` 自己抛异常不许把下载带崩 |

## 四、本次实现踩到并修掉的四个真坑（都留了判据）

1. **`Content-Range` 第三段是资源总长，不是本次响应长度**：拿「本次收到 < 总长」判截断，
   会**误伤每一次正常续传**（本地 102400 + 本次 204800 = 307200，却被判「连接中断」）。
   正确判据 = **已落盘 + 本次收到** < 声明总长。
2. **「尺寸到点但内容坏」是死局**：若只给 `expected_size`，服务器见「你要的起点=整卷大小」
   就不发字节，重试每次都收 0 字节，白转到上限（实测报「重试 4 次仍未下完（307200 / 307200）」）。
   解法 = 一并传清单 `sha256`：不符就清掉整份重下。
3. **长度判定必须写在重试循环内**：写在循环外时，第一次尝试结束就跳出，`continue` 永远走不到，
   「自动重试」形同虚设（这是我自己写的第一版）。
4. **`min_resume_bytes` 原来定 1 MB 太高**：探针实测断在 800 KB 时走的是「整卷重下」。
   门槛的含义是「一次断流最多白下多少」，改 64 KB。
