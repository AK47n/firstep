# 工单 06 档③ 证据：真实完整包端到端（resumable-download/06）

日期：2026-09-13　脚本：`.scratch/resumable-download/verify-06-tier3.py`
原始数据：`verify-06-tier3.json`、`verify-06-tier3-resume.txt`（确定性那一段的运行输出）

## 一、这一段验的是什么（以及它**替代**了什么）

工单原本的剧本是：「真实完整包 → 下载 → **中途断开一次确认从偏移接上** → 替换 → 重启」。

实际执行下来发现那个剧本**在快网上不可控**：783 MB 在本机只要 ~80 秒，20–25% 的目标
往往在杀掉进程之前就已经越过（实测两次：一次杀在下载完成之后、一次杀在 25% 但刚好
下载已结束）。所以本单改成两段互补的取证：

| 段 | 做什么 | 判什么 |
|---|---|---|
| ① 真跑一遍（`verify-06-tier3.json` 的 phase1/phase2） | 一次性工具根起服务 → 真检查 → 真下载 → 杀进程 → 重启再点下载 | 真实链路能不能走通（含**一次真的把 783 MB 下完并校验通过**） |
| ② **确定性**复检（本文件） | 用**真 `Range`** 取线上资产前 32 MB 铺成半成品 + 边车 → 交给**产品自己的 `FullDownloadTask`**（真 URL）跑完 | 「盘上有半成品 + 边车时，真任务会不会接着下」——这条判据本身不依赖杀得多准 |

## 二、确定性复检：成立（这一条是本单最硬的证据）

```
真资产：https://github.com/AK47n/firstep/releases/download/v1.1.1/firstep-full-v1.1.1.zip
先取前 32 MB（真 Range 请求）→ 铺好 32.0 MB + 边车 firstep-full-v1.1.1.zip.partial.json
state=done / 用时 78.0s / 下载器每次尝试的起始偏移 [33554432]
卷状态：ok=True / downloaded_bytes=821352026（= 清单里的 783 MB）
→ 从断点接着下：成立（第一次尝试起始偏移 33554432，不是 0）
```

**怎么读**：真任务在真 783 MB 资产上，第一次尝试就从 **33,554,432 字节**（铺下去的那 32 MB）
接着要 `Range`，而不是从 0 重来；最终整卷校验通过（`ok=True`）。
`33554432` 这个数字就是判据本身——它不是探针自己重试出来的，是产品代码里那条路。

## 三、真跑那一段：下完了、替换没走完（`verify-06-tier3.json`）

第一次真跑（本文件同目录的 JSON）：

- 真检查：`latest=v1.1.1`，分卷 1 个，`783 MB`，`error=''`；
- 真下载：**完整下完 783 MB 并校验通过**（`full-task.json` 快照：`ok: true`,
  `downloaded_bytes: 821352026`，与清单 `size` 一致）；
- 替换：写了 `pending-update.json`（`mode: full` / `parts: [firstep-full-v1.1.1.zip]` /
  `manifest: …manifest.json`）并拉起更新器，但**没走完**（任务终态 `failed`，
  工具根没被替换，更新器没有留下日志）；
- 因此**「重启后版本号正确」这条完成判据本轮没验到**。

## 四、这一档实测出来的**真产品缺陷**（已修 + 已钉判据）

**硬杀进程留下的半成品没有边车 → 重启后白下 210 MB。**

第一次真跑就是这么走的：下到 210 MB 时把服务进程杀掉，盘上是
`firstep-full-v1.1.1.zip`（210 MB）+ **没有** `.partial.json`；重启后点重试，
任务把这份半成品当「来路不明的不完整文件」清掉，**从 0 重下**。

根因：边车原来只在「取消 / 失败」两处写，而**硬杀**（任务管理器结束进程 / 崩溃 / 断电）
两条路都不走。修法：`resumable_download` **开跑就写边车**（成功路径本来就会清掉）。
判据：`tests/test_download_resume.py` 两条——
`test_download_start_writes_sidecar_so_a_killed_process_can_resume`（下载进行中边车必须在场）
与 `test_success_clears_the_early_sidecar`（成功必须清干净）。

> 如实记账：改的是「验出来的真缺陷」，判据、根因、修法都写在上面的工单 03 验收记录里；

## 五、本轮**没验到**的（别读大）

1. **替换 → 重启后的版本号**：第一次真跑卡在替换环节（见第三节），本轮没看到
   「重启后工具根变成线上包版本」。
2. **中途断网（拔线 / 代理掐断）而不是杀进程**：本单用的是杀进程 + 确定性铺半成品两条路，
   「网还在但传输断了」这一形态由档① 的 `cut` / `stall` 覆盖（本地可控服务器），
   没在真资产上造过。
3. **8020 沙箱那条路径**：本单跑的是**一次性工具根**（`%TEMP%`），没动
   `Desktop\firstep-sim` 沙箱（跑档③ 会把它替换掉）。
4. **演练期间的隔离边界（诚实记账，把能核实的与不能核实的分开写）**：

   - **演练脚本第一版有个缺陷**：它只重定向了 `USERPROFILE`，而 `contest_generator.config`
     的 `DEFAULT_CONFIG_PATH = Path.home() / ...` 是在**模块导入时**就求值的，所以那次
     运行**没能真正隔离数据目录**；后来改成启动时显式传 `config_path`（shim）才隔离住。
   - **可核实的现状**：真身 `~\.contest_generator` 目录 mtime = `2026-09-12 23:48:39`
     （早于本次演练），目录内既有文件都在；`updates\` **存在但空**（0 个条目）——
     即演练没在真身目录里留下 zip / 快照 / 待更新标记。
   - **不能核实的**：第一版脚本那次运行**到底有没有**在真身目录里写过东西，事后已无法判定
     （那次打印的「mtime 变了」既可能是脚本的误报，也可能是真的写过又被清掉了）。
     其中临时下载物在 `%TEMP%` 演练目录里，已随目录删除。
   - 结论按**保守**写：**不能声称「真身数据目录全程零触碰」**；能证实的是「此刻真身目录
     内容与演练前一致（mtime 早于演练、upserts 目录为空）」。下次跑这一档务必先确认
     启动 shim 生效（`app.log` 里的 updates 路径应当落在演练目录里）。
