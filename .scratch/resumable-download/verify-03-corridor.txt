# 工单 03 验收证据：两条链路接上可续下载（resumable-download/03）

日期：2026-09-13　判据来源：**真 socket**（`.scratch/resumable-download/probe-03-corridor.py`
驱动 `sim-server.py`，工单 01 的那台可控服务器）
被测对象：`FullDownloadTask`（完整包，缺省下载器，不注入假件）+ 同源改法的 `ApplyTask`（资料库）
原始数据：`verify-03-corridor.json`（本文件是它的读法）；反证：`verify-03-negative.txt`

## 一、走廊：断 3 次 → 自动重试 → 接上 → 完成（总判 PASS）

```
实现 = contest_generator.full_task.FullDownloadTask
载荷 = 2097152 字节；断流点 = 每次剩余部分的 40%，连断 3 次；退避压到 0.2 秒

OK corridor    state=done  0.7s
   请求起始偏移 [0, 838860, 1342176, 1644166]      重试计数 3
   落盘 2097152/2097152   哈希一致   边车还在 False   终态摘要清空
```

**怎么读**（都不是「跑绿了」，是数字本身在说话）：

| 判据 | 数据 | 说明 |
|---|---|---|
| 断点续传 | 起始偏移 `[0, 838860, 1342176, 1644166]` | 连断 3 次，每次都从**上一次断掉的那个字节**接着下；4 次请求 = 1 次首发 + 3 次自动重连 |
| 重试如实 | `task_retry_count = 3` | 与服务器台账里的 3 次重连**对得上**（任务不再自己重试，计数由 `before_retry` 从下载器内部上报） |
| 最终正确 | 落盘 2097152/2097152，`sha_local == sha_expected` | 断点拼接出来的文件与载荷逐字节一致 |
| 进度没算丢 | `part_downloaded_bytes == 2097152` | 续传时「本轮起点 + 本次读到」都算进进度（工单 03 备注点名的那条） |
| 不留孤儿 | `marker_left = False` | 成功后边车被清掉 |
| 终态干净 | `message_at_end = ""` | 进行中的摘要只在过程中出现，终态原因走 `error` |

**与工单 02 的同一套数字对照**：02 那支探针（直接测下载函数）跑出的 `cut` 起始偏移是
`[0, 838860, 1342176, 1644166]`——本单在**任务层**跑出**逐字节相同**的序列。
这说明「接上了」不是探针自己的重试循环凑出来的，而是产品代码里的那条路。

## 二、忽略 Range：带了断点、服务器不认 → 从 0 重下但文件仍正确

```
OK ignore-range   state=done  0.01s  起始偏移 [1048576]
   种子半成品 1048576 字节（带边车）；服务器恒回 200 整份
   最终 2097152/2097152，哈希一致，进度 2097152（不超算）
```

**判什么**：带 `Range: bytes=1048576-` 去请求 → 服务器忽略它回 200 整份 → 任务必须
**丢弃半成品从 0 重写**（拼接会得到坏文件），最终哈希仍要与载荷一致；进度基准也要跟着
回到 0（拿「调用前盘上有多少」当基准会把已丢弃的 1 MB 继续算进进度 = 进度超算）。

> 判据卫生（本单修的一处）：模拟服务器的台账原来在 `ignore-range` 模式下把
> 「起始偏移」记成 0（= 服务器实际从哪发），于是「客户端带了 Range 却被忽略」这件事
> 在台账里根本看不到——任务层明明做对了，判据却判它「第一次请求没带 Range」。
> 现在台账记的是 **Range 头里客户端要的那一段**，两种语义不再混。

## 三、失败态 + 跨进程续传（用户视角收益就长在这儿）

这条才是工单 03 的要害：**跑了半截失败 → 换个任务实例（= 换一次进程）→ 接着下**。

```
OK failed-case   state=failed  0.03s
   断流 1 次后失败：落盘 838860/2097152，边车在（resumable_next_time = true）
   新任务实例第一次请求起始偏移 = 838860  ← 正是上一个任务断掉的字节
   第二个实例 state=done，最终哈希一致
```

「重启后不重下已完成部分」这条验收标准，判据就是那个 `838860`：它等于第一个任务的落盘
长度，而不是 0。

## 四、本单实测出来的真问题（都留了判据）

| # | 问题 | 怎么发现的 | 现在怎么防 |
|---|---|---|---|
| 1 | **失败态不写边车**：`write_partial_marker` 只出现在「取消」与「重试用尽」两处，而产品的重试**无上限**——「重试用尽」真机上永远走不到。于是断流失败后盘上只有半成品、**没有边车**，下一个进程把它当来路不明的东西清掉重下 | 本单探针的失败态用例：`marker_left = False` / `resumable_next_time = False`，而任务层明明保留了半成品 | 边车改在**重试循环内**写（失败即写）；`tests/test_download_resume.py::test_failure_writes_sidecar_for_the_next_process` 钉住 |
| 2 | **「服务器不支持续传」这句话永远说不出来**：`restarted` 想用 `_attempt` 的返回值带出来，可截断是**在 `_attempt` 内部抛的**——返回值那一行根本走不到，于是 `before_retry(..., restarted=False)` 恒为假 | 双轴评审（Spec 轴）指出；写用例复现：起始偏移明明是 0，消息却写「从 21% 接着下」 | 改成 `_RestartFlag` 记号（`_attempt` 里**先记账再可能抛**）；`test_ignored_range_retry_message_says_from_zero` 钉住 |
| 3 | **盘上已是一整卷却被删了重下**：`is_resumable_partial` 对「长度到点」返回 False，调用点于是 `clear_partial` —— 任何「文件已下完但快照没记 ok」的卷白下几百 MB | 双轴评审（Spec 轴）指出（spec 断点契约表：「已下字节 == 卷大小 → 不再发请求，直接进校验」） | `_download_one` 加「长度到点 → 跳过下载直接校验」分支；两条链路各一条用例（`server.starts == []`） |
| 4 | **进度会超算**：基准取「调用前盘上有多少」，而服务器忽略 Range 时会丢弃半成品从 0 重下——那部分字节还在进度里，能算出「进度 > 卷大小」 | 双轴评审（Spec 轴）指出 | 基准改由**下载器每轮开始时报**（`on_start`）；用例：`test_server_ignoring_range_restarts_progress_without_overcounting` |
| 5 | **判据读错了时刻**：`marker_left` 在「第二个任务跑完」之后才读——那时边车已被（正确地）清掉，把「已经清干净」误判成「从来没写过」 | 全用例判红，但手工复现里边车明明在 | 失败态快照改在第二个任务**开跑之前**取；探针注释写明这个坑 |

> 1/2/3/4 是**真产品缺陷**（已修），5 是判据自身的卫生问题（工单 01 立的规矩：判据自己也会错）。
> 3/4 由本单的**双轴评审**发现——真 socket 探针没覆盖到「忽略 Range 后进度」与「完整卷复用」这两条。

## 五、反向验证（详细留痕见 `verify-03-negative.txt`）

对照实现 = 缺省下载器外面包一层「每次尝试前先删半成品」（旧行为：不留断点）。

- **失败态用例转红**：`resume_start_after_restart = 0`（正证同一格是 `838860`）——
  证明「保留半成品 → 下次接着下」这条判据真的在判别，不是恒绿。
- **走廊 / 忽略 Range 两例在反证下不判**（探针里显式登记为「仅登记不判」）：它们的重试
  都发生在**同一个进程内**、且由下载器自己接上，与「失败后删不删」无关。
  头两版反证就是想在这里判红，结果得到的是**假红**（理由与要否掉的事无关）——
  返工细节写在 `verify-03-negative.txt` 与探针 `make_negative_class` 的注释里。
