# 下载抗断（resumable-download）spec

> 范围经用户确认（2026-09-13 会话，三处取舍逐条拍板）：
> ① 缝改在**共用下载层**——完整包与资料库批次包一起受益；
> ② 断线**自动重试到成功但每次都告知**（无上限、可随时取消）；
> ③ 服务器忽略 `Range` 返回 200 时**从头重下并在界面说明**（不浪费用户等待，也不硬失败）；
> ④ 本轮 UI 只做**进度人话化 + 弱网提示**（重启后续下 / 磁盘预检说理不做，见「范围外」）；
> ⑤ 真机复检走**三档**：本地可控服务器 → 线上真资产 → 真实完整包端到端。
>
> 本特性**显式扩界**：`newuser-download` spec 的「不改任何下载行为与下载器代码」是那一轮的边界，
> 本轮用户明确要求改下载行为本身，故那条边界在此作废（见「补充说明 · 与上一轮的关系」）。

## 问题陈述

用户从 GitHub 或工具内开始下载完整包（821 MB 单卷）时，**一次网络抖动就白下**：

1. **卷内没有断点。** 下载是单连接流式写盘，落盘标记只记在**卷**这一级——卷没下完，
   重试就从字节 0 重来。手机上热点、宿舍网、公司代理随手一抖，前功尽弃。
   实测判据：`download_part` 一次 `urlopen`、256 KB 分块、只在**全部读完**后才由调用方
   算 SHA256 并标 `ok`；`full_task._download_one` 失败时 `dest.unlink()` 直接把半成品删掉。
2. **断了不会自己接。** 传输失败直接冒泡到任务层，整个任务转 `failed`，等用户回来点「重试」。
   用户不在电脑前 = 一晚上白等；而这类失败绝大多数是**瞬时的**（连接被重置、代理掐断、
   服务端偶发 5xx）。
3. **状态面不说人话。** 进度区写「剩余 720 秒」；速度掉到 20 KB/s 时，界面与「断了」长得一样，
   用户分不清「慢」、「卡死」还是「已经失败」；失败原因直接把 `URLError` 类的原始信息甩出来。
4. **⚠️ 截断被当成「下完了」（工单 01 探针实测，比预期更硬）。** 下载实现以「每次读 256 KB、
   读到空为止」的循环收工，**从不校验 `Content-Length`**：对端声明 2 MiB、实际只发 40% 时，
   它读成「正常读完」并返回一个自称成功的 SHA256。用户侧因此看到的是
   「进度条跑到 100% → 报校验失败 → 从头再来」，而不是「网络断了」。
   证据：`.scratch/resumable-download/verify-01-baseline.txt`（预登记红基线）。

结论：**主要摩擦不是带宽，是「已经下了 90% 的那部分会消失」和「断了之后没人拉它一把」**，
而且**连「断」这件事本身都还没被识别出来**。

## 方案

把「下载一卷」从「一次连接读完」升级成**可续、可观测、会自愈**的过程，两条下载链路同源受益：

1. **卷内断点续传**：超过 1 MB 的卷改用 `Range` 请求续下，已落盘字节直接接上；
   小卷（≤ 1 MB）不折腾，直接整卷重下。
2. **瞬时失败自动重试**：断流 / 超时 / 连接重置 = 换连接从断点接着下，指数退避（2 秒起、封顶 60 秒），
   **无次数上限**，但每次都在界面上如实写「第 N 次自动重试」；用户点取消随时中断（退避等待中也能立刻停）。
3. **卡死可判**：既靠 socket 读超时，也靠「数据不动了」的判据——两者都归入「可重试的网络失败」。
4. **半成品保留**：`下载中 / 已取消` 的半成品**不再删除**（删了就等于断点没了），
   只在两种情况下丢弃：校验失败（重下也是坏的）、本地比远端还大（本地文件是坏的）。
5. **失败说人话**：把底层网络异常翻成中文可行动句子，并带上**已经下到多少**：
   「网络中断（已下载 68%，下次会从这里接着下）」。
6. **进度看得懂**：剩余时间从「720 秒」改成人话（「约 12 分钟」）；速度过低时明写
   「网络较慢」，重试期间明写重试次数——让「慢 / 卡 / 失败」三态在界面上长得不一样。

## 用户故事

1. 作为用手机热点下完整包的用户，我想要断网后从断点接着下，以便不必重下已经下完的几百 MB。
2. 作为把下载挂在后台去吃饭的用户，我想要它自己重试，以便回来时是下好了而不是停在失败态等我点。
3. 作为看着进度条的用户，我想要知道「现在是在重试还是在慢慢下」，以便判断该等还是该换个网。
4. 作为断网后又连上的用户，我想要重试**自动**发生而不是要求我先点一下，以便不必守在电脑前。
5. 作为看到「剩余 720 秒」的用户，我想要它写成「约 12 分钟」，以便一眼判断要不要现在等。
6. 作为速度只有几十 KB/s 的用户，我想要界面明说「网络较慢」并给出预计时间，以便知道不是卡死了。
7. 作为遇到失败的用户，我想要中文的、带下一步的失败原因（已下多少 / 会不会重下），以便决定怎么办。
8. 作为想取消的用户，我想要在重试等待期间也能立刻取消，以便不必等退避时间走完。
9. 作为中途取消的用户，我想要已下部分保留且下次接着下，以便取消不再等于清空进度。
10. 作为下资料库增量包的用户，我想要同一套「续 + 重试 + 说人话」，以便不必等完整包那轮才受益。
11. 作为维护者，我想要断点续传的验证有一条**真网络**路径（本地可控服务器），以便不必靠真断网来回归。
12. 作为维护者，我想要「半成品保留、校验失败才丢」这条不变量被测试钉住，以便下次改动不会悄悄退化成删文件。

## 实现决策

### 模块与接口

**新增域模块 `download_resume.py`**（宿主：与 `materials_task.py` / `full_task.py` 同层，属「下载」域；
两者都要用它，故不能塞进任一侧，否则造成同层依赖）：

- `DownloadResult`（dataclass）：`sha256: str`、`transferred_bytes: int`、`attempts: int`、
  `resumed_from: int`（本次真正用 Range 接上的起始偏移，0 = 从头）。
- `resumable_download(url, dest, on_progress, *, cancel=None, before_retry=None, ...) -> DownloadResult`：
  **保签名兼容** `download_part(url, dest, on_progress)` 的三参调用形态（前三个参数位置与语义不变），
  新增参数全部关键字可选。
- `describe_network_error(exc) -> str`：底层异常 → 中文可行动句子（单源文案）。
- 退避策略 `retry_delay(attempt) -> float`（2、4、8、16、32、60、60…）——函数住模块内，
  **不进设置页**（本仓库先例：不引入新配置项）。

**`download_part` 保留**为「单次尝试」语义的实现（`download_resume` 内部调用它），
既有 monkeypatch 点（`tests/test_full_task.py` / `tests/test_full_apply.py` 打 `full_task.download_part`）
**继续有效、零改动**。

**任务层**（`full_task.py` / `materials_task.py`，两条链路对称改）：

- `download` 缺省值 → `resumable_download`（注入点与 `(url, dest, on_progress)` 三参签名不变，
  既有假下载器照旧可用——新增能力只在**缺省实现**里）。
- `_download_one` **删掉** `dest.unlink()`（两处，分别在下载异常与校验失败分支）：异常分支保留半成品，
  校验失败分支才删。
- 下载完成后**直接用 `DownloadResult.sha256`** 判等（不再重复读盘算哈希）；仍保留「返回裸字符串」
  的兼容分支（= 注入的假下载器），此时按既有行为读盘算哈希。
- 任务新增重试状态：`retry_count`、`last_retry_at`、`last_error_kind`（内存态，不落快照）。
- `before_retry` 回调：写重试计数并把「正在重试」摘要塞进 status；退避等待通过
  `cancel.wait(delay)` 实现，**取消在退避中即刻生效**。

### 断点契约（写工单时按这个口径，别即兴）

| 情形 | 判据 | 动作 |
|---|---|---|
| 本地无文件 / 0 字节 | — | 从 0 开始，不发 Range |
| 本地已有 N 字节，卷 > 1 MB | 发 `Range: bytes=N-` | 期望 `206`；`Content-Range` 与 N 对齐则续写 |
| 服务器忽略 Range | 收到 `200` | **丢弃本地半成品，从 0 重下**，并在重试消息里说明「服务器不支持续传」 |
| 服务器返回 `416` | — | 本地比远端大 = 本地坏：**清掉本地那份、去掉 Range 从 0 重下**；若清干净后仍 `416` → 不可重试，中文报「本地记录与远端对不上，请重新点一次下载」 |
| 已下字节 == 卷大小 | 本地长度自证 | 不再发请求，直接进校验 |
| **下完但内容与清单 SHA256 不符** | `DownloadResult.sha256` 与清单比对 | **删半成品 + 走退避重试**（从 0 整卷重来，直到对上或用户取消）；单列 `DownloadContentMismatchError`，归 `error_kind="verify"` |
| 本地已下字节 > 卷大小（清单说的大小） | — | 本地那份是坏的：**清掉、从 0 重下**（不再抛不可重试异常） |
| **被截断**（实收 < 对端声明） | `Content-Length` / `Content-Range` 给出的总长 vs 实收 | **算失败**（当前实现把它当成功，是工单 01 实测到的缺陷）；半成品保留，走重试 |
| **清单 size 与对端总长矛盾** | 清单 `size` vs 响应给出的总长 | **不可重试**：这是发布物与清单不一致，重试同样结果；中文直报「发布信息不一致，请稍后重试或反馈」 |
| 单次尝试到点（size 已知且已达） | — | 当作成功，进校验 |

> **工单 08 补记（2026-09-13）：上表有五行被实现改写，「重下」那一半此前根本没做。**
> `416`、`本地已下字节 > 卷大小`、`下完但内容不符` 三条，实现里都是**清掉本地那份
> 之后就抛 `DownloadLocalCorruptError`**——而它在 `_NOT_RETRYABLE` 里，于是重下从来没
> 发生，坏半成品把那一卷**永久卡住**（用户点重试仍带同样的 `Range`、仍 `416` 或仍失败）。
> 其中「内容不符」那条的异常文案还写着「已丢弃整份重新下载」，说了一套做了一套。
> 工单 08 的处置：前两条**就地清掉重来**（同一次尝试内完成），内容不符**清掉 + 走退避重试**。
> 另按「本地的补救只做一次、再做还是 416」把持久 `416` 定成**不可重试**
> （否则就是每 60 秒撞一次墙的安静死循环），归 `error_kind="verify"`。
> 判据见 `tests/test_download_resume.py`：
> `test_http_416_clears_stale_partial_and_redownloads` /
> `test_http_416_without_range_is_not_retried_forever` /
> `test_local_bigger_than_manifest_recovers_from_zero` /
> `test_content_mismatch_is_retried_from_zero`；
> 真 HTTP 探针 `.scratch/resumable-download/probe-08-416.py`（含实现前的红基线）。
> 表内其余各条不变。

**跨进程残留**：`dest` 旁落 `.partial.json` 边车（只记 `url` 与期望总字节），**只在取消 / 失败时写**；
进程重启后 `run()` 里若发现「本地长度 + 边车期望」自洽，就继续用、不重下。
本轮**不做**重启后的 UI 入口（见「范围外」），边车只为「下次接着下不多下一份」这个事实。
成功 / 校验失败时**一并删除边车与半成品**，不留孤儿。

> **⚠️ 本条已在实现中被真机实测推翻一半（工单 06 档③，2026-09-13）**：
> 「只在取消 / 失败时写」漏掉了**硬杀进程**（任务管理器结束 / 崩溃 / 断电）——
> 那两条路都不走，盘上于是只剩半成品、没有边车，下一个进程把它当来路不明的文件
> 清掉重下（实测白下 210 MB）。**现行为 = 开跑就写**（取消 / 失败时兜底重写，成功
> 与校验失败时照旧一并清掉）。本节其余各条不变。
> 权威口径见 `CONTEXT.md` 的「下载抗断」行；判据见
> `tests/test_download_resume.py::test_download_start_writes_sidecar_so_a_killed_process_can_resume`
> 与 `tests/test_download_resume.py::test_success_clears_the_early_sidecar`。
> 原文保留在此，是为了让后来的人看得见「契约怎么被现实修正的」，不是现行口径。
### 状态面契约（前端消费）

`task_status` / `full_task_status` 的既有字段**一个不改**（前端零破坏），**新增**三个：

- `retry_count: int`——本卷（当前 `current_part_name`）累计自动重试次数；
- `retrying: bool`——当前是否正处在退避等待中；
- `error_kind: str`——`""` / `"network"` / `"verify"`（前端据此选话术，不解析文案）。

`message` 字段（现在恒为 `""`）复用为**进行中的摘要**，如「网络中断，第 2 次自动重试，从 68% 接着下」；
终态时清空（终态原因走 `error`）。

### 前端

- `core.js` 新增共享格式化 `fmtEta(sec) -> "约 12 分钟" / "约 1 小时 20 分"`（复用既有
  `fmtDuration` 的词形，不另起一套），两条进度区共用。
- `full-update.js`：剩余时间改 `fmtEta`；速度 < 50 KB/s 时补「网络较慢」；`retrying` 时进度区
  明写重试；完成行在有重试时补「（下载中自动重试 N 次）」。
- `materials-update.js`：同一套口径；顺带修掉它现在显示 `done / total 字节` 的原始数字
  （与完整包用 `formatSize` 不一致）。
- 失败文案：`error_kind == "verify"` → 校验失败话术（明确「重下不会有变化」）；
  其余 → 网络话术 + 已下载百分比。

## 测试决策

沿用**三个既有缝**，不新造跨层缝：

1. **注入缝（最高、已在用）**：两个任务类的 `download` 可注入参数——既有假下载器全部原样可用，
   证明「三参签名兼容」这条契约。新增用例走 `resumable_download` 的注入式单测。
2. **单元缝**：新增 `tests/test_download_resume.py`
   - `describe_network_error` 对 `URLError` / `TimeoutError` / `ConnectionResetError` / `IncompleteRead`
     / 其它 `OSError` / `HTTPError` 的中文映射（含**文案里带「可重试 / 不可重试」语义区分**）；
   - 退避序列（2→4→8→16→32→60→60）；`cancel` 在退避中被置位 → **不发起下一次尝试**、立即返回取消；
   - `resumable_download` 的偏移判定用**假尝试函数**（返回 `DownloadResult`）驱动，不碰网络：
     本地 0 字节 → `resumed_from == 0`；本地 N 字节 → `resumed_from == N`；
     尝试返回「服务器不支持续传」→ 落盘从 0 重新计；到点成功；校验不符不重试。
3. **真网络缝（本特性新造，但只给探针用，不进 `tests/`）**：
   `.scratch/resumable-download/sim-server.py`——本地可控 HTTP 服务器，
   支持 `Range`/`206`、`416`、忽略 Range 的 `200` 模式、**中途断流**、**卡死不动**、
   **死线到点**、**慢速**六种可切换行为；探针跑真 socket，验「断 3 次仍能从偏移接上且最终 SHA256 正确」。
   为什么不进 `tests/`：真 socket 与 sleep 会让 CI 变脆；**行为判据（偏移/重试/校验）已由缝 1、2 覆盖**，
   探针只回答「真 socket 上确实如此」。

**真机复检三档（本轮完成判据，不是单测）**：

| 档 | 做什么 | 判什么 |
|---|---|---|
| ① 本地可控 | 探针连 `sim-server.py`，依次跑稳定 / 断流 / 卡死 / 忽略 Range | 断点偏移正确、重试如实计数、忽略 Range 时从 0 且**最终哈希正确** |
| ② 线上真资产 | 用 `Range` 对**真实线上资产**取分段（已实测 `206`），并跑一次小卷真实下载 | GitHub 侧确支持（**已验证**，复检防回归） |
| ③ 真实完整包 | 8020 沙箱口径跑一遍真实完整包下载 → 替换 → 重启 | 端到端不回归；中途断开一次，确认从偏移接上 |

**反证要求（防假绿）**：至少一处**故意让断点逻辑失效**（例如强制每次从 0 开始）并证明探针转红——
本项目已多次踩到「判据本身失效导致的假绿」。

## 范围外

- **重启后的「上次下到 45%，接着下」UI 入口**：用户本轮未选。半成品与边车按上文保留，
  数据先攒着，将来要做时不必再动下载层。
- **磁盘预检说理化**（「为什么需要 1.5 倍空间」）：用户本轮未选，`full_apply` 的
  `DISK_HEADROOM_FACTOR` 与端点文案**一行不动**。
  注意一处事实修正：磁盘预检的 1.5× + 16 MB 是**上界**（旧口径是「必须能同时装下下载量 + 备份量」），
  现在有半成品续传后实际占用只会更低——**不收紧阈值**（收紧 = 逼走本来能装下的用户）。
- **多连接 / 分片并行下载**：那是提速，不是抗断；且会打乱 GitHub 的限流语义，本轮不做。
- **资料库增量之外的其它下载**（如参考库素材、模块包）：不在本轮。
- **`newuser-download` 已交付部分的回改**（README / Release 说明 / `00-START-HERE.txt` / 资产名）：
  一律不动。
- **删历史 release 资产、改资产名、改发布流程**：不动。
