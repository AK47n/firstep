# 提炼进度可视化

## Problem Statement

母版提炼（导入旧工程 → AI 判定 → 确认入库）的耗时大头在 AI 两阶段判定：先逐文件读全文出摘要、再基于摘要判定，各阶段按批发送（25 文件 / 批），单批模型生成 2-5 分钟，整轮提炼实测 10-15 分钟。期间前端只有按钮上的静态"AI 判定中…"转圈，没有任何进展信号——用户无法判断是正常等待还是卡死，只能干等或关页面重来（浪费一整轮 API 调用）。

## Solution

提炼期间实时显示进度：阶段 stepper + 批次进度 + 文件计数 + 双计时器（总用时 / 当前调用已等待，每秒跳动）+ 补问徽标 + 可折叠事件日志（批开始时列出该批文件清单）。进度事件经 SSE 流从后端推送；模型单次调用期间后端无法产生事件，由客户端每秒跳动的计时器证明进程存活——"逐文件进度"在调用内不存在，不做假进度。提炼完成 / 失败后进度区收敛为一行摘要，提炼报告照常渲染在下方。确认前不落任何东西的语义不变：刷新页面 = 安全放弃本次提炼。

## User Stories

1. 作为用户，我想在点击"AI 提炼报告"后立刻看到进度区出现，以便知道提炼已经开始而不是按钮失灵。
2. 作为用户，我想看到当前阶段（开始 → 摘要 → 判定 → 完成），以便理解提炼流程走到哪一步。
3. 作为用户，我想看到阶段内批次进度（如"第 2/5 批"），以便估计剩余工作量。
4. 作为用户，我想看到已处理文件数与总数（如 43/115），以便判断阶段推进速度。
5. 作为用户，我想看到每秒跳动的计时器（总用时 + 当前调用已等待），以便确认提炼没有卡死。
6. 作为用户，我想在批开始时看到该批在读哪些文件（清单可折叠），以便知道模型正在读什么。
7. 作为用户，我想在每批完成后看到批进度前进与"已读完"日志行，以便确认阶段在持续推进。
8. 作为用户，我想看到补问重试的发生（徽标 + 日志行），以便理解某批为何耗时更长。
9. 作为用户，我想在提炼失败时看到具体错误信息且日志保留，以便排查失败原因。
10. 作为用户，我想在提炼完成后看到用时总结（"提炼完成，用时 12 分 34 秒"），以便评估流程成本。
11. 作为用户，我想在提炼完成后报告照常渲染（与现状形态一致），以便照常审查判定清单。
12. 作为用户，我想在提炼期间切换页签而不中断提炼，以便等待时做别的事。
13. 作为用户，我想在刷新页面后知道本次提炼未落任何东西、可安全重新开始，以便放心重试。
14. 作为用户，我想在小规模导入（单工程 / 少量文件）时进度显示依然正确（批次 1/1、瞬间完成），以便不出现怪异进度。
15. 作为用户，我想在日志过长时不撑爆页面（可折叠、完成态自动收起），以便页面保持整洁。
16. 作为用户，我想在提炼无待判文件时立即得到完成报告（不显示空批次进度），以便边界情况不困惑。

## Implementation Decisions

- **范围**：只做母版提炼的进度。进度机制做成可复用通道（发射器参数默认关闭），其他 LLM 调用（模块推荐 / 骨架 / 模块录入校验）暂不接入，以后接入是顺手的。
- **传输**：SSE（text/event-stream）。后端在阶段 / 批次 / 补问边界推事件；客户端用 fetch + ReadableStream 手动解析（EventSource 仅支持 GET，现状接口是 POST JSON；且不需要自动重连——断线 = 放弃本次）。流的最后一个事件携带完整提炼报告（与现状响应同构），前端报告渲染代码原样复用——提炼确认前不落任何东西，服务端无状态，报告必须随流返回，没有二次查询的可能。
- **事件契约**（唯一出处，可测试）：`start`（总量：待判文件数、阶段 1 批数——由分批算法先算定；阶段 2 批数 = ⌈待判文件数 / 批大小⌉，同样先算定）→ 每批 `batch_start`（阶段、批号、批总数、该批文件路径清单）→ `batch_done`（阶段、批号、已处理文件数）→ 补问轮 `retry`（阶段、批号、轮次、缺失数）→ 阶段完成 `phase_done` → `done`（完整报告）或 `error`（中文错误信息）→ 流结束。事件类型集合预留 token 级流式扩展位（本次不做）。
- **发射 seam**（新，唯一）：LLM 层提炼入口增加可选进度发射器参数（默认 None，不接不影响行为；测试假 LLM 与真 LLM 走同一参数）；发射点在批次循环层（批开始 / 批完成 / 补问轮），阶段边界由两阶段流程各自发射。其余复用现有 seam：假传输（逐步喂响应 → 驱动事件序列断言）、webapp 测试的 TestClient（SSE 端点端到端）、LLM 工厂注入（注入会发射脚本化事件的假 LLM）。
- **显示**：4 步 stepper（开始 → 摘要 → 判定 → 完成；扫描 / 拼装是瞬间步骤，划过即可）+ 批进度条（"摘要 第 2/5 批 · 已读 43/115"）+ 双计时器（总用时 + 当前调用已等待，每秒跳动）+ 补问徽标 + 可折叠事件日志（批开始列出该批文件清单，可展开）。
- **存活证明**：单次模型调用期间后端发不出任何事件，客户端计时器每秒跳动是"没卡死"的唯一证明——这是批粒度约束的诚实边界，UI 不做调用内的假进度。
- **完成 / 失败态**：完成 → 进度区折叠为一行"提炼完成，用时 12 分 34 秒"，报告渲染在下方；失败 → 日志保留 + 红色错误行 + 按钮恢复可重试。
- **不做**：取消按钮（刷新 = 安全放弃，确认前不落任何东西）；断线重连与进度恢复（进度不持久化）。

## Testing Decisions

- 只测外部行为，不测实现细节：给定假传输的响应序列，断言发射器收到的完整事件序列（批边界、补问轮、错误路径、阶段完成）。
- 测试模块：LLM 层（事件序列契约：正常路径 / 补问路径 / 失败路径）、webapp 路由层（SSE 端点：注入脚本化假 LLM → 断言流式响应的事件顺序与 done 载荷 = 报告；error 事件 → 流以错误结束；无待判文件 → 直接 done）。
- 先例：现有假传输 / 假 LLM（tests/fakes）、TestClient 端点测试（test_webapp）、双端契约测试风格（test_llm）。
- 前端无单测基建（仓库先例：UI 手动验收）——进度 UI 以真机提炼实测验收：计时器跳动、批跳变、死寂期观感、日志折叠手感。

## Out of Scope

- token 级流式（DeepSeek stream 透传——事件 schema 预留扩展位，本次不做）
- 其他 LLM 调用（模块推荐 / 骨架 / 模块录入校验）的进度接入
- 取消按钮
- 断线重连与进度恢复（进度不持久化）
- 前端单测基建

## Further Notes

- 术语"进度事件"已进 CONTEXT.md 词表；本 spec 的传输与粒度决策记录在 ADR 0004（批边界事件 + 客户端计时器 / SSE 选型）。
- 批数为 0（全部文件都是规则处理的残留 / 二进制等）时：不发射任何批事件，阶段直接完成 → done，UI 显示即时完成。
- 报告载荷与现状提炼接口响应同构：前端现有报告渲染、确认、预览逻辑全部原样复用，只换传输形态。
