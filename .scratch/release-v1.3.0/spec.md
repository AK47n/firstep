## 问题陈述

线上最新仍是 **v1.2.2（2026-09-19）**，而 main 上积累了七批用户可见的改动，任何发布包里
都没有——其中第一批就是**整块新栏目「硬件检测」**：

- v1.2.2 的用户**看不到「硬件检测」这一栏**（`module-hwcheck/01-09` + 检测页引脚出口）；
- **库外陌生器件**（「我的器件」）的登记、探测小节、串口复测、工程内快照（`hwcheck-unknown-device/01-12`）
  也全在 main 上；
- **地猛星（MSPM0）生成的工程此前烧进去外设不初始化**（`SYSCFG_DL_init()` 那一行是注释占位，
  `hwcheck-acceptance/01`）——用户看到的是「灯不闪、串口一个字没有」，最像板子坏了；
- **「OLED 屏 + 任意 I2C 器件」等 10 组组合此前必 400**（母版 14 组同名引脚符号，
  `hwcheck-acceptance/02`）；
- **首批 20 件器件的专精检测**（身份探头 + 读数 + 复测字符，`hwcheck-specialize/01-08`）；
- 两处小修：bfcache 后退回来补登记与「应用服务已停止」可见态（`bfcache-return-register/01`）、
  生成工程 README 的 mspm0「打开姿势」（`a0602718`）；
- 本次会话新修的三处**库内驱动缺陷**（`driver-defect-fixes/01-03`）：摇杆读数很可能恒 0、
  舵机 50Hz 出不来、称重模块上电第一次读必超时。

## 方案

**发 v1.3.0（次版本 +1：整块新栏目 = 新增功能），一次把上面这些带上。**

用户可观察的结果：打开工具点「检查更新 → 一键更新」，拿到硬件检测栏目与那三处驱动修复；
新用户走完整包（约 755 MB）拿到同一份内容。

## 用户故事

1. 作为学生，我想在写题之前先验一遍手上的硬件，以便不把「模块坏了」带进调试。
2. 作为已经装了 v1.2.2 的用户，我想点一次「一键更新」就拿到这一栏，以便不重下 755 MB。
3. 作为新用户，我想在 Releases 里一眼看到该下哪个包，以便不在一堆资产之间犹豫。
4. 作为维护者，我想这一版的发布产物可核对（sha256 实算 = 记录、`00-START-HERE.txt` 在场、
   删除清单非空），以便发完就知道发对了。
5. 作为维护者，我想发完当场把账本（`local-environment` 第 0 节、`VERSIONS.md`、CHANGELOG）改对，
   以便下一轮接手不必重新推一遍。

## 实现决策

- **版本号**：`v1.3.0`（`docs/agents/releasing.md` 的 SemVer 表：新增功能 → 次版本 +1）。
- **两件套都发**：小发版四件套 + 完整包四件套，同一个 Release（完整包是新用户唯一的安装入口，
  README 只指它一个文件，必须在场）。
- **不带新代码**：本版只做「版本号同步 + 打包 + 发布 + 账本」，三张单见本目录 `issues/`。
- **工作树必须干净**：两个打包器都拒绝脏工作树，而「工单标 claimed / resolved」本身就是 tracked
  变更（2026-09-19 踩过）——所以**先打包打 tag，再落账本与工单标记**（账本提交跟在 tag 之后，
  与 v1.2.2 那一轮同款）。
- **不重跑真机 drill**：`drill-01`（起点 v1.1.1 → 走产品端点升到本版）是 v1.2.2 那一轮的验收；
  本轮沙箱（`firstep-sim`）停在 v1.2.2，**重演一次要先把真身挪端口**（v1.1.1 的
  `spawn_updater` 没有 `--port`，会杀掉 8000 上的真身，见 `local-environment` 第 0 节第 1 条）。
  本轮不做，如实记在账本里：**升级路径的判据止于 v1.2.2 那一轮**，本版只保证发布产物自洽。
