# spec — backlog 机器侧小账清扫（不等人、不等板子）

> 上游：`.scratch/backlog.md` **§27**「仍未做／有意留着」清单 ＋ `docs/agents/local-environment.md` **§0**
> （v1.4.0 交接区）＋ 两条旧账的原文（`ui-density-sitewide/issues/08-closeout.md` 账第 9 条、
> 同目录 `README.md` 的巡检图索引段）。

## 问题陈述

v1.4.0 发完之后盘了一遍仍开着的事，其中**有一类不需要人、也不需要板子**——机器自己就能做完、
而且判据现成：

1. **一条已知会红的用例**：`tests/test_hwcheck_triage.py::test_concurrent_record_writes_share_no_tmp_file`
   在机器忙时以 `PermissionError(13)` 红。根因是**同一目标上两次真实 `os.replace` 重叠**（Windows 平台行为），
   不是被测实现的缺陷。账里已经写好了处方：「要根治得给那条用例的两次真实替换**排序**
   （本批 02–05 的新并发用例就是那么写的：第二个先落盘、再放行第一个）——属另开单」。
   代价是每次撞上都要单跑复证一遍，且**假红会污染整轮读数**。
2. **更新器解压留下的残渣**：`tools/update-app.py::extract_zip` 写的是**固定临时名**
   `<目标>.update-tmp`，且**没有 `finally`**——解压中途异常/被杀就在工具根里留下 `*.update-tmp`。
   这个脚本不 import `contest_generator`（它跑在应用被替换之前），所以不能直接复用 `atomic_io`，
   得在脚本内部照同一套纪律写。
3. **两条已经过期、但还挂在账上的措辞**：① `ui-density-sitewide/issues/08-closeout.md` 账第 9 条写
   「`probe-01` 仍是 01 单立的草稿探针（自带一份 `rules_of` / `scope_of` / `load_backlog`）」
   ——09 单已经把它换成 `from scope_lib import …`（单一出处），这条账没人回改；
   ② 同目录 `README.md` 的巡检图索引段写「生成页 `#rec-progress` 这一趟没拍……留给下一轮」
   ——10 单已经拍了 `10-{light-light,dark-dark}-rec-progress.png`。
   两处都会让下一个人白推一遍（§23/§24 记过同一个坑：**修完没人回改标记**）。

## 方案

一轮扫完三件，各自一张单（`01` / `02` / `03`）。**都不改产品行为**：一件只改测试编排、
一件改的是**更新器脚本**（跑在应用进程之外的独立脚本）、一件只改文档措辞。

## 用户故事

1. 作为维护者，我不想在机器忙的时候看到一条与本轮改动无关的假红，更不想每次都为它单跑复证。
2. 作为维护者，我不想更新器中断之后在工具根里留下一堆 `*.update-tmp`（它们会被"产品文件与全新安装
   是否一致"那类判据读成"多出来的文件"）。
3. 作为下一个接手的人，我不想照着过期的账去重做一件已经做完的事。

## 实现决策

- **01 排序而不是放宽**：给两次真实替换**定序**（第二个整条走完 → 再放行第一个），
  **不动任何断言**、也不加 `pytest.mark.flaky` 之类的兜底——它仍然必须能抓到"临时名互抢"那个真缺陷
  （固定名实现下，第一个的源临时文件被第二个吃掉 → 第一个的 `replace` 失败，照样红）。
- **02 照 `atomic_io` 的纪律、但不 import 它**：唯一临时名（`pid` + 进程内计数）+ `finally` 清残渣 +
  **清理失败不许掩盖原异常**；`update-app.py` 的"独立脚本"边界（不 import `contest_generator`）保持。
- **03 只回改措辞、不动判据**：把两处过期描述改成事实口径，并各留一句"为什么会过期"（供下一个人
  照 §23 的模式复核）。

## 测试决策

- **01**：改的是**编排**，判据仍是原用例那三条（无异常 / 零残留 / 读回的是其中一个写者的内容）。
  另做一次**反向验证**：把被测实现临时换回"固定临时名"（在内存里 monkeypatch 一个旧形态的写函数）
  → 该用例必须变红，证明排序之后**判据强度没被削弱**；复原后逐字节相同。
- **02**：新增两条判据（`tests/test_update_app.py`）：① 解压中途抛错 → 目标目录里**零 `*.update-tmp`**；
  ② 正常解压 → 内容正确且零残渣。另加一条**同名目标并发/重入**的判据（两个 `extract_zip` 用不同 pid
  的替身 → 两套临时名不互抢）。反证：把实现换回固定名 → ① 必须红。
- **03**：无新判据（纯文档）。复核方式 = 读盘：`grep` 确认 `probe-01-scope-draft.py` 已 `import scope_lib`、
  `shots/` 里那两张图在盘且在 `.gitignore` 白名单里（`git check-ignore -v` 零输出）。
- 三道门禁按落点走：本轮**不动** `static/`，所以浏览器门禁不必在本轮单独跑；推之前 pre-push 会按落点选。

## 范围外（同类里"机器能自己干"但本轮**不做**的，逐条写明去向）

| 项 | 为什么不在本轮 |
|---|---|
| **描边那条线的机器守卫** | 要先解决"哪些框算例外"的**判据问题**（现状是逐条申报 + 清单）——设计活，一轮一件 |
| **`--accent` 小字浅色 3.39:1 / "去框留淡底" ×1.06** | 调色板级决定（动 `--panel-2` 是全局），要过颜色守卫 + 全站人眼复核 |
| **库层 MQ 预热口径**（mq3/4/6/7/8/9 的 manifest mspm0 notes 仍写「预热 3-5 分钟」） | 改的是**库内容**，按纪律要跟一次两平台真编译矩阵——单开一轮 |
| **三库更新路径的读-改-写持锁** | `backlog-closeout/05` 已判定**不开单**（失败面是"后写的赢 / 一次报错"，不是条目变坏） |
| **`launcher-reload` 在本机负载下偶发红** | 根因修过一轮（`launcher-exit-race/01–05`），残留部分要专门一轮做压测定位 |
| **`record-write-hardening` 的另两条相邻洞**（跨进程并发 / 强杀残渣清扫） | 账里明确"维持不动"的边界 |

## 补充说明

- **为什么这轮值得做**：三件都是"每次撞上就白花一轮"的税——假红、残渣、过期账。
  单件都小，合起来是"下一轮开工前把地面扫干净"。
- **§23 的模式照做**：这轮改完的旧账，将来复核时**直接读盘**，不信本文件的旧标记。
