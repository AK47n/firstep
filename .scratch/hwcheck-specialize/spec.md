# 硬件检测专精面扩张（首批 20 件：身份探头 + 读数 + 复测）——功能规格

> 2026-09-25 立项。起因 = 复测报告 `.scratch/hwcheck-acceptance/报告-复测.md` 的差距 5：
> **专精面窄**（10 件 / 17 格专精 vs 库内 96 件 → 90% 的件落在「未专精：只验总线和初始化」）。
> 用户当场拍板四件事：射程 = 首批 20 件（I2C 传感器一族 + 控制题高频件）；
> 深度 = 身份探头 + 读数 + 复测命令；验收 = 两平台真编译矩阵 + 守卫 + 反证，上板照旧如实写「未上板」；
> 节奏 = 每批做完停下汇报。本 spec 只收这四条的落地，不重开已 resolved 的两块
> （`module-hwcheck` 01–09、`hwcheck-unknown-device` 01–12）。

## 问题陈述

学生对着一件器件问「它能不能正常用」，而库里 **86 / 96 件**（159 个「模块 × 平台」格）
没有配方，只能走通用降级——那一档只做两件事：调一次初始化、扫一遍 I2C 地址。
学生因此拿不到三样东西：

- **板端判定**：没有通信探头，就不存在 OK / FAIL，只有「初始化没报错」；
- **读数**：不猜读函数（这是对的），但也就不回显任何量，学生看不出器件是否真在出数；
- **复测**：没有命令字符，线动过之后只能重新烧录，而不是敲一个字符再看一眼。

复测报告把这一条列为「如实但很浅」，并指出它的实际影响：**学生手上这一件落到"未专精"的概率是 90%**——
而原始目标① 的字面要求恰恰是「看看拿到的硬件能不能正常用」。

## 方案

把首批 20 件从「未专精」升到「专精」，每件每个平台一条配方，四件事一起给：

1. **身份探头**（能判就判）：读器件自己的身份 / 状态寄存器比对常量，**板上打 OK / FAIL**——
   不信驱动的初始化返回值（库里多份驱动压根不做通信校验）；
2. **读数**：整数表达式 + 单位 + 正常范围参考（浮点量拆整数 / 小数两行，沿用 ml_mpu6050 先例）；
3. **复测命令**：一个字符，不重烧就能边动线边看；
4. **如实降级**：器件天生没有可判身份（如 BH1750 没有 ID 寄存器、servo / relay 是纯写执行件），
   就明说「没有读取型探头」或「只有读数」，**不编一个假探头**（沿用 sr04 / key 的先例）。

### 首批名单（20 件）

| 批次 | 件 |
|---|---|
| 环境传感 A | `aht10`、`sht20`、`sht30` |
| 环境传感 B | `bh1750`、`bmp180`、`ms5611` |
| 姿态与光色 | `hmc5883l`、`qmc5883l`、`tcs34725` |

| ADC / PWM / 单总线 | `ads1115`、`pca9685`、`dht11` |

## 用户故事

1. 作为学生，我想要**手上这 20 件中的任何一件都有板端 OK / FAIL**（器件真给身份寄存器的那些），
   以便我不用从一个返回值猜通信通没通。
2. 作为学生，我想要**每件都有带单位的读数**（温度 / 湿度 / 光照 / 气压 / 姿态 / 距离 / 重量 / 摇杆百分比），
   以便我看见「有数在动」而不是只看见「初始化没报错」。
3. 作为学生，我想要**读数旁边写着正常范围参考**（放平 ≈ 1g、松手 ≈ 中位、室温 ≈ 25℃），
   以便我自己判断这数是合理还是离谱。
4. 作为学生，我想要**每件一个复测字符**，以便我边动线边复测，不用重烧。
5. 作为学生，当一件**天生没有身份寄存器**时，我想要页面**如实说"没有读取型探头"**，
   以便我不把"没有判定"读成"这件没测"。
6. 作为学生，当一件是**纯写执行件**（servo / relay）时，我想要页面说清**上电瞬间会看到什么现象**
   （比如继电器上电会不会吸合一下），以便我不被吓到、也知道该看什么。
7. 作为学生，我想要**同一件在两个平台上的差异被写明**（接口不同、精度不同、有的平台根本没这一格），
   以便我换板子时不用重新猜。
8. 作为学生，我想要**一次勾多件时命令字符不冲突**（这是本 spec 前置要解决的：现在两件抢同一个字符
   会让生成前 400），以便我按常见组合选件。
9. 作为维护者，我想要**配方引用的每个函数 / 宏都在该模块接口里**（构建期红），
   以便配方不会慢慢腐烂成"看着测了其实没测"。
10. 作为维护者，我想要**覆盖清单有地板断言、基线数按批次如实下调并写原因**，
    以便"配方变多"与"判据失灵"两件事不会混着读。
11. 作为维护者，我想要**未专精样本件的测试夹具不再绑死在某一两件上**，
    以便每批专精化不再连带改一堆无关用例。
12. 作为维护者，我想要**每一批都有两平台真编译矩阵（0 error / 0 warning）**，
    以便"能生成"与"能编译"不脱钩。
13. 作为维护者，我想要**每条新守卫都配一次反证**（撤掉一条配方 / 制造一次撞字符，用例必须红），
    以便守卫不是摆设。
14. 作为维护者，我想要**上板状态依旧如实写"未上板"**，以便不拿编译绿当板上证据。

## 实现决策

**射程与边界**

- 只做首批 20 件（40 格上下；单平台件按库内实况只列它有的那一格）。
- 深度统一为「身份探头 + 读数 + 复测命令」，**不追求**现有 pilot 那种长 note（sr04 一格 6 条说明）——
  note 写这一件真正会咬人的几条（平台差异 / 失败模式 / 正常范围 / 接线坑），不写套话。
- 已 resolved 的两块**只允许被动适配**（配方文件多几格、地板清单加几行），不许借这批重构它们的机制。
- **不修库内驱动缺陷**：侦察中发现的（不做身份校验、漏依赖、接口在两平台不一致）只记录，
  检测没过时另开修复单——这是 `module-hwcheck` spec 定下的口径。

**前置一：配方命令字符让位（生产代码）**

- 实测依据（`.scratch/hwcheck-specialize/probe-console-space.txt`）：可用字符池 **31 个**
  （字母数字里扣掉保留字 `?bgory`），现状已占 **10 个**，扩到 30 件专精件只剩 1 个；
  而"首字母记法"（sht / sgp / servo / sr04 都想用 `s`）必然撞车。
- 撞车的后果是**构建期硬失败**（400）：`build_console_table` 的判据之二就是"两件不得占用同一字符"，
  实测反证已确认它真的红。
- 改法照**自建件已有的先例**（`_assign_custom_command` 从池子里分配）：
  配方 `console` 段在**首选字符之外允许声明候选**，命令表按「配方顺序 + 首选优先 + 候选次之」分配
  第一个没被占用的字符；分不出来仍当场红（那时要说的仍是"去掉几件 / 换字符"）。
- 口径不变的三条：保留字（`r/y/g/o/b/?`）一个不碰；分配**确定性**（同一选中集恒定同一结果）；
  **页面与板端读同一张表**（单源不破，页面本来就渲染表里的实际字符）。

**前置二：未专精样本夹具解耦（测试代码）**

- 现状：`tests/test_hwcheck_generic.py` 等把 `sht20` / `pca9685` / `servo` 当"未专精样本"
  用了十几处——它们一旦被专精化，这些用例会变成**假红**（既有用例自己写过这条教训）。
- 改法：夹具改成"**从真实库里现挑一个未专精格**"（按平台 + 总线类型选），
  或登记一组**明确留作样本的件**（清单写在一处并注明"这批不专精它"）。
  两条都行，工单内选面窄的那条；判据 = 本批专精化后**不需要改任何一条既有用例**。

**配方内容口径（每格）**

> 写法上的**六条硬约束**（四份侦察实测得出，逐条都能让"校验通过但编译/判定出错"）：
> ① **mspm0 没有母版头** → mspm0 侧的 `init/probe/read` 只认本模块头里的名字，
> `delay_ms` / `gpio_get` / `DL_*` 一律构建期红；跨模块调用只能进 `prereq`（唯一天然放行的段）。
> ② **`r = call;` 前缀**：一旦写了 `init_expect` / `probe.expect`，**该段每一条调用**都会被加前缀
> → 那一段里**不许出现 void 调用**（校验器不查返回类型，漏在这条上）。
> ③ **`expect` 只能写返回码**（`"0"` / `"1"`），不能写身份常量——写 `HMC5883L_ID_A_VALUE` 会渲成
> 永远 FAIL 的比较式。
> ④ **`read` 表达式不能碰结构体成员**（`rgb.c` 会被拆成裸名 `c` 而报错）→ 结构体出参先拷进标量
> `locals`；结构体 locals 不能带初值。
> ⑤ **`read` 表达式禁用十六进制字面量**（`0x00` 切出 `x00`）；`probe` / `expect` 不受限。
> ⑥ 判定计数：一件要"只记一笔"就只能在 `init_expect` 与 `probe.expect` 之间二选一；
> 两个都写 = 两笔（ml_mpu6050 的"两级自证"先例，可接受但要知情）。

- `include`：这一节真正需要的头（跨模块前置要的头也算，如软 I2C）。
- `prereq`：总线 / 外设的前置初始化；没有就留空。
- `init` + `init_expect`：`init_expect` **只在驱动的返回值真能当判据时才写**（读驱动实现判断：
  它到底有没有做通信校验），不许把"驱动说 0"当成"器件通了"。
- `probe`：能自证的读法（身份 / 状态寄存器比对常量，或 EEPROM 的"写回读"这类**强自证**）；
  没有就**不写**，并在 `note` 里说清"本件没有读取型探头"及理由。
- `read`：整数表达式；浮点量拆「整数部分 + 小数第一位」两行并登记 `locals`；
  单位里带**量纲与正常范围参考**（沿用 ml_mpu6050 / sr04 的写法）。
- `console`：一个字符 + 一句说明；字符给"首选 + 候选"（见前置一）。
  分配顺序 = `resolve_sections` 的**验证顺序**（`sort_verification_order`），不是配方文件的书写顺序。
- `note`：平台差异、失败模式（读数恒 0 / 恒定值 / 超时各意味着什么）、正常范围、接线与上拉 / 地址注意点。

**覆盖记录与地板**

- 测试里的 `PILOT` 清单（10 件 / 17 格）**不许动**：它有 `len(PILOT) == 17` 的**精确条数**断言，
  钉的是「v1 pilot 清单」这段历史（`test_pilot_floor_covers_every_v1_slot`）。
- 扩张部分另立**一条地板**（新常量 + 新用例）：逐格列出本轮专精化的格，条数**精确**（每批长一次），
  判据同样是"少一格当场红"。它管的是"扩张成果不许悄悄缩水"，与 `PILOT` 的"v1 清单不许改小"分工不重叠。
- 既有那条按**配方文件实数**判的下限断言（`test_recipe_file_itself_keeps_the_floor_cell_count`，
  `>= 17` 格 / `>= 10` 件）加格子不会红，**不改**。
- 另有一条**随批次下降**的基线：`test_hwcheck_generic.py` 的"未专精格 ≥ 157 / 能拿初始化 ≥ 132"
  （实测现值是 **159 / 134**）。每批按实数**如实下调并写明原因**——该用例的注释本就要求这么做
  （它挡的是"初始化判据失灵"，不是"配方变多"）。
- 不建议把候选/分配规则偷偷写进配方数据当"默认字符表"——分配逻辑只活在命令表一处。

## 测试决策

- **最高既有缝 = 域层纯函数**（配方加载 / 校验 / 渲染 / 命令表，字符串进字符串出、零 LLM）：
  本 spec 的绝大多数行为都在这一层直测（沿用 `tests/test_hwcheck_recipe.py` / `test_hwcheck_console.py` 先例）。
- **配方守卫**：引用必须落在该模块该平台的接口清单里（既有 `validate_recipes`，不另造一套）。
- **地板与基线**：`PILOT` 逐格钉住；未专精基线随批次下调（如实改数并写原因）。
- **命令字符分配**：纯函数直测（首选可用→用首选；首选被占→用候选；全被占→中文大声失败；
  保留字永不被抢；同一选中集结果确定）+ 页面读到的是**分配后**的字符。
- **真编译矩阵**：每批的每一格 × 两平台（mspm0 走 gmake、stm32 走 UV4），判据 0 error / 0 warning
  （**链接器形态的告警另记**——复测已发现 `.sysmem` 那条面板解析不出来，见"补充说明"）。
- **反证要求**（本仓库既有纪律）：① 撤掉一条新配方 → 地板断言必须红；
  ② 把两件配方的字符改成同一个 → 命令表必须红（或按新规则让位，此时要证明页面显示的是让位后的字符）。
- **上板（真机）不做自动化、本批也不做**：落地形式照旧是"没跑过就写未上板"。

## 范围外

- 库内其余 **66 件 / 119 格**（本轮只做首批 20 件）。
- 真机上板（工单 `hwcheck-acceptance/05` 仍是它的家）与发版动作（v1.3.0）。
- 修库内驱动缺陷本身（侦察发现的只记录、另开单）。
- 检测工程与赛题工程的合并、引脚配置入口搬进检测页。
- 页面级"本批配方未上板"的显式标注（它属于复测报告差距 4/12 的一部分，随上板工单一起解决）。

## 补充说明

- **证据**（`.scratch/hwcheck-specialize/`）：`probe-recon.py` / `probe-recon.txt`（20 件的可调用面：
  90 件有 init、78 件有 read 路径；首批里 11 件有身份/地址常量、9 件没有；7 件是浮点读数）、
  `probe-console-space.py` / `probe-console-space.txt`（字符池容量 31 / 已占 10 / 撞车判据实测会红）。
- **命名纪律**：本仓库「自检」二字已被「自检冒烟」占用，本功能一律叫「硬件检测」；
  「专精 / 未专精」两个词沿用既有页面文案，不新造词。
- **一条与验收线有关的口径漏洞**（复测发现，不在本 spec 修）：`parse_compile_errors` 认不出
  链接器形态告警（`warning #10210-D:`），所以"0 warning"这条判据在链接器诊断上是漏的——
  本批的编译矩阵会**另行统计原始日志里的 `warning #` 行**，如实在读数里写出来。
- **本批完成后专精覆盖**：30 件 / 57 格上下（现 10 件 / 17 格 + 首批 20 件 / 40 格），
  未专精占比从 90% 降到约 69%（按格算 119/176）。
