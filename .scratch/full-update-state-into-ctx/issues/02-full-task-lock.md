# 02 — 并发 apply 只放一个任务进闸（_full_task_lock）

**要做什么：** 给完整包链路补上 C6 给资料库那半补过的同一把锁。apply 的「查在跑 → 建任务 →
占槽」是 check-then-act（同步端点跑在线程池 worker 上，中间还夹着要读磁盘快照的任务构造），
两个并发 apply 能同时过关：第二个静默顶掉第一个的槽位（那个任务还在跑却查不到 / 取消不了），
两个线程还往同一个 `updates/full/` 与同一份快照里写。前端没有防重（两个标签页即可触发）。

**被谁阻塞：** 01（同一段代码，实操按顺序做，避免同文件并发编辑）

**状态：** resolved

## 验收标准

- [x] `AppContext` 新增 `_full_task_lock`（私有，形状照 `_materials_task_lock`：缝外的状态公开、
      缝内的互斥件私有）
- [x] apply 的「查在跑 → 建任务 → 占槽 → **起线程**」整段进锁，**语句次序逐字留在原位**
      （磁盘校验 → 查在跑 → dry_run 早返 → 建任务 → 占槽 → 起线程）；**兜底自查那份网络调用
      （`_refresh_check`）留在锁外**（不许持锁打网络）
      —— 起线程也进锁是**比资料库那半宽的一条**（那半的 `worker.start()` 在锁外）：占槽后、
      `run()` 置 downloading 前任务仍是 IDLE，那一跳会被第二个请求读到；`Thread.start()` 本身
      等到新线程真的跑起来才返回，缝于是从「整段构造（读快照）」缩到「线程调度一跳」。
      **spec 的「实现决策」已按修订追认**（2026-09-22，双轴评审提出后经用户拍板），并如实写明
      **这是收紧不是硬保证**、以及资料库那半留着同一条缝（本轮不动）
- [x] cancel 的「查在跑 → 取消 → 强制快照」整段进锁（与 apply 的占槽互斥）
- [x] **真并发判据（修前红 / 修后绿）**：同一个 app 的一个 client ＋ 两个线程，用事件把第一个
      请求卡在临界区内、等第二个请求真的走起来（过了磁盘校验那一跳）再放行——修前第二个请求
      同时过关（200、两个任务被建出来），修后它等锁并吃到 400「已有完整包下载任务在进行中」，
      且槽位仍是第一个请求那个任务
