## 问题陈述

蜂鸣器模块（`beep`）在 stm32 线的代码里直接驱动 `BUZZER_GPIO` / `BUZZER_PIN` 两个引脚宏，但它的清单文件既没声明这两个引脚、也没声明提供这两个宏的 `config` 依赖。

后果三连：

1. **引脚绑定界面看不到蜂鸣器脚**——用户没法给蜂鸣器换脚、也没法看到它占了哪个脚；
2. **默认布局白名单看不见它**——冲突检查把蜂鸣器当空气；
3. **生成期引脚门禁静默放行**——实测 `beep` 与 `jq8900` 同时吃 PA15，门禁一声不吭，生成的工程编译能过、上板两个器件抢一个脚。

全库扫下来这是唯一一处（`debug_uart` 也驱动 LED/BUZZER，但它声明了 `config` 依赖，链是通的），属于单点缺陷，但暴露的是**结构性缺口**：没有测试保证「模块源码用到的引脚宏必须被它自己或它的依赖声明」。

## 方案

1. 给 `beep` 的 stm32 条目补一条引脚声明：`gpio_out`，默认 PA15，宏名 `BUZZER_GPIO` / `BUZZER_PIN`——与代码实际用法和母版 `pin_config.h` 默认值一致。mspm0 条目不动（占位实现、不引用任何引脚宏、库内无蜂鸣器引脚可分配）。
2. 补一条结构测试，把「模块源码里用到的 `pin_config.h` 引脚宏，必须被该模块自身或其依赖闭包里的某个模块声明」钉成全库不变量。这条测试同时兜住未来的新模块：以后谁再写一个偷用宏的驱动，测试立刻红。

## 用户故事

1. 作为使用者，我想要蜂鸣器出现在引脚绑定界面里，以便能给它换脚、也能看到它占了哪个脚。
2. 作为使用者，我想要蜂鸣器和别的器件抢同一个脚时生成期门禁报错，以便上板前就知道冲突，而不是烧录完才发现。
3. 作为使用者，我想要默认引脚布局把蜂鸣器算进去，以便默认生成的工程不会出现两个器件共脚。
4. 作为维护者，我想要一条全库不变量测试，以便新模块偷用未声明的引脚宏时立刻被抓住。
5. 作为维护者，我想要这次修复与代码实际用法对齐（宏名、默认脚、类型都照实），以便声明不会变成又一处漂移。

## 实现决策

- **改动面**：`beep` 的 stm32 平台条目补 `pins`（一条，`type=gpio_out`，`default=PA15`，`macros=[BUZZER_GPIO, BUZZER_PIN]`，`required=true`）。mspm0 条目与两个平台的代码文件都不改。
- **结构测试位置**：`tests/test_library_invariants.py`（新文件，见第 3 批同一文件的收敛目标；本工单只落这一条不变量，不抢第 3 批的范围）。
- **不变量定义**：扫描模块源码（`library/modules/*/code/*.c`）中出现的引脚宏名 → 与「该模块自身声明 ∪ 其依赖闭包内各模块声明」的宏集合比对 → 有差集即失败并列出「模块 / 未声明宏 / 出处文件」。
- **宏名单的取源**：从母版 `pin_config.h` 里机械抽取引脚宏（不手写词表，避免词表漂移）；抽取规则与母版书写形态一致。
- **依赖闭包**：复用库内既有依赖展开能力，不新写一套遍历。
- **既有测试联动**：`test_stm32_macro_bidirectional_alignment`（373 个宏双向对齐）在补声明后必须仍全绿——若 beep 的宏已在母版里存在，对齐关系不变；测试红说明声明写错了，按实测修正而不是改测试。

## 测试决策

- **测试接缝**：库结构不变量测试（扫真实 `library/modules/` 语料），先例 `tests/test_library_invariants` 系同类结构测试与 `tests/test_lckfb_attribution`（扫真实库文件的机械校验）。
- **只测外部行为**：断言「源码用到的宏都能被声明溯源」，不断言声明条目的字段顺序、不断言具体模块清单——修好后新模块加入不会误伤。
- **反向验证**：测试必须在「beep 未补声明」时是红的（先红后绿），并且对 `debug_uart`（靠依赖 `config` 合法）保持绿——一条测试同时守住「漏声明」和「依赖合法」两侧。
- **回归**：`pytest` 全绿，含既有引脚相关测试（绑定界面、默认布局、门禁、宏对齐）。
