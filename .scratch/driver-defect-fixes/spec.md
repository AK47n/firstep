# 库内驱动缺陷修复（硬件检测侦察带出来的三件）——功能规格

> 2026-09-25 立项。起因 = `hwcheck-specialize` 的四份只读侦察在写配方时撞出来的**驱动缺陷**：
> 它们不在那个 spec 的射程内（该 spec 明写「不修库内驱动缺陷：侦察中发现的只记录，检测没过时
> 另开修复单」），但**不能丢**——三件都直接影响学生上板能不能用，且都属于"库内代码与手册/自身
> 常量不自洽"这一类。本 spec 只收这三张单的落地口径，不重开任何已 resolved 的块。

## 问题陈述

三处缺陷都不是"配方写得不对"，而是**驱动本身在规定条件下必然失败**——学生在检测页看到 FAIL，
会去查接线、换模块、重烧，而真正的病灶在库内代码里：

1. **`servo` × mspm0：PWM 周期超过 16 位定时器量程** ⇒ 50Hz 出不来、大角度输出恒高。
   现象是"舵机不动 / 只在某个角度区间能动"，看起来像舵机坏了或线接错了。
2. **`joystick` × mspm0：ADC 超时判据用"自旋次数"而不是时间** ⇒ X/Y 读数**很可能恒 0**，
   而 `0%` 恰好又是"杆推到端点"的合法读数——学生无法区分"坏了"和"推到端点"。
3. **`hx711`：20ms 超时窗口短于模块默认 10SPS 的 100ms 转换周期** ⇒ `init`（去皮）之后紧接着
   读**必然超时返 0**；而且 `0` 既可能是"没等到数据"也可能是"秤正好在零点"，歧义无法区分。

## 方案

每件一张修复单，各自独立可验证；共同的落地口径（本 spec 的射程边界）：

- **只改驱动**，不动配方数据、不动检测页 / 生成链、不改 manifest 字段形状；
- 判据落在**驱动级用例**（`tests/test_module_*.py` 既有缝）与**真编译矩阵**
  （`py -3 .scratch/hwcheck-specialize/probe-compile-matrix.py --slugs <件>` 全 `[PASS]`）；
- **两平台 API 对偶不许破**：库内 `tests/test_module_*.py` 已有 API 对偶守卫，改一侧必须
  同步另一侧（或如实说明为什么只有一侧需要改）；
- **反证**：每条新判据都要有一次"把修复撤掉 → 用例变红"的实测读数；
- 需要**上板或 SDK 复核**才能定案的点，如实写"未上板 / 未复核"，不许拿推断当结论
  （三件的证据链都来自只读侦察，其中两条侦察原文自己就标着"推断，需上板/SDK 复核"）。

## 用户故事

1. 作为学生，我想要 `servo` 在 mspm0 上**真的输出 50Hz**、写多少度就停在多少度，
   以便我不用把"库内量程溢出"误判成"舵机坏了"。
2. 作为学生，我想要 `joystick` 的 X/Y 读数**在杆在中位时是中位值**（不是恒 0），
   以便我能区分"线没接好"与"杆推到端点"。
3. 作为学生，我想要 `hx711` 在**接好传感器**时第一次读就能拿到数据（而不是必然超时），
   并且能区分"没等到数据"与"读数正好是零点"。
4. 作为维护者，我想要每件修复都有**一条能在 CI 里跑的判据**，以便下次改驱动时不靠人肉回忆。
5. 作为维护者，我想要**修复不牵连配方数据**（配方随修复变得更简单是另一单的事），
   以便"驱动对"与"配方怎么写"两件事分开推进。

## 实现决策

- **落点**：`library/modules/<slug>/code/*.c` 与必要的头文件；测试落 `tests/test_module_<slug>.py`。
- **判据面**：优先"用库内已声明的事实算出来的量"（频率、计数、转换周期），少写魔法数；
  测试断言要能独立复算（不许照抄实现里的表达式）。
- **`hx711` 的歧义**那条要想清楚再动：改返回语义会波及双平台 API 与配方
  （`hwcheck-specialize/08` 还没落地，改在这里最省事）——**先评估再改**，评估结论写进工单。
- **不新增依赖、不改母线**：三件都不需要新模块。

## 测试决策

- 驱动级用例（既有先例：`tests/test_module_servo.py` / `tests/test_module_joystick.py` /
  `tests/test_module_hx711.py` 若不存在则新建，照同款体例：读源码 + 断言行为常量）。
- 真编译矩阵：三件各自两平台全 `[PASS]`（编译器 0 error / 0 warning，链接器告警另记）。
- 反证：每条新判据一次"撤掉修复 → 红"的实测。

## 范围外

- 修 `hwcheck-specialize` 侦察报告里其余那些"只记录不修"的缺陷（如 `at24c02` 头/实现不符、
  `ads1115` 无法读回寄存器、`pca9685` 板上不可自证、`dht11` 位循环超时不报错、
  stm32 全库没有释放 JTAG 的代码、`tcs34725` × mspm0 假通过……）——它们**没有**在本 spec 的三张单里。
- 上板实测（本机没有板子：落地时照仓库惯例写"未上板"，或由用户按 `docs/agents/local-environment.md` 安排）。
- **配方段结构与格数不动**（`library/hwcheck_recipes.json` 的 `include` / `prereq` / `init` /
  `probe` / `read` / `console` 各段形状与格数一个不改；**但三张单各自点名了「回来改配方口径」
  的那几处文案要跟着改**——修好之后配方不该再说「本单不修的驱动缺陷」，读数行也要认新出现的
  「本次无效」哨兵值。2026-09-25 落地按这条执行：改动只落 `read` 的 `unit` 与 `note` 行，
  并由 `tests/test_hwcheck_recipe.py` 的读数行宽 / 扩张地板 / locals 三条既有守卫兜住）。
- 发版动作。
