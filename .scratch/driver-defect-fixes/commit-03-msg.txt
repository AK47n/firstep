工单 driver-defect-fixes/03：hx711 的就绪窗口按转换周期算，「0」的歧义有出口

问题两处（都是"编译过、板上必失败"那一类）：
- 等 DT 就绪的窗口写死 `2000 × delay_us(10)` = **20ms**（注释自称"近似手册转换周期"），
  而模块默认 **10SPS ⇒ 100ms** 才出一个新数据；`hx711_init()` 内部就先读一次（空秤去皮）
  消费掉一个采样 ⇒ **init 之后紧接着读必然超时**。
- 超时 `return 0`，而 `count ^ 0x800000` 在空秤零点（count == 0x800000）时**也返 0**
  ⇒ 「没等到数据」与「秤正好在零点」分不开。

改法：
- 窗口改成**按转换周期算**：`1000 / 10SPS = 100ms`，取 2 倍 = **200ms**；轮询圈数由
  「窗口 ÷ 步长」推出来（不再手写 2000）。init/tare 那种"消费一次采样"的读**由驱动自己
  承担节流**（等满一个周期），调用方不必再补 `delay_ms`。
- 「0 的歧义」取**候选①超时返回哨兵值**（工单要求先评估再改，评估表与理由写进工单结论）：
  合法读数是 24 位（0 ~ 0xFFFFFF），哨兵取 **0xFFFFFFFF**（落在合法域之外）；签名零改动
  ⇒ 配方 / 骨架 / 克换算都不用跟着改。②改签名会破 API 对偶与配方，③另加查询接口"要靠
  调用方自觉"（工单明确否掉）。
- **评审抓出并修掉的一处真缺陷**：`s_tare = hx711_read_raw();` 在超时时会把 0xFFFFFFFF
  存成零点 ⇒ `克 = raw - s_tare` 变成 `raw + 1` 的天文数字（比旧代码存 0 更坏）。
  改成 `hx711_tare()` 里过哨兵判断（没读到就**零点原样不动**），`hx711_init()` 走同一处；
  两平台同改。`hx711_get_gram()` 把「没读到」与「空秤」分开（超时 → -1.0f）。
- 配方：两格的探头判据从「非 0」改成「≠ 哨兵值」；stm32 格的 `delay_ms(500)` 拐杖与
  随之无用的 `ml_delay.h`、mspm0 格 `prereq` 的 `delay_ms(500)` 一并撤掉；两格 note 与
  `read` 的 unit 按修后口径重写，并**如实补回**「冷启动那一次仍可能超时」（上电第一个
  样本要 ~400ms，比窗口长）。顺手删掉 mspm0 格里从 stm32 抄错的接线坑（本平台是 PA28/PA31）。

判据与读数：
- 三条新判据（两平台各一眼）：窗口 ≥ 一个转换周期且**循环退出界与步长都绑住**；
  超时不许 `return 0`、哨兵必须 > 0xFFFFFF、克数接口分开两种失败；去皮不许把哨兵存成零点。
  另有一条跨文件对拍（六常量两平台逐项相等 + 公共 API 签名不动）。
- 文案与实现对齐：量具 `probe-03-printed-values.py` 打印真产物，证明哨兵**页面印成 -1**
  （`hwcheck_report_int(int)` 吃 `uint32_t raw`），两格文案按实际印出来的写。
- 反证五条注入全红且逐字节复原：`probe-guard-strength-03.txt`。
- 真编译矩阵两格全 [PASS]：`probe-compile-matrix-03.txt`。
