# 硬件检测（常用模块 bring-up 自检）——功能规格

> 2026-09-20 grilling 两轮定稿（用户逐轮「按你推荐」）。逐条决策见「实现决策」。

## 问题陈述

学生手上新到一件常用器件（典型场景：一块 MPU6050），想确认「它到底通不通、线接对了没、正常应该看到什么」，但现在没有任何入口：

- 主流程要求先有赛题、先选出整套模块集。它自带的「自检骨架」只给一段 main.c 文本（还要再点一次生成工程），**没有接线表、没有"应该看到什么"、没有"没看到先查哪里"，也没有板上自动判通断**——写没写对全靠学生盯着屏幕猜。
- 自检骨架由 LLM 出稿，静态兜底会把"接口里不存在的调用"改写成注释占位：**检测项可能被静默跳掉，学生看到的是一片"OK"其实什么都没测**。
- 库内 170 个「模块 × 平台」条目**全部未上板**（manifest 逐条自述"未上板"），学生对一件器件的期待与代码真实成熟度之间没有桥。
- 器件之间的平台不对称是暗雷：同一件 MPU6050 在 mspm0 上能出三维角度、在 stm32 上只能出原始六轴；地猛星的 MPU6050 默认 I2C0（PA0/PA1）**与板载 LED 同脚**。这些事实目前只写在 manifest 的 notes 里，用户看不到。

## 方案

新开一个顶级栏目「硬件检测」，**完全独立于赛题工作流**：

选平台 →（可选）选器件 → 看见接线表与默认脚冲突 → 一键生成一个可编译可烧录的检测工程 → 编译 / 烧录（复用既有能力）→ 对照「应看到什么 / 不对先查哪里」清单上板逐项确认 → 把实际现象填回来，AI 给排障方向。

检测程序**不靠 AI 生成**：框架（LED 心跳、输出通道分节、结尾汇总）由确定性渲染器产出；「每一件怎么测」来自库内配方数据；没有配方的模块走通用降级（初始化 + I2C 总线扫描），并如实标注「未专精」。

「检测没过」是正常结果——它要么指向接线问题（用户在清单里自查），要么指向库内驱动缺陷（另开修复工单）。

## 用户故事

1. 作为第一次用这个工具的学生，我想要**不需要赛题**就能开始检测，以便我一拿到器件就能用。
2. 作为学生，我想要选完平台和器件就看到「这几个脚分别接哪里」，以便我照着插线。
3. 作为学生，我想要**默认脚冲突被如实标出**，以便我知道哪两件不能同时用默认脚（例：地猛星 MPU6050 的 I2C0 = PA0/PA1 与板载 LED 同脚）。
4. 作为学生，我想要**一个器件都不选也能生成**「板子活着」的最小自检，以便我先确认板子和烧录链路是好的。
5. 作为学生，我想要板载 LED 有规律闪烁（心跳），以便我肉眼就知道程序在跑、板子没死。
6. 作为学生，我想要 OLED 或串口把每一件的检测结果**分段**打出来，以便我不拖串口线也能看结果。
7. 作为学生，我想要板上直接给出**通信 OK / FAIL 的判定**（而不是让我从一个返回值猜），以便我区分「器件坏了 / 线接错了」与「读法不对」。
8. 作为学生，我想要 MPU6050 在地猛星上直接显示 pitch / roll / yaw 三维角度，以便我用它之前就确认姿态解算真能出数。
9. 作为学生，我想要在 stm32 上被如实告知「本平台没有姿态解算，这里只能看原始六轴」，以便我不把"显示不了角度"误判成"我接错了"。
10. 作为学生，我想要检测程序**不假装测过**：没配方的器件明确标「未专精：只验总线和初始化」，以便我知道哪些结论可信、哪些只是走了个过场。
11. 作为学生，我想要上电自动跑一遍之后还能用**串口命令反复复测**（不用重烧），以便我边动线边看现象。
12. 作为学生，我想要一张「应看到什么 / 不对先查哪里」的清单并能逐项勾选，以便我不用凭感觉判断正常与否。
13. 作为学生，我想要把实际现象填回去让 AI 给排查方向，以便我自己搞不定时有下一步。
14. 作为学生，我想要检测工程与赛题工程**互不干扰**（不进最近工程列表、不会被当成赛题工程去深化/修订），以便我两件事同时做。
15. 作为维护者，我想要配方与模块库的一致性有守卫（引用了不存在的函数、或专精清单悄悄缩水，当场红），以便配方不会慢慢烂掉。
16. 作为维护者，我想要前端守卫真的会在推之前跑，以便新栏目的注册错误不会没人发现。

## 实现决策

**形态与入口**

- 新顶级栏目，放在「做题」组第 2 位（紧跟「生成」之后）；自带「平台 + 器件」选择，**不依赖生成流程的任何状态**。
- 与既有「自检骨架」（自检冒烟）的关系：目标不同（做题前验通路 vs 我手上这件通不通），**冒烟原样不动**；两条路共用同一个「检测程序」生成缝，不各长一套。

**检测程序怎么来**

- **确定性框架 + 声明式配方**：框架永远由渲染器产出（LED 心跳、输出通道分节、逐件小节、结尾汇总）；每件「怎么测」读配方；无配方走通用降级。渲染全程零 LLM。
- 配方数据落**库根的中央文件**（跟随模块库根、不新增配置键），键 = `slug → platform → 配方`。不往每个模块目录里塞空壳文件，避免把「目录即数据库」的审计面撑宽。
- 配方形状（决策密集，grilling 定稿）：

  ```
  prereq   前置调用（如 stm32 侧 MPU6050 需要先初始化软 I2C 总线）
  init     初始化调用 + 期望（判 OK/FAIL）
  probe    通信探头 + 期望（如读 WHO_AM_I 期望 0x68；判"通信通没通"）
  read     要展示的表达式 + 单位（如三维角度 / 距离 cm / 灰度值）
  console  串口控制台的命令字符
  note     平台差异说明（直接印到检测页；如"本平台无姿态解算"）
  ```

- 配方里的「调用什么」写成 **C 表达式字符串**（它最终就是 C 代码；结构化描述只会重新发明一遍 C 的参数语义）。
- 配方里出现的函数名**必须能在该模块的接口清单里找到**，找不到 = **构建期大声失败**（守卫测试），绝不学骨架兜底把它改成注释——那是"看着测了其实没测"。
- 通用降级 = **初始化 +（I2C 类模块）总线地址扫描**；**不猜读函数**（猜出来的垃圾值比不测更坏）。判据零新增知识：总线类型是 manifest 已声明的事实。这类模块在检测页标「未专精：只验总线和初始化」。

**板上行为与判据**

- 程序形态 = **上电自动跑一遍**（逐件自报 + LED 心跳常驻），之后进**串口命令交互**（复测不用重烧）。
- 既有 `r/y/g/o/b` 四条命令（点灯/灭灯/蜂鸣）**语义一个字节不动**（已上过板的既有行为）；新命令追加，字符冲突在构建期报错。无 `debug_uart` 的构建降级为"只跑自动那遍"，检测页明说"没有串口 = 不能交互式复测"。
- 判据三层，UI 上分开标注：① 编译绿（工具已验证）② 板端通信判定 OK/FAIL（**自证探头**，不信驱动的 init 返回值——驱动可能压根没做通信校验）③ 数据合理性**只回显 + 给正常范围参考**（静止时 |a|≈1g、角速度≈0），不在板上做阈值判决。
- 检测顺序复用生成 README 里已有的 bring-up 顺序判据（先"板子活着"类：延时 / 串口 / LED / 声光，再按依赖序测器件），不另立一套；顺序在检测页显式展示。

**平台不对称如实呈现**

- mspm0：MPU6050 走官方 DMP，出 pitch / roll / yaw；但该平台**没有浮点显示接口**，角度要拆整数/小数显示。
- stm32：MPU6050 只有原始六轴 + 明写「本平台无姿态解算，要角度请用串口姿态模块或改 mspm0」；DMP 移植不在本期。
- 地猛星的 LED 驱动会把越界通道静默钳回通道 0，配方只能走通道 0 / 通道表，不能照搬 stm32 的红黄绿宏。

**生成链与落盘边界**

- 新端点复用既有生成内核（**不新开第二条写盘路径**），只在生成前注入检测 main.c。
- 输出策略：检测页自带「输出父目录」，每次生成**新子目录**（`hwcheck-<平台>-<时间戳>`，天然不覆盖）。
- **不动最近工程记录**（那是"一道题做几天"的记录，检测工程会污染它）；检测页自己列最近几次。
- 上下文清单照写，但加一个 `kind` 字段（`contest` / `hwcheck`；读侧缺字段 = 赛题工程，向后兼容）——这样以后"修订 / 深化"这类赛题专属功能不会误抓检测工程。
- 生成的 README 照写（引脚接线表正好有用）；演示脚本不写（本来就没内容）。

**v1 专精范围（按「模块 × 平台」格算）**

led / oled / debug_uart / key / beep / sr04 / jy61p / xunji / adc / ml_mpu6050。清单外模块照样能生成（走通用降级），不报错、也不假装经过专精验证。

**命名与记录**

- 栏目名「硬件检测」；tab key `hwcheck`；域模块 `hwcheck.py`；异常 `HwCheckError`（→ 400）；进度事件 `EVENT_HWCHECK_*`；CONTEXT 词条「硬件检测」。
- 新写一条 ADR：**检测程序 = 确定性渲染 + 库内配方数据**（记清与「模块 = 纯驱动切片」那条 ADR 的关系：配方是"怎么用这个模块"的元数据，不是模块逻辑，不进模块源码）。本仓库第一次出现"渲染出的程序不靠 AI"的生成形态，值得留档。

**已知会立刻撞上的库内缺陷（本期不修，检测没过时另开单）**

- `ml_mpu6050` 的 stm32 条目漏声明 `delay` 依赖，代码里却调了延时。
- 同一件的 stm32 驱动**不初始化总线**（要调用方先初始化）且**不做 WHO_AM_I 校验**，通信失败也照样往下写寄存器——这正是检测程序必须自己带探头的原因。

## 测试决策

- **最高既有缝 = 域层纯函数**（字符串进 / 字符串出，内存直测，零 LLM）：配方加载与校验、检测 main.c 渲染、控制台命令表生成、通用降级判定。
- **端点**：两个——出 main.c 预览、SSE 出工程（生成沿用既有 SSE 机制与错误映射表）。测试用既有 TestClient 与假 LLM 桩。
- **守卫**：① 配方 ↔ 库一致性（键存在、平台条目存在、引用的函数在该模块接口清单内）；② 专精覆盖清单**地板断言**（照「wiki 来源覆盖面地板」先例，防止清单缩水而无人察觉）。
- **前端**：fx 纯函数单测（命令表 / 清单 / 接线表渲染）+ 导航 parity 守卫（既有两处守卫同步）；浏览器人工验收。
- **真机口径**：stm32 UV4 / mspm0 gmake 编译绿（同既有编译矩阵口径）+ 用户照清单上板跑一轮并把现象回填。**没跑过就写"未上板"，不假装。**
- 反证要求：每条新守卫都要有一次"停用后用例必须变红"的实测（本仓库既有纪律）。

## 范围外

- PC 上位机 / 串口实时波形 / 自动烧录。
- stm32 侧 DMP 姿态解算移植（另立条目）。
- 全库配方回填（本期只做 pilot 清单）。
- 检测结果云端同步 / 检测历史跨机迁移。
- 多器件并发采集（允许多选，但顺序执行）。
- 修库内驱动缺陷本身（另开单；本期只负责把它们暴露出来）。

## 补充说明

- **两处必须避免的重名**：本仓库「自检」二字已被「自检冒烟」占用，本功能一律叫「硬件检测」；「预算」已被请求体字节预算占用（本功能不引入同类命名）。
- **检测没过 = 正常结果**：检测页不得为此含糊其辞，要给出下一步（查线 → 回填现象 → 必要时开单）。
- grilling 核查过的关键事实（实施会话可直接引用，但不要把它们当成永久不变量）：库内 94 个有源码的模块里 90 个有 init、60 个有返回值读取路径，而**只有 2 个**（debug_uart / uart）有打印路径——所以"打印"必须由检测程序自己带，不能指望各模块；`debug_uart` 里已有一个既有的接线检测台（单字符命令点灯 / 蜂鸣），是控制台形态的先例；stm32 板载三色 LED 在 PC13/14/15，地猛星用户 LED 是 PA15。
