# spec — 更新完了，跑着的服务还是旧版本：别让启动器盲信端口上那个服务

> 缺陷单：`issues/01-stale-service-after-update.md`（发现于沙箱真机演练 B1，`sandbox-drill/01`）。
> 本 spec 是在那张单子的「待定修法（择一或组合，动代码前先 spec）」上做的**拍板**，
> 并把拍板前查出来的两条错误更正记在文末「补充说明」。

## 问题陈述

用户点了「检查更新 → 一键更新」，进度条走完、工具说更新成功，但**打开的还是旧版本**：
`/api/health` 与设置页都还是旧版本号，必须自己把工具关掉再重开一次才到新版。

链条（沙箱真机实测，非推断）：

1. 发起更新的那一代代码（v1.1.1）拉起更新器时**没传停服端口**，更新器按默认 8000 停服；
2. 旧进程没被停掉，还占着端口；
3. 更新器照常换完文件、清标记，然后调启动器重启；
4. 启动器探测端口，看到 `/api/health` 应答且 `app == contest-generator`，就判定
   「本应用已在运行」→ 只开一个浏览器标签就退出——**端口上那个旧进程永远不会被换掉**。

**射程（工单原文写宽了，这里更正）**：更新器默认端口是 8000，而普通用户双击启动时启动器
也把端口定成 8000（`start-app.bat` 第 21–23 行），**两边默认值相同 → 停服停对了**。
所以这条缺陷只在**端口不是 8000** 时才咬人：沙箱（8020）正是这种；另有
`docs/agents/local-environment.md` 第 2 节记的「同机双实例」形态——那一次更糟：更新器把
**8000 上用户正在用的那个**停掉，而自己留在旧版。工单里「≤v1.1.1 的那批人点一次就会中招」
是推断过头，`backlog.md` 的级别口径要跟着改。

另外核实：v1.1.1 的**完整包**路径是传 `--port` 的（备份里 `full_apply.py` 同时带
`resolve_launcher_port` 与 `--port`）——**只有小发版那一条路缺**。

## 方案

**一条判据，落在启动器里**：`start-app.bat` 在「端口上确实是我们自己的应用」这一判定之后，
**再比一次版本**——端口上服务的 `version` **小于**盘上 `contest_generator.__version__`
→ 判定为「旧进程」→ 按既有停服纪律（先确认身份、再 kill）踢掉它 → 走原本的「起服务」路径；
否则保持现在的行为（只开一个浏览器标签）。

为什么是启动器：**启动器是随包分发、更新时被替换的那个文件**。用户装到的包里带着修好的
启动器，重启那一步就会自己把僵着的旧进程踢掉——**发起更新的是哪一代代码都不影响**，
连 ≤v1.1.1 的老用户也被顺手带上（他们装到含本修复的包，第一次重启就自愈）。

用户可观察的结果：更新完成后重新打开，**跑着的服务就是新版本**，不需要用户自己关掉再重开。

## 用户故事

1. 作为点了「一键更新」的用户，我希望更新完成后打开的就是新版本，以便不必自己关掉再重开。
2. 作为端口不是默认值的用户（多实例 / 验收实例 / 沙箱），我希望更新后服务真的被换掉，
   以便不会有「界面说更新成功、实际还是旧版」这种没人能察觉的状态。
3. 作为同机跑两个实例的用户，我希望一个实例更新时不要把另一个实例算成「自己已在运行」，
   以便我不用重启另一个实例才能确认版本。
4. 作为手动改过代码 / 换过文件的人，我希望重新启动时拿到的就是盘上那份代码，
   以便「盘上改了、跑着的还是旧的」这种状态不会一直挂着。
5. 作为维护者，我希望这条修复**有静态守卫 + 有真机证据**，以便它不会在下次改启动器时被悄悄改掉。
6. 作为维护者，我希望这条修复**真的能到用户手上**（进线上 v1.2.1 的包），
   以便「修好了但没人拿到」不会重演。

## 实现决策

### 判据（单条，语义比较）

- 谓词：`服务版本 < 盘上版本` → 旧进程。**相等、或服务版本更新** → 不算旧进程（不误杀
  「另一个根跑着更新版本」的情形）。
- 版本语义**复用既有单源** `contest_generator.update.compare_versions`（容忍 `v` 前缀与空白；
  任一侧非合法 semver 返回 None）。**非合法 semver → 不下判断**（返回 unknown，保持原行为），
  宁可少踢一次，也不拿解析不了的东西去 kill 用户的服务。
- 谓词进产品包（`src/contest_generator/update.py`，与 `compare_versions` 同处——版本语义只有一个家），
  形如 `is_stale_service(served, on_disk) -> bool`。

### 启动器怎么问这个判据

- 新增一个**薄 CLI**（`tools/launcher-stale.py`）：`--port <端口>` → 取一次 `/api/health` →
  自己确认 `app == contest-generator` → 取 `version` → 与盘上版本比较 →
  **stdout 恰好一行**，三选一：
  - `stale stale=1 served=<旧> disk=<盘上>`（要踢）
  - `fresh served=<端口上> disk=<盘上>`（复用，保持原行为）
  - `unknown`（任何异常 / 身份不符 / 版本读不到 / 非法 semver）
  任何内部异常都打印 `unknown` 并退出码 0——判据只有 stdout 一行，调用方不吃退出码。
- `start-app.bat` 只**消费这一行**：`for /f "tokens=1,*"` 取首 token 作判据、其余作留痕字段；
  token 不是 `stale`（含空、含 `unknown`）→ 一律走原来的 `:already_running`。
  **判据不在 .bat 里手写**（字符串比较会把 `1.10.0` 判成小于 `1.9.0`）。

### 踢旧进程的纪律

- **只在身份已是本应用的那个分支里踢**（身份判据是既有行为，未改动）；
- 目标端口 = `%FIRSTEP_LAUNCHER_PORT%`（与既有端口探测同一个变量，不新开口径）；
- 杀掉后**等一拍**（`ping -n 2`，与既有轮询同款的可移植「睡一秒」，不用 `timeout /t`——
  它在 stdin 被重定向时会立刻失败）再起服务，避免新进程绑不上端口；
- 踢完走**原本的 `:start_service`**（起服务 + 20 秒轮询就绪 + 开浏览器），不另造一条起服务的路。

### 留痕：**不新增 reason 码**

- `tools/launcher-log.ps1` 只校验形态、不校验码表成员，但 `tests/test_launcher_log.py` 有三条判据
  把码表钉死了：每条 `exit /b` 前必须有一次留痕调用、**留痕调用数与退出分支数一一对应**、
  用到的码集合**恰好等于** `REASON_CODES`，而 `REASON_CODES` 又要与
  `.scratch/launcher-failure-reason/spec.md` 的码表表格集合相等。
- 认旧进程这条分支**不 `exit /b`**（踢完继续起服务），所以给它单独写一行留痕会**破坏
  「调用数 == 退出数」这条不变量**，并连带要改守卫、改码表、改已封口的
  `launcher-failure-reason` spec、重跑那支需要交互桌面、约 106 秒的探针（落盘还有 30 天新鲜度门禁）。
- 因此：**旧进程被踢这件事记在既有的 `started` 那一行上**——把 CLI 给的后半段当附加字段拼上去：
  `reason=started tries=1 port=8020 stale=1 served=1.1.1 disk=1.2.1`。
  变量为空时整段字段消失（`key=value` 形态要求值非空，空值会让 helper 抛错并**静默丢整行**，
  故取值前一律给初值）。`already_running` 那一行同样带上字段（便于事后判读「为什么复用了」）。
- 好处：码表、退出分支数、探针、以及 `launcher-failure-reason` 的已封口状态**全部不动**。

### 修复怎么到用户手上：**重发 v1.2.1（同 tag 换资产）**

- 事实：决定重启行为的是**被替换进去的那个包**里的启动器，而线上最新只到 v1.2.1，
  且 v1.1.1 与 v1.2.1 的 `start-app.bat` **逐字节相同**（sha256 `88a9c45b…` 三处相等）。
  **修复不在线上包里 → 不重发就永远到不了用户手上，验收判据也永远不成立。**
- 拍板（用户指示）：**版本号不动**，用 `pack-update.ps1` / `pack-full.ps1` 从修好的工作树
  重打两套资产，`gh release upload --clobber` 覆盖 v1.2.1 的 8 个附件。
- 代价（如实记账）：**已经装了旧 v1.2.1 的用户不会收到更新提示**（「检查更新」比的是版本号）。
  这条与 v1.2.0 两次重发留下的缺口同源，写进 `local-environment` 第 3 节。
- 打包纪律：`pack-update.ps1` 默认拒绝脏工作树 → **先提交修复再打包**，包内容 = 那笔提交。
- 自校验：重打出来的 `removed.txt` 应与线上那份**一致**（本次改动只增不删）——不一致就说明基线选错了。

### 真旧起点：还原一台真 v1.1.1 沙箱

- 「只把 `__init__.py` 改回 1.1.1」**验不出这条修复**：跑着的 webapp 仍是新版（带 `--port`），
  更新器会正确停掉端口，旧进程根本不存在 → drill 在「一行修复都没写」时也会绿。
- 起点 = 本机那份**没下过线的全量包** `firstep-pack\firstep-full-v1.1.1.zip`（783 MB / 8777 文件 /
  `version=v1.1.1`，其 `webapp.spawn_updater` 经逐行核实**没有** `--port`）：清空
  `Desktop\firstep-sim` → 解包 → 补回包内没有的沙箱专用入口 `sim-run.py`。
- 顺手写一个**可复跑的重建脚本**（`--write` 才落盘），把「下次还要重演」变成一条命令；
  `local-environment` 第 1 节要当场改正「用 `make_sim_sandbox.py` 重建就能还原旧版」这句错话
  （那个脚本是从**当前工作树**拷的，重建出来还是今天的代码）。

### 不做（明确否掉）

- **①「发布说明 / README 写『更新后请手动重开一次』」**：不改任何行为，drill 判据不可能成立；
  它服务的对象是「已经被旧包坑到的人」，而那批人靠本修复就能自愈。
- **③「更新器只清 lock，由启动器轮询 lock 消失后自己拉起」**：锁不是拦路虎（见「补充说明」的更正）。
- **⑤「更新器重启前先放锁」**：同上，且它对老用户结构性无效（跑着的更新器永远是发起那一代的代码）。

## 测试决策

- **谓词单测**（唯一新接缝，放既有 `tests/test_update_check.py` 的版本语义一组里）：
  真旧 / 相等 / 服务更新 / 空串 / 非 semver / `v` 前缀 / `1.10.0` vs `1.9.0`（语义而非字符串）；
  反向用例必须能红（把 `<` 改成 `<=` 或改成字符串比较，用例要挂）。
- **CLI 契约测试**（新测试文件）：真起一个进程内 HTTP 桩服务器 + **真子进程**跑 CLI，
  断言三种 token 与附加字段；覆盖「端口没人听」「应答的不是本应用」「health 缺 version」
  「非法 semver」四种 unknown 路径。判据只看 stdout 那一行。
- **`.bat` 静态守卫**：改后的启动器必须（a）调用那个 CLI（判据不在批处理里手写）、
  （b）只在 token 等于 `stale` 时才走踢进程那条路、（c）踢进程的作用域是
  `%FIRSTEP_LAUNCHER_PORT%`、（d）踢完仍走原 `:start_service`；并断言既有守卫**不动**：
  退出分支数不变、留痕调用数与之一一对应、码集合与码表一致。
- **不在 pytest 里真跑 `.bat` 的失败分支**——沿用 `tests/test_launcher_log.py` 开头那条硬约束：
  这些分支会弹**模态**弹窗，跑进测试会在用户桌面上留下一排框并把测试挂死。
  `.bat` 的真机结论由**演练**给（下一条）。
- **真机验收 = 既有演练脚本，不改脚本**：
  `python .scratch/verify-gate-drills/drill-01-upgrade.py`，
  判据 `RESULTS.endpoint.restarted_by_updater == true` 且 `RESULTS.endpoint.served == "1.2.1"`。
  脚本一个字不改（重发资产之后它下到的就是含修复的包），原始输出照旧落
  `.scratch/verify-gate-drills/verify-01-upgrade.{txt,json}`。
- 顺带把该脚本的「前后构成」一节当**孤儿文件**那条账的复核（不改口径，只如实记录）。

## 范围外

- 不改 README / 发布说明的「更新后请手动重开」话术（修法①已否）。
- 不动更新器的停服端口逻辑、不动锁协议、不动启动器的 `:updating` / `:update_left` 分支。
- 不修「同机双实例时更新器把 8000 上那个停掉」——那是发起方那一代代码的错，已发布的代码改不了，
  也不在本次修复的判据里。
- 不做资料库增量包、不动 `sources/materials`、不动版本号。
- 不给 `start-app.bat` 新增 reason 码（见「留痕」）。
- 不在真机上验「CCS 打开工程是否乱码」之类的相邻事项（与本缺陷无关）。

## 补充说明

### 两条更正（都推翻了本轮早先的判断，证据在文里）

1. **「更新器持着锁去重启 → 启动器先撞 `:updating` 弹窗、连端口探测都走不到」——错了，撤回。**
   决定性证据：B4 那个一次性演练目录还在（`%TEMP%\fe04-20260918-225014`），里面的
   `launcher.log` 是两行 `reason=started tries=1 port=8021`，其中第二行就是**更新器那次重启**——
   启动器走到的是「起服务」而不是「更新中」。原因是时序：更新器在
   `os.startfile(start-app.vbs)` 之后只剩一行日志 + `finally` 删锁（毫秒级），而
   `wscript → cmd → start-app.bat` 走到锁检查那一行要跑 `chcp`、`cd /d`、若干 `set` 与
   `echo|findstr` 两个进程（几十上百毫秒）——**锁在启动器检查之前就没了**。
   ⇒ ③/⑤ 都不需要；drill 把 `USERPROFILE` 重定向出去**不是保真度问题**（真机上启动器看到的
   同样是「没锁」），**不用动 drill 的隔离手法**。
2. **缺陷射程更正**（见「问题陈述」末段）：默认端口 8000 的用户不受影响，
   只有端口 ≠ 8000（含同机双实例）才中招；且只有**小发版**那条路缺 `--port`。
   `backlog.md` 里本单标的是 🔴「用户可见」，要按这条更正口径。

### 一处已知窗口（不修，如实记）

「更新器放锁」与「启动器检查锁」之间是**竞争**：机器极慢或启动器链极慢时，启动器仍可能
先看到锁而弹「正在更新中」。这是既有行为，概率极低，且**自愈**：用户再双击一次即可
（那时顺手也会命中本修复）。本轮不动它。

本 spec 的拍板来自一次 grilling：修法三选一 → ②（用户：老版用户不用管；查证后确认 ② 无需
