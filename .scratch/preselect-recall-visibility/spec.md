## 问题陈述

用户用 AI 推荐模块时，模型会推荐库里明明有的模块（典型：小车题推荐 `motor`），系统却回一句「模型推荐了库中不存在的模块：motor」并以 400 结束，**整条推荐流程中断**，用户拿不到任何推荐结果，只能自己翻模块网格手动补。

根因不是模型幻觉，而是判据取错了源：提示词里的模块清单被题面预筛截断成子集（真实库 stm32 86 条只进 34 条），而「库里有什么模块」这个合法性判据也取自同一份子集。**模型看不见的模块被当成了不存在的模块**。实测（2024H 自动行驶小车 / stm32）：`motor` 排名 71/86、`pid` 76、`servo` 78、`key` 65、`led` 67、`oled` 74，全部在截断线外。

同一份子集还被用来决定「哪些模块支持多实例」：即使推荐被放行，模型给这些模块配实例时也会二次硬失败（「给非多实例模块带 instances」），或实例卡空着让用户手填。

## 方案

把两件事分开，各归其位：

1. **「库里有什么」= 平台全量**（判据，权威、不随题面变）；
2. **「提示词里展示什么」= 预筛子集**（只是给模型看的上下文，可以截断）。

模型推荐任何平台库内模块都放行；多实例能力清单同样取平台全量，保证放行之后配实例不再二次失败。展示子集保持不变，本轮不承诺「关键模块可见」——那是下一批（预筛评分与摘要行瘦身）的事。

同时补一层**覆盖率守卫**：用真实题库跑预筛，把「小车类赛题的关键执行/交互模块必须出现在提示词里」钉成断言。现在它红着（xfail 标记，原因写清），下一批修好预筛后自动转绿并反过来锁住修复成果——防止「库再长大、可见比例再降」再次静默发生（现有测试只断字节数不守覆盖，这是它能一直绿的原因）。

## 用户故事

1. 作为使用者，我想要模型推荐库内模块时不被当成幻觉拒绝，以便小车、循迹、PID 这类题能正常拿到推荐结果。
2. 作为使用者，我想要推荐结果里出现的关键模块能直接配实例（实例卡有默认值），以便不用手动添加。
3. 作为使用者，我想要「模型看不见的模块」和「库里没有的模块」被区分对待——前者放行、后者仍然大声拒绝，以便真正的幻觉不会被静默吞掉。
4. 作为维护者，我想要一条能复跑的覆盖率断言，以便模块库继续长大时，可见性退化会被测试抓住而不是靠人工审计。
5. 作为维护者，我想要预筛子集与合法性判据的边界在代码里有唯一出处，以便以后调整预筛评分时不会再连带改变「什么算合法模块」。
6. 作为维护者，我想要 CLI 与网页两条入口对同一份库行为一致，以便修一处不会漏另一处。

## 实现决策

- **装配点**：`TopicContext` 新增「平台全量摘要」字段（与既有「摘要行」字段并存）。既有字段语义收紧为「喂给模型的清单行」（**仍可被预筛截断**）；新字段语义为「判据用的库内全集」。CLI 与网页两条入口都由装配点填充；网页侧**继续**把清单行替换为预筛子集（那是 128KB 网关预算的必要截断），被纠正的是「判据也跟着截断」——判据改取新字段，不再受替换影响。
- **预筛结果**：`PreselectResult` 增加「全量」字段（与「子集」「总数」「是否截断」并列），预筛成为「子集 + 全量」的唯一出处；调用方要哪一份显式取哪一份。
- **推荐编排**：`run_recommendation` 从 `topic.library_summaries` 取「全量」传给收敛循环用于（a）模型推荐合法性校验、（b）多实例能力清单、（c）默认实例兜底；「子集」仍只用于渲染提示词清单段。`select_modules` 增加可选入参承接「合法性全集」；**入参与清单行相同则不传**，缺省回落清单行（CLI 与既有调用零改动）。
- **收敛循环**：`select_modules_convergent` 透传上述可选入参，且仅在「全量 ≠ 清单行」时传（相同则保持旧调用形状）；每轮都传同一个全集（预筛只在进入循环前发生一次，全集不随轮次变）。
- **不变式**：展示子集 ⊆ 全量；不传「合法性全集」时判据 == 展示集（向后兼容既有调用与测试）。
- **平台过滤**：全量已经是平台过滤后的集合（装配点按生成平台过滤一次），本轮不引入跨平台模块。
- **缓存**：缓存键仍只由题面决定。**库指纹取源改为平台全量**（评审整改，见「补充说明」）：本轮把「库里有什么」归给全量后，指纹若仍吃预筛子集，子集外模块的增删改不会让缓存失效——与「判据同源」原则冲突。代价：既有缓存条目在库内容变化时按新口径失效一次。
- **错误契约**：真幻觉（库内确无此 slug）仍抛 `SelectionError` → 400 中文，文案逐字不变；客户端类错误免重试的既有取舍不变。

## 测试决策

- **测试接缝**（与用户确认 + 评审整改）：判据修复走**最高 seam = `/api/recommend` 端点**（`TestClient` + 假 LLM 按生产语义用 `known_summaries` 做域判决，断言 done 载荷），域判决的逐字红证落在 `select_modules` 解析层（`tests/test_llm.py`，真 `DeepSeekLLM` + 假 transport——只有这一层能跑 `build_module_selection`）；覆盖率守卫走**预筛层**（真实题库 `library/topics/*/topic.md` 跑 `preselect_module_summaries`）。
- **只测外部行为**：断言「模型推荐不可见模块时推荐不被拒、done 载荷含该模块」「真幻觉仍拒」「关键模块出现在预筛结果里」。预筛结果的三元契约（子集 / 总数 / 是否截断 / 全量）是 `PreselectResult` 的公开形状，断言它属于契约测试而非实现细节。
- **既有先例**：`tests/test_webapp.py::test_recommend_done_includes_default_instances_for_multi_module`（端点 seam + done 载荷）、`tests/test_selection.py::test_run_recommendation_*`（编排直调）、`tests/test_llm.py::test_recommend_real_library_budget`（真实库预算回归）。
- **覆盖率断言的处理**：本轮以 `pytest.mark.xfail(strict=True, reason=...)` 落盘——断言「2024H / stm32 下 motor / pid / servo / led / key 必须在预筛结果内」，当前必然失败故标记预期失败；下一批修好预筛后自动转绿，`strict=True` 保证「修好了却没摘标记」也会红。断言消息（缺哪些模块、可见 N/M）默认被 xfail 吞掉，复看用 `pytest tests/test_preselect_coverage.py --runxfail -q`。
