# 修订与深化（revise-deepen）— spec

## 问题陈述

当前管线是单向流水线：赛题 → 推荐（含 Q&A）→ 选模块 → 骨架 → 生成 → 编译修复 → 交接。赛题答疑 Q&A（赛事组澄清）**只允许在推荐之前输入**；但实际竞赛中，专家答复常常在工程生成之后甚至很久之后才发布。此时用户没有途径把新 Q&A 补进流程：

- 无法让 AI 判断新 Q&A 是否与已推荐的模块一致（可能新增需求、可能确认原方案、也可能推翻部分模块）；
- 无法把模块变化应用到已生成的工程；
- 工具承诺停在"骨架 + 交接"，AI 精打磨被推给下一个会话，用户想在工具内继续把逻辑写出来（"挂肉"）也没有入口。

## 方案

在生成页新增一个生成后阶段「修订与深化」，支持两个能力，共用一条流程：

- **修订**：补入新 Q&A → AI 逐条分析影响（影响哪些功能需求 → 建议模块增/删/不变 + 理由）→ 展示确定性 diff（新旧模块集差异）→ 用户确认 → 覆盖式重生成进同一输出目录（修订前整树备份，可回滚）。
- **深化**：AI 按功能需求清单逐条填充 main.c 的 TODO 预留区 → 强制走编译验证闭环（编译 → 失败自动修复 → 重编译）→ 编译绿标记"已验证"；无工具链时大声降级提示，不静默交付未验证逻辑。

两条入口共用同一流程：

- **当前会话入口**：上下文（题面 / 平台 / 模块 / 绑定 / 输出目录）直接从页面状态取，一键进入。
- **历史目录入口**：选择任意输出目录 → 自动反推上下文（工程配置文件认平台；工程内模块文件反查库内 slug；引脚配置回读绑定；main.c 现读）→ 题面无法反推时要求用户补（粘贴或选题号）。新生成的工程自带上下文清单（见实现决策），有清单时直读、无需反推。

模块有变化 → 重生成（main.c 由新骨架替换，旧 main.c 进备份）；模块没变化 → 不重生成、main.c 原样保留（不丢手工编辑），深化直接在现有 main.c 上填 TODO。

## 用户故事

1. 作为参赛学生，我想要在工程生成后把新发布的赛事答疑 Q&A 补进来，以便 AI 判断新 Q&A 是否改变原有模块推荐。
2. 作为参赛学生，我想要看到逐条 Q&A 的影响分析（影响哪些功能需求、建议增删哪些模块、理由是什么），以便理解并确认 AI 的判断，而不是盲信。
3. 作为参赛学生，我想要在确认后让工具把模块变化应用到已生成工程（覆盖式重生成进同一目录），以便工程与新 Q&A 保持一致。
4. 作为参赛学生，我想要修订前自动整树备份、修订后可一键回滚，以便修订结果不理想时恢复原状。
5. 作为参赛学生，我想要在很久之后（甚至隔天隔周）对一个历史输出目录发起修订（选目录 → 自动识别平台/模块/绑定 → 补题面），以便专家答复迟到时仍能更新工程。
6. 作为参赛学生，我想要新生成的工程自带上下文清单，以便将来任何时候修订都无需反推、无需回忆当时的选择。
7. 作为参赛学生，我想要在模块没变化时保留我对 main.c 的手工编辑，以便修订不覆盖我的手动改动。
8. 作为参赛学生，我想要可选地让 AI 按功能需求逐条填充 main.c 的 TODO，以便把骨架变成可运行的题解雏形（"挂肉"）。
9. 作为参赛学生，我想要深化产物必须经过编译验证（编译绿才标记"已验证"），以便守住"打开就能编译"的承诺；没有工具链时收到明确降级提示。
10. 作为参赛学生，我想要在修订完成后看到本次 diff 记录（模块增删、Q&A 原文、验证状态），以便留存变更轨迹。
11. 作为后续会话的 AI，我想要从输出目录里的上下文清单完整恢复生成时的输入（题面 / 平台 / 模块 / Q&A / 绑定 / 参考），以便接续修订或交接，不丢失原始上下文。

## 实现决策

- **新阶段卡**：生成页「修复中心」之后新增「修订与深化」阶段卡（不做新顶层板块）——输入全部来自当前会话，独立板块反而要重新收集上下文。历史目录入口作为该卡的第二个入口。
- **两段式 API**（对照「推荐」与「生成」分离按钮的先例）：先 `分析`（耗时 LLM：影响分析 + diff，返回待确认结果），用户确认后再 `执行`（重生成 / 深化，SSE 进度流）。
- **上下文清单**：生成尾部写纯新增隐藏清单文件（README.md 先例——纯新增文件，不触碰任何既有生成文件，逐字节契约不破；不被 Keil/CCS 编译影响）。内容：题面、平台、所选模块 slugs、绑定、多实例清单、Python 副产物模板选择、Q&A 原文、功能需求清单（推荐产物摘要，随生成请求回传）、参考条目、生成时间、工具版本。读侧对缺字段 / 旧版本向后兼容（缺字段 = 走反推或要求补）。
- **历史目录反推**：平台 = 工程配置文件识别（沿用既有查找器）；模块 = 工程内模块文件 ↔ 库内 slug 映射反查（歧义 / 找不到 → 要求用户手动勾选，不猜测）；绑定 = 从引脚配置（stm32 宏 / mspm0 赋值行）回读成绑定载荷；题面 = 反推不了，清单缺失时必填（粘贴或选题号），缺题面明确提示。
- **影响分析**：新 Q&A 以独立段注入（沿用收敛循环的 Q&A 段先例，不并入题面、不动题面编号），产出 = 逐条 Q&A 的影响结论 + 建议模块集；**新旧模块集差异是确定性 diff**（集合差），AI 只负责解释"为什么"，不负责"算差异"。
- **覆盖式重生成**：生成器现拒绝非空输出目录——修订执行 = 整树备份到输出目录外（修复备份先例）→ 重建输出目录 → 复用既有生成管线（含门禁 / 绑定写侧 / 多实例 / 副产物 / README / 构建脚本全链路）。备份编号可回滚（对照修复中心回滚先例）。
- **main.c 保全策略**：模块集变化 → 重生成时骨架重生成（新 main.c 替换，旧版进备份）；模块集不变 → 不重生成，main.c 原样保留，深化读现有 main.c 填 TODO（用户手工编辑不丢）。
- **深化**：输入 = 现有 main.c（含 TODO）+ 功能需求清单 + 模块接口清单 + 题面与 Q&A；输出 = 实现后的 main.c。执行后强制走既有编译 → 修复闭环（工具链探测复用）；编译绿 → 标记"已验证"；无工具链 → 大声降级（结果保留但状态 = 未验证）。深化不设自动循环，用户可重复触发。
- **进度与事件**：SSE 流 + 事件词表扩展（影响分析 / diff 就绪 / 备份 / 重生成 / 深化 / 验证状态），照既有进度事件先例。
- **词表**：修订（revision，新 Q&A → 一致性 → 重生成）、深化（deepening，填 TODO → 编译验证）两个术语进 CONTEXT.md。

## 测试决策

- **只测外部行为**：不测 LLM 内部，LLM 一律走既有假 LLM 先例（结构化输出解析）。
- **上下文清单**：写读 roundtrip；缺字段 / 旧版本清单兼容；落盘不影响既有生成文件（缺省路径输出与现状逐字节一致——沿用既有逐字节断言先例）。
- **反推**：构造已知工程目录 → 平台 / 模块 / 绑定回读断言；歧义模块 → 报错并走手动勾选路径。
- **diff**：新旧 slugs 集合 → 确定性增删清单（纯函数）。
- **影响分析**：假 LLM 输出 → 解析为影响结论 + 建议模块集；非法输出 → 重试兜底（复用解析重试先例）。
- **修订执行**：确认后目录内容 = 新生成产物；回滚后目录内容 = 备份内容（逐文件比对）。
- **深化**：假 LLM 输出 main.c → 写盘断言；编译验证状态标记；无工具链降级路径。
- **测试先例**：selection / generator / fix_errors 的既有测试结构（内存目录、假 LLM、逐字节断言）。

## 范围外

- 不从历史目录反推题面（产物里没有的东西反推不了；靠上下文清单 + 用户补）。
- 不做"无限打磨"自动循环（深化每轮一次，用户可重复触发）。
- 不自动把生成工程提交 git。
- 不为深化引入远程 / 容器化编译。
- 修订过程中发现库外需求 → 走既有「库外建议」展示，不自动补录模块库。
- 不做生成前的 Q&A 输入流程改造（现流程保持不动，本次只加生成后入口）。

## 补充说明

- 术语命名：用户口语称"修改"；spec 定名「修订」（revision）与「深化」（deepening），落 CONTEXT.md 词表。
- 历史遗留工程的修订体验：无上下文清单 → 反推 + 补题面；有清单（新工程）→ 一键直读。
- 影响分析的「逐条 Q&A 影响」是收敛循环的增量扩展：Q&A 段注入机制与缓存指纹机制（Q&A 变化缓存失效）直接复用，不新造轮子。
- 深化依赖功能需求清单：推荐产物摘要需随生成请求回传并落盘（影响 01 工单的清单内容）。
