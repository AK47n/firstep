# 深化效果报告（deepen-report）— spec

## 问题陈述

深化（revise-deepen/04）完成后，用户只看到「深化完成」+ 验证状态徽章（已验证 / 未验证 / 失败）与编译摘要，**完全不知道 AI 对 main.c 到底改了什么**：填了哪些 TODO、新增/删除了哪些代码、一共几处改动。用户原话：「现在说深化完成但我怎么知道深化的效果怎么样呢，应该出个介绍告诉我深化了什么」。

## 方案

深化结束载荷新增「深化效果」报告：以深化前 main_c 与深化后 deepened 的**确定性 diff** 为唯一事实来源（不依赖 LLM 自述，杜绝「说做了 A 实际做了 B」），前端渲染介绍卡：

- **统计行**：新增 +N 行 · 删除 −M 行 · 共 K 处改动；
- **改动点列表**：每个 diff hunk 一块（可折叠 <details>），标题优先取 hunk 中被替换的 TODO 注释（如「填充 TODO：循迹判断」），退化取注释行 / 「第 N 行附近」；展开显示逐行 diff（新增绿 / 删除红 / 上下文灰）；
- 无差异（LLM 原样返回）→ 显示「深化未改动 main.c（无差异）」占位。

不改 LLM 调用链（不额外花一次调用、不冒解析风险）、不改 SSE 事件序列，只扩 done 载荷字段。

## 用户故事

1. 作为参赛学生，我想要深化完成后立刻看到「深化了什么」的介绍（改动统计 + 逐处改动点），以便判断 AI 填充的质量，而不是只看到一句「深化完成」。
2. 作为参赛学生，我想要介绍基于真实代码 diff（可展开查看每处改动的具体代码），以便信任介绍内容、并为后续手工调整定位。

## 实现决策

- **diff 事实源**：`difflib.unified_diff(deepened 前后, n=2)` —— 深化前 main_c 已在 run_deepen 参数里，零额外成本。
- **载荷字段**：done 载荷新增 `main_diff`：`null`（无差异）或 `{"text": unified diff 全文, "stats": {"additions", "deletions", "hunks"}, "hunks": [{"header", "line"（新文件起始行号）, "title", "lines": [{"kind": add|del|ctx, "text": 无前缀原文}]}]}`。旧前端无字段时按「未见报告」处理，不强依赖。
- **标题提取**（纯函数 `_hunk_title`，放在 deepen.py 可单测）：① hunk 删除行中第一条含 TODO/FIXME/XXX 的注释 → 「填充 TODO「<注释文本>」」；② 删除行第一条注释行 → 注释文本；③ 上下文行第一条注释行 → 注释文本；④ 空 → 前端 fallback「第 N 行附近」。
- **渲染位置**：`reviseRenderVerify`（深化验证卡内）追加「深化效果」块；修订执行后勾选深化、直接深化两条路径共用该函数，一处生效。
- **词表**：无新术语（「深化效果」是深化一词的展示侧延伸）。

## 测试决策

- **纯函数测试**：`_main_diff` 单测（无差异 → None；单 hunk 增删统计；多 hunk 统计与 line 号）。
- **行为测试**：既有 run_deepen 用例补断言（载荷含 main_diff、stats 正确、标题含 TODO）；webapp 端点 done 载荷含 main_diff 与 main.c 写盘一致。
- **测试先例**：tests/test_deepen.py 既有结构（假 LLM、fake emit、monkeypatch 工具链）。

## 范围外

- 不做「每条需求 → 实现说明」的 LLM 叙述（diff 已足够回答「改了什么」，且零幻觉风险）。
- 不改深化 prompt / 不新增 LLM 调用。
- 不为 diff 做行级语义分析（函数名识别等）——注释是最高优先级的直读标题。
