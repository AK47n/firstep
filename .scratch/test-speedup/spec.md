# spec —— 测试提速与「卡死」收口（test-speedup）

## 问题陈述

改一处代码要等全套回归跑完，慢得让人不想跑——而不跑的代价已经出现过：2026-09-15 的
「编译产物不入库」清理把 mspm0 母版 `.settings/`（含 CCS 工程编码钉）一起删了，
`tests/test_readme.py` 当场变红，但**没人发现**（本轮基线实测：main 上本来就有这条红）。

两条具体症状：

1. **慢**：全套 196 个测试文件，逐文件跑 315s（2026-09-16 实测）、历史记录 550s 上下；
   单进程一条命令跑 130s 上下——但没人敢用后者（见第 2 条）。
2. **会卡死**：`python -m pytest` 整支跑**间歇性卡住十分钟以上**（`docs/agents/local-environment.md`
   2.5 节记了两次，一次后台跑 40 分钟没完、CPU 只烧了 120s）。卡住时既没有报错也没有栈，
   现场只剩「等」——于是所有人都退回避得远远的逐文件跑法。

## 方案

给测试跑法补两件「计时器」，一件管上限、一件管并行：

1. **全库默认超时**（`pytest-timeout`）：任何一个用例卡住超过阈值 → 当场判红 + 打印所有
   线程的栈。口径从「卡住不算判据」改成「卡住 = 红」。已实测本机平台行为：
   Windows 上只有 `thread` 方法可用（`signal` 直接 INTERNALERROR），且超时触发时**整场
   中止**而不是只废掉那一个用例——这条要写进文档，否则会被误读成「只红一格」。
2. **并行是 opt-in**（`pytest-xdist`）：插件装上、命令里手动 `-n auto`。**不写进
   `pyproject.toml` 的 `addopts`**——全仓共享配置会改掉所有既有跑法（文档、探针、
   `.scratch` 里的批跑器），且并行引入的偶发更难归因。

再补一条**结构守卫**：把「超时口径已配置且值在合理区间」钉成用例，防止下一个人顺手把它删掉
（本仓库既有风格：`test_ps1_encoding.py` / `test_repo_language.py` 都是这类「守口径」用例）。

## 用户故事

1. 作为本仓库的开发者，我想要一条命令跑完全套且**永远不会无限等**，以便放心地用「跑全套」当验收。
2. 作为本仓库的开发者，我想要卡住时**拿到现场**（栈、哪个用例、哪个线程），以便不必重演整晚去定位。
3. 作为本仓库的开发者，我想要需要时能**并行跑**，以便把一轮回归从分钟级压到更短。
4. 作为本仓库的开发者，我想要超时阈值与它所依据的实测数字**写在一处**，以便以后有人改它时知道为什么是这个值。
5. 作为接手这个仓库的下一个人，我想要**「卡住不算判据」这条旧口径被明确作废**，以便不再按旧口径读红绿。

## 实现决策

- **依赖声明**：`pytest-xdist` / `pytest-timeout` 进 `pyproject.toml` 的 `dev` 可选依赖
  （与既有 `pytest` / `httpx` 同处），不新增运行时依赖。
- **配置落点**：`[tool.pytest.ini_options]` 里加 `timeout` 与 `timeout_method`，就近写中文注释
  说明「为什么是这个值」与「Windows 上 thread 方法的语义」。
- **不做并行默认**：`addopts` 不动。
- **超时阈值**：取「实测最慢单用例 × 余量」，具体数字由工单 02 的测量结果定（先测后定，
  不拍脑袋），并在守卫里钉一个允许区间。
- **不改产品代码**：本轮零 `src/` 改动。若复现出的是产品缺陷（而不是测试自身），另立工单，
  不在本 spec 里顺手改。
- **文档**：`docs/agents/local-environment.md` 2.5 节是这条口径的家（那里记着旧现象），
  本轮把新口径与实测数字写回同一处。

## 测试决策

- **好测试**：断言的是「跑法口径」而不是「某个实现细节」——超时配置存在、值在区间内、
  插件在 dev 依赖里。既有先例：`tests/test_ps1_encoding.py`、`tests/test_repo_language.py`。
- **测哪些模块**：`pyproject.toml`（配置面）。不改产品模块，故不新增产品侧用例。
- **仪器的反向验证**（必须做，照本仓库惯例）：故意造一个会睡的用例，确认超时**真的会响**
  （本轮已实测：120s 的 sleep、阈值 3s → 6.5s 判红 + 倒栈 + 退出码 1）；再做一次
  「拿掉配置 → 守卫变红」的反向验证。
- **卡死复现**：`.scratch/test-speedup/probe-hang.py`——整支 pytest 反复跑，卡住时靠
  `-o faulthandler_timeout=30` 自己倒栈（照 2.5 节推荐的定位姿势）。复现不出就如实记
  「n 轮未复现」，不编根因。

## 范围外

- **CI**：用户本轮明确「不做，另议」。仓库无 `.github`，591MB 仓库 + node/pytest 两套用例另立项。
- **node 侧**（`node --test tests/js/*.test.mjs`，1470 用例）：node 自带并发，本轮不动。
- **修那条 main 上的红**（mspm0 `.settings/` 缺失）：属清理线回归，另立条目，见本轮报告。
- **产品性能**：本 spec 只管测试跑法。

## 补充说明

- 唯一改口径的决定 = 「卡住 = 红」。它的代价要写清楚：机器卡顿/杀毒扫描可能造成假红，
  所以阈值要给足余量（依据实测最慢用例），而不是压到刚好够用。
- 逐文件跑法（`.scratch/resumable-download/run-11-suite.py`，每文件 120s 超时）**保留**：
  它的价值是「卡住与红分开记」，与整支超时互补，不互相取代。
