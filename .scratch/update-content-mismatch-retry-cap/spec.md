# spec — 持久的「内容与清单不符」要能收敛：连续 5 次就转终态

> 决策单：`issues/01-content-mismatch-unbounded-retry.md`（发现于沙箱真机演练 B2 场景四，
> `sandbox-drill/02`）。**本轮拍板：选 1（加封顶），N = 5。**
> 证据：`.scratch/verify-gate-drills/verify-02-degraded.{txt,json}` 的 `scenarios.content-mismatch`。

## 问题陈述

「下完了整卷、但内容与清单的 SHA256 不符」这种失败，现在的策略是**删掉半成品 + 退避重试，
从 0 整卷重来，直到对上或用户取消**（`.scratch/resumable-download/spec.md` 第 122 行）。
这条策略是为「服务器上那份是坏的 / 清单里的哈希过期了」这类**持久**故障写的，而它对持久故障
永远收敛不了，真机第一次跑出来的后果是：

| 观察 | 实测 |
|---|---|
| 终态 | **没有**（150 秒观察窗内 6 次重试后仍在 `downloading`） |
| `retry_count` | 1 → 6 持续增长（退避 2、4、8、16、32、60 秒封顶） |
| 服务器台账 | 6 次请求，**起始偏移全是 0**（每轮整卷重下） |
| 进行中摘要 | 中文、说明「内容与清单不符，已删除重下，会重新下载整卷」 |
| 用户看到的出路 | 只有自己点「取消」 |

**代价**：线上完整包 765 MB/卷，退避封顶后约每 60 秒重下一整卷 ⇒ 约 **45 GB/小时**量级的流量
黑洞；同时 spec 第 177 行承诺的那句「校验失败 → 明确『重下不会有变化』」的**终态话术
在这个分支永远不会出现**——它压根进不了失败态。

**为什么网络失败的无上限不能照搬到这条**：网络是**瞬时**的不确定性（同一个请求重试就可能成功），
内容不符是**持久**的不确定性（重试改变不了服务器上那份字节）。两类不确定性不该共用同一条策略。

## 方案

**同一卷连续 N 次「内容不符」→ 转终态失败，中文说清「重下不会有变化」。**

- N = 5（退避 2+4+8+16 = 30 秒，加上 5 次整卷重下与校验的时间，仍在本仓演练的 150 秒观察窗内）。
- 转终态时给的文案要接上 spec 第 177 行的承诺：说明「服务器上这份可能与清单对不上」+
  「重下不会有变化」+ 可行动作（稍后再试 / 反馈发布者）。
- **网络失败仍然无上限**（不动那条口径）；只有「连续内容不符」计数，任何其它错误或任何一次
  成功都把它清零。

用户可观察的结果：撞上持久内容不符时，工具会在约半分钟内**明确失败**并说清原因，
而不是每 60 秒静默重下整整一卷、永远转下去。

## 用户故事

1. 作为撞上「服务器上那份坏了」的用户，我希望工具在一段时间后明确告诉我失败了，
   以便我不是对着进度条等到天荒地老。
2. 作为流量/磁盘有限的用户，我希望它不要每 60 秒重下 765 MB，以便一次故障不会烧掉几十 GB。
3. 作为想自己排查的用户，我希望失败话术说清「发布物可能与清单对不上，重下不会有变化，
   可以稍后再试或反馈发布者」，以便我知道下一步该做什么（而不是看到「网络问题」这种误导）。
4. 作为网络不稳的用户，我希望**网络类失败仍然无上限重试**，以便弱网下我不会被误判成失败。
5. 作为维护者，我希望这条封顶是「分类单源」的一部分（新终态错误也归 `verify`、也不可重试），
   以便它自动落进同批的清理规则（不可重试的校验失败不留半成品），不必各写一遍。
6. 作为维护者，我希望这条修复有单测 + 反向注入探针 + 真机复跑（`terminal_reached == true`），
   以便「它到底会不会转终态」永远有可复跑的答案。

## 实现决策

### 计数与判据

- 计数住在下载域的重试循环里（**连续**计数：遇到内容不符 +1，遇到任何别的错误或成功清零）。
  不跨进程持久化：用户重新点一次下载就是一次新的尝试序列（与「取消后接着下」的语义不冲突）。
- 上限是模块级常量（`MAX_CONTENT_MISMATCH_ATTEMPTS = 5`），只有测试用的假服务器才需要覆盖它
  ——沿用既有的「测试专用参数给假剧本用」的纪律，不新增产品侧开关。

### 新的终态错误

- 新增一个下载域异常类型（**内容不符 · 已连续多次**），语义与谱系：
  - 归 `error_kind = "verify"`（与前几轮的归因一致：别说「网络问题、会自动重连」）；
  - **不可重试**（进既有那张「重试必然同样结果」的表）——它就是为了跳出无上限循环而存在的；
  - 中文文案由既有 `describe_network_error` 单源给出，并**取代**掉进循环前那句
    「会重新下载整卷」（后者对持久故障是谎话）。
- 为什么不复用既有的「清单与服务器总长矛盾」那支：归因不同（那一支是发布物长度对不上、
  这一支是内容哈希对不上），文案要能分别说清；混用会让用户拿错排查方向。
- 前 N−1 次的行为**逐字不变**（仍走「删半成品 + 退避重试」，进行中摘要照旧），
  这样「服务器只是偶发坏了一次」的场景不受影响。

### 两条链路的落点

- 计数与封顶都在共享的下载域里，完整包与资料库两条链路自动同时生效；
  任务层不需要改（它已经有「任何异常 → 失败 + `error_kind`」的路径）。
- 与本批另一条修复的关系：终态异常不可重试且归 `verify` ⇒ 任务层的「不可重试的校验失败
  清掉半成品与边车」自动生效。这条组合**要有断言**（终态之后盘上是干净的），
  否则两条修复各自正确、合起来仍可能留垃圾。

### 验收

- 单测（在既有 `tests/test_download_resume.py` 里，沿用既有的假 opener / 假响应夹具）：
  - 「永远返回坏字节」→ 尝试次数 == 5、抛出的是新终态类型、`error_kind == "verify"`、
    文案含「重下不会有变化」；
  - 「坏 2 次后变好」→ 成功且 `retried == True`（封顶没被误伤）；
  - 「坏 1 次 → 截断 1 次 → 又坏」→ 计数被清零（连续语义，不是累计）；
  - 网络类失败仍然无上限（用小 `max_attempts` 的假剧本证明它走的是原来那条路）。
- 反向注入探针（`.scratch/update-content-mismatch-retry-cap/probe-guard-strength.py`）：
  把封顶去掉（回到无上限）、把连续改成累计、把新错误从「不可重试」表里拿掉，
  三处注入都必须让对应用例**转红**；跑完复原并复核 sha256。
- 真机复跑（`.scratch/update-content-mismatch-retry-cap/run-real-machine.py`，drill-02 零改动）：
  把工作树里修好的源码放进沙箱（harness 步骤，显式记账），
  `python .scratch/verify-gate-drills/drill-02-degraded.py --only content-mismatch`，
  判据 = `.json` 的 `scenarios.content-mismatch.terminal_reached == true`，
  终态 `failed`、`error_kind == "verify"`、`error` 中文且含「重下不会有变化」、
  `max_retry_count` 有界（≤5），且该格不再打印「无终态」那句记录。

## 测试决策

- **好测试**：只断言外部可观察量——尝试次数、抛出的异常类型、`error_kind`、文案关键句、
  以及「坏几次之后转好还能成功」。不测计数器变量本身。
- **既有先例**：`tests/test_download_resume.py` 已有整套假服务器/假 opener 夹具与
  「重试几次后成功」「不可重试直接抛」两类判据，本单在同族里加格。
- **文案判据取关键词**（「重下不会有变化」）而不是整句，避免文案微调就打红——但关键词要
  足够具体，能防「随便一句中文」蒙混（反向注入里会把它改回「会重新下载整卷」验证转红）。
- **真机**：drill-02 冻结不改；偏离写进我们自己的包装脚本。

## 范围外

- 不改网络类失败的无上限重试（这是本单刻意保留的另一半）。
- 不加产品侧的「重试次数上限」配置项（用户看不到、也没人会用；5 是工程判断，
  要调就改常量与它的守卫）。
- 不做「跨进程记住连续次数」（换一次进程就是新序列，符合用户直觉）。
- 不做「换源重试」（另说；当前只有 GitHub 一个源）。
- 不改前端（终态与话术都走既有 `failed` + `error` 通道）。

## 补充说明

### 与「只加可见性」那条备选的比较（拍板理由）

备选 2（不改策略，只在摘要里写「已重试 N 次仍不符（已重下 X MB）」）成本最低，但它把
「要不要停」的判断留给用户，而用户此刻看到的是一句「正在自动重试」——**流量还在烧，
只是多了一行字**。备选 3（维持现状 + 写进 spec）等于承认「校验失败永远进不了失败态」，
与 spec 第 177 行那句承诺直接冲突。选 1 的代价是「真的坏掉的服务器在 5 轮之后被判死」，
但那条路本来也没有出路（用户唯一能做的就是取消），而它换来的是**明确、可行动的失败态**。

### 一处刻意的粗糙

N=5 是工程判断而不是算出来的最优点：它要同时满足「偶发一次坏字节不被误杀」与「150 秒观察窗内
一定收敛」。5 次退避合计 30 秒，对「偶发坏字节」留了足够余量（连续 5 次都坏基本可以确定是
持久故障），也远小于线上用户能忍受的等待。要改它，改常量 + 跑那支反向注入探针。
