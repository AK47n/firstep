# spec — 发 v1.2.2：把 B1–B5 三张单的修复送到用户手上

> 上游：`.scratch/backlog.md` 第 8 节（三张单已 resolved，**本轮不发版**，留给下一个版本号）
> 与 `docs/agents/local-environment.md` 第 0/3 节。发布流程见 `docs/agents/releasing.md`。

## 问题陈述

B1–B5 演练开出来的三张单已经全部修好、判据也都在本机复跑成立，但**线上仍停在 v1.2.1**。
于是那三条修复一个字节都没到用户手上：

1. **小发版包多发本机库备份**（1481 个 `library/revise-backups/**`）——每个点「一键更新」的
   用户盘上都会多出别人机器上的库快照；同时 `00-START-HERE.txt` 从来没通过升级路径发出去过
   （v1.1.1 的用户永远拿不到它，而全新安装的用户有）。
2. **不可重试的校验失败留下整卷半成品**——线上完整包 765 MB/卷，用户看到「失败」之后
   `updates/full/` 里白占几百 MB，磁盘不宽裕的机器直接影响他能不能重下。
3. **持久的「内容与清单不符」永远收敛不了**——线上完整包场景约 45 GB/小时的流量黑洞，
   用户唯一的出路是自己点取消。

这三条都是**用户可见的**（不是内部卫生）：合计后果 = 盘上多一份不属于自己的东西、
失败后白占空间、一个永不停歇的重下循环。

## 方案

**发 v1.2.2（修订号 +1），一次把三条修复带上；`main` 上还有一条同类的「完整包发、小发版不发」
的落差（`src/contest_generator.egg-info/**`）也一并关掉，让「升级后的盘面与全新安装一致」
这条判据在任何安装路径下都成立。**

用户可观察的结果：

- 点「一键更新」之后，工具根里的产品文件与全新安装该版本**一致**——不多（不再多出别人的
  库备份）、不少（新增的 `00-START-HERE.txt` 真的到手）、`egg-info` 这类 pip 构建产物两边都不发；
- 撞上「发布物与清单不一致」时，失败态是**干净的**（不留整卷半成品）；
- 撞上持久的「内容不符」时，约半分钟内**明确失败**并说清「重下不会有变化」，而不是每 60 秒
  静默重下一整卷。

## 实现决策

### 版本号与范围

- **v1.2.2**（`docs/agents/releasing.md` 的 SemVer 表：bug 修复 → 修订号 +1）。
- **只发这一版**：不夹带任何非修复项。`identity-fields/06`（6 slug / 11 条硬件身份字段）
  是「人工取源」队列——本轮实测仍核不出可核实的购买/官方页，**挂账不发版阻塞**（见「范围外」）。
- 两件套都发（小发版四件套 + 完整包四件套，共 8 个资产，同一个 Release）。
  完整包同时是新用户的安装包（README 只指这一个文件），必须有。

### `src/contest_generator.egg-info/**` 摘出产品文件

- 它是 **pip 的构建产物**（盘上 6 件与完整包清单 sha256 全等、由 `pip install -e .` 现写），
  与 `__pycache__` / `*.pyc` 同类。实测它**每个完整包都发、每个小发版包都不发**
  （v1.1.1 / v1.2.0 / v1.2.1 三版一致）——正是「盘面与全新安装一致」这条判据咬的那类落差。
- 修法 = 判据单源加一条目录名跳过规则（`.egg-info` 后缀的目录名），与既有
  `__pycache__` / `revise-backups` 同列；两个打包器自动同时生效（都问 `product_file_reason`）。
- **副作用是有意的**：升级用户的盘上那 6 件会被删除清单点名删掉（旧更新器照单执行），
  下次 `pip install -e .` 或换 `.venv` 时 pip 自行重建。这是「不再分发构建产物」的必然代价。

### 真机 drill-01 的偏离记账

- `.scratch/verify-gate-drills/drill-01-upgrade.py` **一字不改**（照 B2 那轮对 drill-02 的纪律）：
  它的 `TARGET_VERSION` / `PACK_DIR` 是模块级常量，指向 v1.2.1。
- 另写包装脚本（落在本特性目录）用 `runpy` 起同一支 drill，只在运行前覆盖那两处**参数**，
  并把偏离**显式写进证据**。判据本体（`not_in_official == 0` 等）一个字不动。
- 起点必须先还原：`python .scratch\update-restart-stale-service\rebuild-sandbox-v111.py --write`
  （沙箱现停在 v1.2.1，那是上一轮离线演练留下的）。
- **禁用「把 `__init__.py` 改回旧版本号」那一招**（2026-09-19 实测：版本号回去了、代码还是新的，
  更新器会正确停服、这条修复会在「一行都没写」的情况下也变绿）。

### 沙箱资料库基线

- 沙箱仍停在 v1.1.1 时代的资料库状态（无 `.materials-manifest.json`），「资料库更新」永远报
  `baseline-missing`。补基线的判据与真身同一套（与本机 `sources/materials` 逐文件 sha256 对比
  全等才写），工具根 → 沙箱工具根、数据目录零触碰。
- **时机**：drill-01 跑完、沙箱升到 v1.2.2 之后再做——写进去的基线版本要与盘上一致，
  否则会把「本地旧、基线新」的假差异做进沙箱。

### 验收（三层，缺一不可）

- **本机静态**：`tests/test_full_pack.py` / `tests/test_pack_update.py` 既有守卫全绿；
  egg-info 的真值表 + 反向注入探针（把跳过规则拿掉 → 对应用例必须转红）。
- **发版闸门**：`powershell -File tools\preflight.ps1` 全绿（三处版本号 / 母版编码钉 /
  下载文档 / README 版本行），打包后对一次「zip 实算 vs `sha256.txt`」。
- **真机**：还原沙箱到真 v1.1.1 → 走产品端点真下线上 v1.2.2 小发版包 → 替换 → 重启，
  判据 = `not_in_official == 0`（盘上不存在完整包不会给的产品文件）+ 起点/终点版本自证 +
  四条隔离判据（真身数据目录 mtime / updates 条目 / 工作树 tree_stamp）+ 8020 收尾释放。

## 测试决策

- **好测试**：只断言外部可观察量——「某路径算不算产品文件」「清单里有哪些路径」「盘上最终
  多出了哪些文件」。不断言实现细节。
- **接缝**（沿用既有，不新造）：egg-info 判据加进 `tests/test_full_pack.py` 的
  `test_product_file_predicate_is_the_single_source` 真值表（同族判据里加格，不新开文件）。
- **既有守卫一个都不许动**：`tests/test_pack_update.py` 的跨包逐字节一致性、
  `tests/test_full_pack.py` 的路径预算与清单形态、`tests/test_update_app.py` 的删除清单语义。
- **判据强度**（本仓纪律）：新守卫必须有反向注入（把跳过规则拿掉），注入后对应用例必须转红；
  探针照 `.scratch/update-orphan-files/probe-guard-strength.py` 先例（改坏 → 跑 → 复原 → 复核 sha256）。
- **演练脚本与原始证据**落在本特性目录，`.txt`/`.json` 各一份。

## 范围外

- **`identity-fields/06`（6 slug / 11 条硬件身份字段）不打进这一版**：验收项要的是
  「你买过的那件实物的购买/官方页」，实测（wiki 索引两轮穷举 + 立创商城 + 本轮 Web）
  仍核不出可核实页面；工单的裁决一明写「**不许为了清空缺口填占位链接**」。
  本轮只把现状与已排除候选记进台账，下次人工取源后再补。**它不阻塞 v1.2.2 发版。**
- 不做「更新器扫盘清理」（边界无法安全划定，`update-orphan-files` 的 spec 已否掉）。
- 不改网络类失败的无上限重试（与「内容不符封顶」是刻意保留的两半）。
- 不改 7z 完整包渠道 / 资料库增量包发布（本轮没有 `sources/materials` 增删改）。
- 不重写历史、不动 `.git` 体积。
- 不改母版 / 模块库 / 生成链路——本版只有打包器与下载链路的修复。

## 补充说明

### 这一版会改掉的两个「用户可见的小事实」

1. **升级用户的 `src/contest_generator.egg-info/` 会被删掉**（6 件）。它会被 `pip install -e .`
   重建；对 `start-app.bat`（`PYTHONPATH=src`）与 `.venv` 两种启动方式都无影响。
2. **`00-START-HERE.txt` 会第一次通过升级路径到达老用户手上**（v1.1.1 的用户此前永远拿不到）。
