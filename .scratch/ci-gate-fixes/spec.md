# spec — 修掉 v1.3.0 推上去才暴露的两条 CI 缺陷

> 上游：`docs/agents/local-environment.md` 第 0 节「本机网络事实」段所在的那一轮收尾
> ——v1.3.0 发出后 CI（run `36154463953`，head `606494b1`）在 **windows-latest 两条腿**
> 上红：`浏览器门禁` 与 `全套 pytest` 的**前端门禁 step**。上一次绿的 run 是 `b96a9f4a`
> （v1.2.2 那轮），当时 CI **只有 2 个 job**——`ui-dom-contract-gate/03` 之后新增的
> 浏览器门禁 job 与前端门禁 step **从未在 CI 上真跑过**（那之后 main 一直没推）。

## 问题陈述

维护者视角：v1.3.0 发布是成功的（八件资产 / Release / tag 都已核实），但**仓库 CI 是红的**。
两条腿都红，而**本机推之前的闸门是全绿的**——这正是最坏的一类红：闸门给了虚假的安心。

更糟的是，这两条红**都不是产品代码坏了**，而是「本机环境替 CI 兜了底」：

1. **浏览器门禁**：测试夹具在干净机器上找不到模块库。夹具 `spawn` 的是裸
   `python -m contest_generator.webapp`，而该进程只从 `~/.contest_generator/config.json`
   取模块库目录。开发机上那份配置指到 `Desktop\firstep\library`，于是本机全绿；
   CI runner 上没有那份配置 → 库解析不出来 → `POST /api/bindings/matrix` 返回
   **400 `未配置 AI API`**。而夹具的「端点哨兵」只看 `resp.ok`，把 400 读成
   「端口上有个旧后端」，于是**如实**报出 `端口 N 上已有一个不进贡新版端点的服务（旧后端？）`
   并杀掉自己刚起的后端（`[fixture] 后端进程退出 code=1`）。
2. **前端门禁**：CI 的 windows 腿用默认 `core.autocrlf=true` 检出，而 `.gitattributes`
   只声明了 `.githooks/*`（LF）与 `*.bat`（CRLF），**其余文件没有口径** → `static/js` 与
   `tests/js` 整片 CRLF。有两条断言拿 **`\n` 当锚点**，遇到 CRLF 就不匹配
   （本机干净 clone 实测 **1794 passed / 2 fail**）。

维护者视角的真实损失：**一个「CI 全绿」的假象被带进了发布流程**——`prepush.py` 只跑得出
本机的事实，而本机恰好不具备 CI 的两个前提（没有 `~/.contest_generator` 的真实缺省、
不是 CRLF 检出）。

## 方案

三件事，先让 CI 能真跑，再修产品侧的根，最后把断言写成对换行不敏感：

- **A2（产品）**：让「从一份干净检出直接起服务」时**库的位置**自己就能定出来。配置文件**缺失**时，
  不再一律报「未配置」，而是回退到**随包/随检出的库根**（判据复用既有单源 `tool_root.find_tool_root`
  ——`install.bat` 给用户配的就是这一份，`wordlist.py` 也用它）。同时给一个**显式的配置路径
  覆盖口**（环境变量），让夹具 / CI / 高级用户能指到自己的配置，而不必伪造 `HOME`。
  > **实测边界（2026-09-25，落地时量准，spec 原话写大了，按实测收窄）**：库的**位置**认得出来 ≠
  > 库**浏览得了**——库相关的只读端点（`/api/modules` 等四件）与另外 42 处共用 `_require_config`
  > 那道「先配 API」的闸，空 key 下仍答 400（四件实测全 400）。所以用户可观察的结果是
  > **「设置页报出的是随包库路径、AI 面如实说未配置」**；「没配 key 也能浏览库」是**既有**的
  > 产品缺口，另立 `issues/04`，**不在本 spec 射程**。
- **A1（夹具）**：浏览器门禁夹具起后端时喂一份**指向检出内库**的配置，让这个 job 在干净机器上
  真能跑起来（不再依赖开发机的 `~/.contest_generator`）。
- **B（断言）**：把那两条拿 `\n` 当锚点的断言改成对 CRLF 不敏感——照本仓**已有口径**
  （`tests/js/tab-register-guard.test.mjs:276` 的原话：「锚点用**不含缩进与换行**的子串
  ——带 `\n` 的锚点会静默不落上，第一版就是这么假红的」）。

用户可观察的结果：CI 在 windows-latest 上两条腿都绿；把仓库 clone 到一台**没有任何
`~/.contest_generator`** 的机器上，直接起服务就能用库（不再报「未配置」）。
**v1.3.0 的发布产物不受影响**（八件资产 / Release / tag 均已核实），本 spec 不动已发出的包。

## 用户故事

1. 作为维护者，我想推完一眼看到 CI 全绿，以便不必自己去分辨「红的是产品还是环境」。
2. 作为维护者，我想本机闸门与 CI 的判据一致，以便「推之前全绿」真的意味着「推之后绿」。
3. 作为维护者，我想浏览器门禁在干净 runner 上真能跑，以便它不再是一道从没生效过的门。
4. 作为新接手的人，我想把仓库 clone 到新机器上就直接能起服务，以便不必先猜
   「为什么说我没配置 AI」——库随软件分发（ADR 0008），起服务就该能看见库。
5. 作为维护者，我想夹具不读开发机的真实用户目录，以便验收结果与「这台机器上装过什么」解耦。
6. 作为维护者，我想断言对检出换行不敏感，以便 `core.autocrlf` 的差异不再制造假红。
7. 作为维护者，我想这次修完顺手把 `local-environment` 里那条「已知本地/CI 落差」更正掉，
   以便下一轮不必重新推一遍这两条红。

## 实现决策

- **库根判据复用既有单源**：不新造「仓库根」推导。`tool_root.find_tool_root` 已是唯一出处
  （`wordlist.py` / `changelog.py` / `materials_update.py` / `webapp.py` 都引它）；
  随包库根 = `<工具根>/library/modules` 与 `<工具根>/library/masters`，与 `install.bat`
  第 49 行传给 `write_bootstrap_config` 的是**同一对路径**。
- **回退只在「配置缺失」时发生**：配置存在就一律按配置走（用户写了什么就是什么，不静默覆盖）；
  配置存在但 `api_key` 空仍然报「未配置 AI API」（那是 `install.bat` 引导态的既有语义，
  本次不改）。**随包库不存在时**（站点包安装等）保持既有行为，不假装有库。
- **配置路径覆盖口**：新增环境变量（`FIRSTEP_CONFIG_PATH`）作为**显式**入口；
  缺省路径的解析从「导入期绑定」改成「调用期解析」，否则夹具在子进程里设的环境变量不生效。
  这是接口面变更，**默认参数语义要保持逐字节兼容**（现有调用方与测试都按原缺省走）。
- **夹具喂配置的方式**：写一份临时配置（指向检出内的 `library/modules` 与 `library/masters`），
  用上面的环境变量指过去。**不伪造 `HOME` / `USERPROFILE`**——那会连带改掉夹具与产品的
  其它路径推导（数据目录、最近工程等），把一个显式契约换成全局副作用。
- **夹具的哨兵判据不动**：它这次报的是**真话**（后端确实答不出那个较新端点）。修的是让它
  在干净机器上能起来。**不把哨兵改成「只看健康检查」**——那会把这道门重新变瞎
  （`gen-chain-audit/06` 立它就是为此：旧实现只看健康检查，结果整轮验收跑在旧后端上）。
- **断言改法照既有口径**：锚点避开换行（用单行子串 / `[\s\S]` / `\r?\n`）。
  **不用 `.gitattributes` 全局 `* text=auto eol=lf` 一刀切**——那会牵动 1871 个库文件与母版
  （含 `library/hwcheck_recipes.json` 那条 LF 纪律），是另一个量级、另一条账。
- **顺序**：A2 是 A1 的接口前提（A1 要用那个环境变量），故 A2 排 `01`、A1 排 `02`；
  B 与两者无依赖，独立成 `03`。

## 测试决策

- **最高既有缝优先**，三处都不新造测试框架：
  - **A2**：`tests/test_config.py`（已有 `load_config` 缺文件 / 坏 JSON / 缺字段的用例族）
    ——新增「配置缺失 + 随包库在场 → 用随包库」「随包库不在 → 仍报原错」「环境变量指到
    另一份配置 → 读那一份」三条；判据只测**外部行为**（返回的 `AppConfig` 字段），
    不测内部推导过程。
  - **A1**：`tests/browser/server.mjs` 是夹具，判据落在**它自己的孩子进程真能答出哨兵端点**上
    ——即这次红的那条路本身（真起后端 + 打 `/api/bindings/matrix`）。**复现口径**：
    把 `USERPROFILE`/`HOME` 指到空目录（模拟 CI runner），夹具必须仍起得来。
  - **B**：`node --test "tests/js/*.test.mjs"`，判据 = **CRLF 检出下全绿**。本机复现口径
    = 干净 clone（`core.autocrlf=true`，实测 1794/2 fail）；修完同一 clone 必须
    **1796 passed / 0 fail**。这是**反向验证**（先让它可以红，再让它绿）——不是只跑一遍绿。
- **本机预检**：CI 的 windows 腿用默认 `autocrlf`，故 B 的判据必须在 CRLF 检出下成立；
  LF 检出（本工作树）同样要绿——两个方向都要跑。
- **端到端**：浏览器门禁整支（5 spec / 42 用例）在**空 HOME** 下跑一遍，
  这是 A1 的真判据（本机现在能跑，是因为有 `~/.contest_generator`）。

## 补充说明

### 这两条红为什么能一路活到发布

- 浏览器门禁 job 是 `ui-dom-contract-gate/03` 加的，**加完就没推过 main**（那之后到 v1.3.0
  之间 main 一直没推），所以它一次都没在 CI 上跑过；本机跑它是绿的（有配置），
  于是「本机绿」被当成了「这道门有效」。
- 前端门禁 step 同理：`module-hwcheck/01` 加进 ci.yml 时也在同一次「没推 main」的窗口里。
  本条 B 的两条假红**早被写在 `local-environment` 里**（2026-09-21 那条
  「`core.autocrlf=true` 时 CRLF 检出下这两条必红」），**只是没人回头修**。
- 教训（写进账本）：**新加一道门之后必须真推一次让它跑起来**，否则「门存在」与
  「门生效」是两件事；本机绿证明不了 CI 绿，因为 CI 的缺省环境与本机不同。
