# 11 — 夹具清器件集的 10 秒等待在 CI 上会超时：`clearDevices()` 派发的事件会落在被重绘换掉的节点上

**要做什么：** 让 `tests/browser/hwcheck.spec.mjs` 的 `clearDevices()` 在**慢机器**上也能真的清干净
——不是把超时调大糊过去，而是认出真正的机制：器件集每次变化都会 `box.innerHTML = …` **整块重绘**，
派发在旧 chip 上的 `click` 会连同那个节点一起被丢掉（白点一次），于是"等 10 秒仍不空"。

**被谁阻塞：** 无——可立即开始。

**状态：** resolved

- [x] 定性：CI 上每次跑都能看到 `[afterEach] 器件集未清干净：page.waitForFunction: Timeout 10000ms exceeded.`
      （本机偶发、CI 常发）；run `36218384073` 里它第一次**从 afterEach 冒到用例体内**——
      `:1046` 那处 `await clearDevices()`（用例自己的前置清理）没被 try 包住，于是整条
      `检测页 → 生成页` 用例红（12.4 秒，10 秒等待 + 2.4 秒派发）。**同一条用例在上一次
      CI run 里是绿的** → 是偶发，不是功能坏。
- [x] 改法：**重试派发**（最多 5 轮，每轮 10 秒等待）：派发 → 等空 → 还空不了就**再派发一次**。
      这样"事件落在被重绘丢掉的节点上"这一类就被下一轮补上；真清不干净（连续 5 轮）仍然
      **大声抛错**——判据没被削弱，只是把"白点一次"从必然失败变成可重试。
- [x] 反向验证：本机（快机器）行为不变（该 spec 42 条仍全绿）；
      **且真清不干净时仍会抛**（连续 5 轮都空不了才会走到那句 throw，逻辑上不可能静默变绿：
      调用方 `:1046` 与 afterEach 都还按"抛了就红/就记一行"处理）。

### 为什么不是"把超时调大"

调大只把"什么时候撞"往后推（CI 的负载是别人的机器说了算）；真正吃得住的是**重试**：
这条重绘竞态是产品的既定行为（`innerHTML` 全量重绘，见文件头那段"chip 容器每次选择变化后
被整体重绘"），派发式点击本来就该容忍它。判据没动：清不干净照样抛。
