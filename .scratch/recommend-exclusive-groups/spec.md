# recommend-exclusive-groups：同功能模块「功能组选择卡」（2024H 推荐 bug 修复）

> 2026-08-21 用户口头定稿方向（原话：「把选择题抛给用户，对每个重复的模块都进行
> 描述然后让用户从这些模块中选择」）；组范围与陀螺仪处理经两轮 ask_user_question
> 确认（均选推荐项）。

## 问题陈述

跑 2024H AI 推荐（MSPM0）时出现两个真实问题：

1. **重复推荐**：AI 同时推荐了 `pid` 与 `xunji`——两者都是同一颗 8 路灰度传感器的
   驱动（引脚同为 PA22/PA23/PA24/PA25/PA26/PA27/PB6/PB7），配置引脚页出现两份
   相同的 8 路灰度配置，用户被重复选择困扰。
2. **漏推荐**：2024H 直线段（AB/CD）无引导线（题面说明：「行驶场地上不得有其他
   任何指示标记」），直线行驶必须靠航向保持（陀螺仪/姿态），但 AI 没推荐任何
   姿态模块（库内 `imu_uart`、`ml_mpu6050` 均没被命中）——虽然系统提示词已有
   「无引导线 → 航向保持」规则（2024H 复盘加入），实测模型仍漏。

## 方案

引入 **「功能组（互斥组）选择卡」**：同种功能 / 同一硬件上的多个模块在功能上
互斥（选一个就够，选多个 = 同功能重复配置），系统不再替用户自动去重，而是把
这些模块组织为一个功能组，**推荐结果里以一张选择卡呈现**：组内每个成员带差异
定位描述（接口 / 控制方式 / 真机先例），由用户选定这题用哪个。用户可换选、可
全部不选（不强制，用户拥有最终选择权）。

首批登记的功能组（mspm0）：

| 组 id | 组名 | 成员 | 差异定位（role 初稿） |
| --- | --- | --- | --- |
| `gray-track` | 8 路灰度传感器驱动（三选一） | `huidu` | 仅 8 路灰度读取，不含巡线核心（适合自写巡线逻辑） |
| | | `pid` | 灰度读取 + 边缘中点偏差 + PID 巡线 + 编码器速度环（双平台，滚球线移植） |
| | | `xunji` | 灰度读取（位图）+ 加权质心巡线 + 编码器采样（开环，2024H 真机验证） |
| `attitude-hold` | 航向保持 / 姿态传感器（二选一） | `imu_uart` | UART 串口陀螺仪（9 字节帧 CRC16，yaw 直出，接 PA28/PA31） |
| | | `ml_mpu6050` | I2C + DMP 官方姿态解算（pitch/roll/yaw，接 PA0/PA1，MPU6050 kit） |

stm32 侧：`gray-track` 只有 pid（huidu 无 stm32 条目 / xunji 仅 mspm0）→ 单成员
组不显示选择卡，行为与现状一致；`attitude-hold` 成员按平台条目过滤。

陀螺仪补漏采用**双保险**：①提示词强化（用户消息段「题面核查」条 + 模块摘要行
组标注——教训先例：只改系统提示词会被用户消息尾句盖过）；②**确定性兜底**：
赛题 manifest 可声明 `hint_module_groups`（组 id 清单，2024H 声明 `attitude-hold`）
→ 即使 AI 没命中该组，done 载荷**无条件出卡**（卡上标注「AI 未推荐，题面疑似
需要——请确认」，无默认选中），用户自己确认要不要。题面需要但 AI 漏了的失败
模式从「静默缺失」变成「一个待确认的选择卡」。

## 用户故事

1. 作为学生，2024H 推荐完成后，灰度驱动只出现在一张「8 路灰度传感器驱动（三选一）」
   选择卡里，而不是两个一模一样 8 路灰度芯片。
2. 作为学生，选择卡里每个成员有差异描述（纯读取 / PID 闭环 / 质心开环），我一看
   就知道选哪个、差在哪。
3. 作为学生，我点选卡里另一个成员时，已选模块自动换掉旧成员（不叠加、不出现
   两份灰度配置），生成请求只带我选的那一个。
4. 作为学生，我把卡里当前选中项再点一次 = 取消整组（这题我不用灰度/不用陀螺仪），
   系统不强制我选。
5. 作为学生，AI 推荐了两个同组成员时，默认只勾选 AI 推荐的第一个，另一个以
   「AI 推荐」徽标列在卡里（推荐理由可见），我随时可换。
6. 作为学生，AI 没推荐任何姿态模块但题面疑似需要（2024H 无引导线直线段）时，
   航向保持选择卡仍会显示，并标注「AI 未推荐，题面疑似需要——请确认」，我确认
   后选择一个姿态模块（imu_uart 或 ml_mpu6050）。
7. 作为学生，功能组内模块的推荐理由是「按需求句」展示的（该组需求句仍列在
   需求清单里，组卡不吞掉需求层面的可见性）。
8. 作为学生，我手动在模块库同时加进同组两个成员（如 pid + xunji）时，已选列表
   出现黄字警告（同属一组共用同一硬件，建议只留一个），但系统不拦我。
9. 作为学生，stm32 题推荐 pid 时行为不变（单成员组不出卡、chips 照旧）。
10. 作为维护者，manifest 里给模块写 `exclusive_group`（id + label + role）即完成
    登记，推荐 / 前端 / 提示词 / 缓存失效全部自动生效，不加其他配置。
11. 作为维护者，同组 id 的 label 不一致 / role 缺失时库校验报错（与多实例同款
    严格口径），不静默。
12. 作为维护者，模块库有变（组字段改了）时推荐缓存自动失效（组标注进摘要行，
    指纹已覆盖）。
13. 作为维护者，旧推荐缓存 / 旧版推荐结果（done 载荷无 `exclusive_groups`）前端
    正常渲染（无卡），不报错。
14. 作为学生，生成时选中的组内成员照常展开依赖、配引脚（选哪个用哪套引脚，
    不冲突不重复）。

## 实现决策

### 组声明（manifest 模块级，新增可选字段）

```json
"exclusive_group": {
  "id": "gray-track",        // 库内唯一组 id（跨模块相同 = 同组）
  "label": "8 路灰度传感器驱动",   // 组名（同组 id 的各模块 label 必须一致）
  "role": "灰度读取 + 质心巡线（开环，2024H 真机验证）"  // 本模块组内差异定位
}
```

- 缺省不落键 = 不属任何组（旧 manifest 兼容）。
- 校验（库加载时）：`exclusive_group` 为对象、三字段类型正确；同 id 的 label 逐字
  一致（不一致 = 库错误）；role 非空字符串；id 不与多实例字段冲突语义（无干系）。
- 投影：`ManifestSummary` 增 `exclusive_group: (id, label, role) | None`；
  `to_line()` 追加 `（同组互斥：<label>，组内仅选其一）`——摘要行变化自动使
  推荐缓存指纹（摘要行排序 hash）失效，无需额外处理。
- 组定义（id → 成员清单）由库加载时从 manifest 汇总得出：成员带平台过滤
  （该平台有条目才算成员），单平台成员数 ≤1 的组 = 无意义组（不出卡）。

### 推荐链路（后端）

- AI 输出契约**不变**（requirements/modules/suggestions/questions 照旧）——组是
  机器侧派生，不新增模型字段，无新解析风险。
- 派生纯函数：`build_exclusive_groups(selection_modules, group_defs, platform,
  *, hint_module_groups=())` → 命中组（成员 ∩ 推荐集非空）列表；每项 = {id,
  label, members:[{slug, role}], recommended:[命中的 slug 按成员登记序]}。
  `recommended` 为成员登记序（非 AI 推荐序）；AI 首选由 AI 原输出的
  `data.modules` 顺序决定（前端默认勾选取 `data.modules` 序，不依赖本字段）。
  done 载荷增：

```json
"exclusive_groups": [
  {"id": "gray-track", "label": "8 路灰度传感器驱动", "hint": false,
   "members": [{"slug": "huidu", "role": "…"}, {"slug": "pid", "role": "…"},
               {"slug": "xunji", "role": "…"}],
   "recommended": ["pid", "xunji"]}
]
```

- hint 兜底：topic manifest 增可选 `hint_module_groups: ["attitude-hold"]`（组 id
  清单）；`TopicEntry` 解析该字段（缺省空）。done 载荷对 hint 组**无条件出卡**
  （`hint: true`、`recommended` 可空、卡内无默认选中）。hint id 在库内无对应组 →
  静默忽略（不炸推荐）。
- 载荷只在「命中组或 hint 组」非空时落键（旧载荷 / 旧缓存逐字节兼容）。

### 提示词（用户消息段，尾句前 + 摘要行）

- 规则段（条件段：库内存在组时出段，与多实例规则段同款先例）：
  「同组互斥（硬约束）：清单带『同组互斥』标注的模块共用同一传感器/同一功能，
  同一题内**只推荐一个**；同组多个被推荐 = 配置页出现两份相同硬件配置（2024H
  复盘）。按题面择优推荐一个即可，同组其它候选由系统展示给用户选择。」
- 题面核查条（条件段：库内存在 attitude 类组时出段）：「无引导线/无其他指示
  标记/沿直线自主行驶 → 必须从『航向保持』组中推荐一个；漏推荐 = 直线段无法
  完成。」
- 预算：两段合计 X KB 内（工单 03 精确算，SELECT 预算余量约 8KB，够用；契约
  断言同步更新）。

### 前端（index.html）

- 推荐结果顶部（评分点面板后、需求清单前）渲染组卡区：每卡显示 label（hint 卡
  带「AI 未推荐，题面疑似需要——请确认」标注）；成员行 = radio + slug + role
  （+ 若为该成员推荐则带「AI 推荐」徽标与理由）。
- 默认选中 = 组内当前在 selectedSlugs 的成员（多个取第一个）；点击 radio →
  选中该成员并从 selectedSlugs 移除同组其他成员后加入它；再点已选成员 = 取消
  整组（从 selectedSlugs 移除）。
- autoAdd 去重：data.modules 逐个加入时，若该 slug 属某组且 selectedSlugs 已有
  同组任一成员 → 跳过（只保留首个推荐成员入集；AI 的其它同组推荐仅以徽标展示）。
- 需求清单 chips：r.modules 中属于某组的 slug 不再渲染成独立 chip（避免视觉
  重复），改为「该需求的组内成员已在『功能组选择』中」灰色小注；需求句/理由
  可见性保留。非组模块 chips 交互完全不变。
- renderSelected 兜底：selectedSlugs 同组 ≥2 成员 → 黄字警告条（同属一组共用
  同一硬件，建议只留一个）；不硬拦（用户选择权）。
- 旧载荷 / 旧缓存无 `exclusive_groups` → `|| []` 容错，渲染不变。

### 向后兼容

- 旧 manifest（无新字段）逐字节不变；旧缓存因摘要行指纹变化自动失效（组登记后
  首跑重新推荐一次，之后缓存恢复）。
- 单成员组 / 无组库（stm32 或未登记库）→ 无卡、无提示词段、无载荷键，行为
  与现状一致。

## 测试决策

- 后端纯函数（`build_exclusive_groups`）：命中组派生 / 平台成员过滤 / 单成员组
  不出卡 / hint 触发（hint 未命中出卡、hint id 未知静默忽略）。role 回退不需要
  ——工单 01 已强校验 role 非空（spec:92），成员必然带 role。
- 库校验：同 id label 不一致报错、字段类型错报错、缺省兼容（新单测文件）。
- 提示词契约：用户消息段含「同组互斥」「航向保持」核查条（库有组时）；契约
  预算断言更新（新增段字节计入最坏形态）。
- done 载荷契约：命中组 / hint 卡形状（含旧无组库不落键）。
- 前端：tests/js/*.test.mjs 既有先例形态——组卡渲染（radio/徽标/role）、autoAdd
  去重、换选 swap、取消、同组多选警告。
- 端到端验收（工单 05）：真跑 2024H 推荐（MSPM0）——①不再出现双 8 路灰度配置
  （pid/xunji 只一个进 selectedSlugs）；②航向保持卡出现（AI 命中或 hint 兜底）；
  ③换选 xunji 后展开/引脚无重复；④stm32 出题回归无组卡。

## 范围外

- 生成/展开侧硬门禁（同组多选报 400）——前端警告即可，用户拥有选择权；
- 其他潜在同功能组登记（beep/key/电机等，机制通用留扩展口）；
- 模块库 UI（add_module 表单）新增组字段编辑器——manifest 手工编辑 + 库校验
  兜底即可；
- 组卡「默认选中 AI 首个推荐」的推荐顺序优化（组内择优规则）——提示词引导，
  不做排序算法。

## 补充说明

- 真机事实：2024H 真机用 JY61P 类 UART 陀螺仪（`extern float Yaw`，control.c
  直行用 yaw 修正），MPU6050 仅 syscfg 残留；但库内 `imu_uart` 帧协议为
  `0A 03 04` 9 字节帧 + CRC16（IMU601 类新 IMU 器件），与真机 JY61P 的
  `0x55 0x53` 协议**不同**——role 文案按库内实现如实写，不冒称真机先例。
- 竞态教训沿用：并行工单各自独立 worktree，提示词给文件边界。
