# spec — webapp 收口（检测页装配回域 + LLM 工作流观测一处）

## 问题陈述

`webapp.py` 是全仓最热的文件：近 300 次提交里它被改 19 次，近 40 次里 9 次——**几乎每张功能
工单都要穿过它**。它只有一个函数 `create_app`，里面装着 140 个闭包 handler；一个 handler
真正依赖什么，读签名读不出来（context 靠词法捕获）。

两处具体的重复，各有一个真实代价：

1. **检测页（硬件检测栏目）的三块装配住在 webapp 里**（引脚消解 + 板侧投影 + 逐件小节 +
   兼容降级 + 互斥组，约 483 行）。这些装配的判据来源全都是 hwcheck 族域模块，却因为住在
   路由里只能经 `create_app + TestClient` 端到端测——域层没有直接缝；而且每张 hwcheck
   工单（04/05/06/07/08/09 与引脚出口单）都要改 webapp.py，最热的文件被最活跃的栏目反复穿过。
2. **「预算 + 观测收集器 + 客户端派发」三件套在 20 个路由里逐字重复**（另有 5 处视觉工作流
   重复「收集器 + 结算」半套）。这三件事必须**一起**做对：预算要跨同一趟工作流的多次派发
   共享（否则重试预算各算各的）、收集器要能被 `bind_llm_telemetry` 挂上（否则 SSE 面板没有
   实时遥测）、退出时要结算进 `recent_llm_workflows`（否则观察面板看不见这一轮）。漏一样
   不会报错，只是行为悄悄变差——正是"写得出来但要读 30 行才知道"的那类重复。

## 方案

两件事，HTTP 面一个字节不动：

1. **检测页装配搬回它的域模块**，接口从 `AppContext` 收成**显式路径 + 配置对象**：路径进、
   载荷出。webapp 侧只剩「取配置（400 文案单源）→ 调域函数 → 组响应」。
2. **25 处工作流观测收成一个缝**：`_llm_run(context, workflow)` 造出的观测单元持有预算与
   收集器；`.llm()` 每次取用按既有契约现派发客户端；`with` 退出即结算观测。视觉工作流只用
   它的收集器，不造模型。

**不做 route 分册**（把 140 个 handler 拆成 `routes/*.py`）——见「范围外」。

## 用户故事

1. 作为维护者，我想让检测页装配住进 hwcheck 族域模块，以便改检测页不必动 webapp 这个热点。
2. 作为维护者，我想让「检测页一次投影」有直接测试缝（不必起 TestClient），以便按输入 /
   输出断言板块载荷。
3. 作为维护者，我想让检测页装配只吃显式路径与配置对象（不吃 AppContext），以便域函数不
   依赖 HTTP 层的状态容器。
4. 作为维护者，我想让 webapp 不再 import 只为检测页装配而存在的域原语，以便 import 面自己
   说清「这一层只管 HTTP」。
5. 作为维护者，我想让「预算 + 收集器 + 派发 + 结算」只写一次，以便新增路由时不可能漏掉其
   中一件。
6. 作为维护者，我想让这条不变量有结构守卫钉住（并配可复现的红证），以便三件套不会再长回来。
7. 作为用户 / 维护者，我想让这次收口行为零变化——端点路径、SSE 事件序列、载荷键、观测面板
   的记录条数与先后、400/409/502 的错误码与中文文案全不变，以便当天合入。
8. 作为测试维护者，我想让既有的 LLM 工厂契约用例（同一趟工作流的多次派发共享同一个预算与
   收集器）继续成立，以便不把「收口」做成悄悄改语义。

## 实现决策

### 一、检测页装配回域

- **落点按职责分**：检测页一次投影（`hwcheck_view`）与母版 syscfg 读取（引脚消解的输入）
  归 **`hwcheck_board`**——板侧投影 / 同脚冲突 / 引脚消解本来就是它的职责，它已有一个
  「路由侧入口」`hwcheck_board_view_for` 的同款形状；配方装载（库 + 母版头 → 接口清单 →
  `load_recipes`）与小节载荷投影归 **`hwcheck_recipe`**——`SECTION_TAG`、`interface_names`、
  `platform_header_names`、`load_recipes` 都是它的所有物。
- **`hwcheck.py` 不动**：它的既有边界是「纯函数、不碰盘」（模块 docstring 明写），而这次搬的
  三块都要读盘（库 / 母版 / 配方文件）。搬进去会破坏那条边界，收益为零。
- **接口形状**：`hwcheck_view(config, *, module_library_dir, masters_dir, recipe_path=None,
  require_pins=True) -> HwCheckView`。**AppContext 不再出现在域层**；`recipe_path` 是为
  测试注入坏配方留的既有覆盖点（原 `AppContext.hwcheck_recipe_path`）。
- **返回值收成 dataclass**（`HwCheckView`：`board` / `sections` / `generic` / `pin_bindings`
  / `known_slugs`）。理由：这五个是不同的东西（载荷字典 / 域对象 / 域对象 / 绑定增量 / 库
  slug 词表），住在一个 dict 里只能靠 docstring 说清；具名字段让 typo 当场 `AttributeError`，
  与仓库既有惯例一致（`HwCheckBoardView` / `HwCheckPinPlan` / `ChecklistItem` / `TriageFacts`）。
- **`board` 那六个键的载荷形状逐字不变**（前端零改动）。
- **不要薄适配层**：四个端点自己调 `_hwcheck_library_config(context)` 拿 AppConfig，再直调域
  函数。`_hwcheck_library_config` 留在 webapp——它是「AppContext → 配置」这一层的翻译，400
  文案单源，不属于检测页装配。
- **错误时机与顺序逐字保持**：`_hwcheck_library_config` 的 400 在各端点里的**触发位置不变**
  （平台 / payload 校验仍在它之前，回读端点的「不是检测工程」判定仍在它之前；生成端点本来
  就先取配置）。
- **配置缺失时不给半张接线表**：既有语义（库路径缺失 = 400 中文，不降级）照旧，只是这句
  400 现在由各端点显式取配置时抛。

### 二、LLM 工作流观测一处

- **一个缝**：`LLMRun(context, workflow)`（类落 webapp.py，紧邻既有的 `_llm`）。它建预算与
  观测收集器；`.llm()` 现派发客户端；`.settle()` 结算进 `context.recent_llm_workflows`。
  *（实施记录：原计划是一个 `_llm_run` 工厂 + `with` 退出结算；实现时收敛为「直接构造 +
  显式 `settle()`」——25 处调用点每一处本来就有明确的结算位置（22 处在 `finally`、3 处紧随
  其后），再养一个 `with` 写法就是同一件事的第二套惯用法；`_llm_run` 那层纯转发的工厂也被
  评审判为 Middle Man 删掉了。）*
- **派发语义逐字保持**：`.llm()` 是**方法**、**每次调用现派发**（不缓存），与从前每处的
  `_llm(context, budget, collector)` 逐字等价——「同一趟工作流的多次派发共享同一个预算与
  收集器」这条既有契约被 `tests/test_webapp.py` 的 skeleton / recommend 两条用例钉着
  （断言工厂被调用 ≥2 次且两次拿到同一个 budget / collector 对象），收口不许改它。
- **视觉工作流不造模型**：缝的对象只在 `.llm()` 被调用时才走工厂，所以 5 处只做视觉观测的
  工作流（上传抽取 ×2 / 拆条 / 取题面补图注 / 推荐里的按需视觉问答）只用 `run.collector`，
  零多余派发。这是它们能并进同一个缝的前提。
- **结算单源**：`recent_llm_workflows.add_completed` 只在 `settle()` 里出现一次。
  `settle()` **幂等**（重复调用只记一条）。
- **推荐路由的结算顺序逐字保持**：主流观测与「按需视觉问答」观测的结算先后（先主流、
  后视觉）与异常路径（正文抛错时两者**都**要结算，今天由 `finally` 保证）都不变。
- **`_llm(context)` 的 7 处裸调用不动**：它们不重复三件套（单次调用、无观测需求），
  `_llm` 的工厂兼容面（1 / 2 / 3 参数工厂派发）也一字不动。
- **结构守卫**：新增一条断言「收集器创建 / 预算创建 / 客户端派发 / 结算」**各恰好一处**
  （按**每一个调用点**数，不按所在函数去重）、且都落在缝内。判据写成纯函数（吃源码文本 →
  调用点清单），既作用在真源码上，也能在**合成片段**上复现红——红证不靠手改仓库文件。

## 测试决策

- **测试面一（检测页，新缝）**：`hwcheck_view` 直测，不经 HTTP——真库 + 真母版（本仓
  `library/`）与假库两种输入；断言 `HwCheckView` 五个字段、`board` **五**键齐全、`require_pins
  =False` 不因装不下 400、坏配方仍大声失败、库外 slug 仍 400。先例：`test_hwcheck_board.py` /
  `test_hwcheck_recipe.py` 的域层直测。
- **测试面二（观测缝，新缝）**：`LLMRun` 直测——3 参数工厂收到共享的预算与收集器；1 参数
  工厂不炸（既有兼容面）；不调 `.llm()` 则零派发（视觉路径）；`settle()` 结算且幂等；零调用
  不记（`add_completed` 既有语义）。**路由面上的两条**（单源缝盖不到的部分）走既有夹具：
  视觉抽取端点全程不派发工厂；推荐路由的主流 / 视觉两条观测都结算且顺序不变（含正文抛错
  的异常路径）。
- **行为零变化的裁决者是既有用例**：`tests/test_hwcheck*.py`（检测页端点全量）与
  `tests/test_webapp.py`（含上面两条工厂契约用例、SSE 事件序列、`recent_llm_workflows`
  观察面板那条）必须全绿且**不需要改判据**。若某条既有用例必须改，就说明收口改到了语义，
  回头改实现——这条写进工单验收。
- **不做**：不写「某个私有函数不见了」这类实现细节断言（只在两条结构钉上钉 import 面与
  单源不变量，那正是本单要守的东西）。

## 范围外

- **route 分册**（`routes/hwcheck.py` 等按领域分册、`register(app, ctx)`）：不做。① 那是整理
  不是收口；② `tests/test_webapp.py` 里那条结构守卫按**源码文本**钉 recommend 路由「恰好
  一个函数且体内无编排调用」（AST 解析 webapp.py），分册会把它判红——那是守卫形状的问题，
  正确的改法是先把守卫换成「按注册名唯一 + 行数上限」，属于另一条工单。
- **`create_app` 内部的其它重复**：校验类重复（94/140）不在本轮；`add_completed` 之外的横切
  （`@_map_errors` / SSE 运行器）已经收好了，不动。
- **`AppContext` 的进程级状态搬移**（评审候选 C6 的另一半）、**C7 的私有符号公开化**：不在本单。
- 不动前端 / 端点路径 / 载荷键 / 事件名 / `_llm` 的工厂兼容面 / `hwcheck.py` 的纯函数边界。

## 补充说明

- **来源**：架构评审（2026-09-20 报告，候选 C2「给 create_app 内部画缝」）。复审结论把它排在
  「该做的只有两件半」的第 1 件——近 40 次提交里 webapp.py 与 index.html 各被改 9 次且两两
  同现，每个功能工单都要穿过这两个文件；同批第 2 件（前端装载清单去化石）已由
  `frontend-import-fossils/01` 落地。
- **本单同时是评审候选 C7 的验收尺**：那条候选的判据是「私有符号被测试翻墙的条数趋于 0」。
  本单之后检测页测试可以走域入口（新缝是公开面），`tests/` 对 webapp 私有名的依赖只许减
  不许增。
- **命名纪律**：本仓库「装配」指「读库 / 读母版 → 拼出一个载荷」这类域内工作，与「编排」
  （域判决 + 事件序列，如 `run_recommendation`）不是一回事；本单只搬装配，不搬编排。
- 证据落点：`.scratch/webapp-consolidation/`（探针 / 红证 / 前后对照）。
