# spec — 不可重试的校验失败不该留下整卷半成品

> 缺陷单：`issues/01-nonretryable-verify-leaves-partial.md`（发现于沙箱真机演练 B2 场景三，
> `sandbox-drill/02`）。证据：`.scratch/verify-gate-drills/verify-02-degraded.{txt,json}`
> 的 `scenarios.verify-size`。

## 问题陈述

用户在完整包更新里撞上**不可重试**的校验失败（清单声明的卷大小与服务器实际总长互相矛盾——
「发布物不一致」）时，工具给的行为大部分是对的：终态 `failed`、不重试、中文话术指明不一致、
`updating.lock` 与 `pending-update.json` 都没留下、旧版本照常可用。

**唯一不对的是盘面**：`updates/full/` 里留下**整卷半成品**（真机实测 3,961,701 字节）与它的
`.partial.json` 边车。而 spec（`.scratch/resumable-download/spec.md` 第 147 行）明文写着
「成功 / **校验失败**时一并删除边车与半成品，不留孤儿」。

代价不是洁癖：线上完整包 765 MB/卷 → 用户看到「失败」之后 `updates/full/` 里白占 **~765 MB**；
磁盘不宽裕的机器上，这直接影响他能不能重下（完整包换装前的磁盘预检正是拿这附近的余量算的）。
它**会**自愈（下次点重试时本地那份长度 > 清单声明 → 服务器回 416 → 下载器就地清掉重下），
但用户不点重试它就一直在。

## 方案

**把「这半成品留着还是清掉」这条分界接到既有分类上，接在任务层的失败分支上。**

- 拿到下载域抛出的异常时，任务层现在一律「留着当断点」；改成先问一次既有单源分类：
  - `error_kind == "verify"` 且**不可重试** → 这份重下也不会有变化 → **清掉半成品与边车**；
  - 其余一律维持现状（**网络失败必须留断点**——那是可续下载的立身之本，spec 第 145 行）。
- 判据只用既有的两个纯函数（分类与可重试性），**不新增第三张表**；也不解析异常文案。
- 事件顺序不变：异常照旧如实上抛，任务层照旧转 `failed` + 中文 `error`；只是清完再抛。

用户可观察的结果：不可重试的校验失败之后，`updates/full/` 是空的——「失败」不再意味着
「盘上多躺一份整卷垃圾」。

## 用户故事

1. 作为撞上「发布物与清单不一致」的用户，我希望失败之后不留下一整卷几百 MB 的残骸，
   以便我的磁盘不会被一次失败悄悄吃掉几 GB。
2. 作为同一台机器上还要重试的用户，我希望失败态是干净的，以便下次点重试时不会先撞上
   「本地那份比清单声明还大」这类二次噪音。
3. 作为网络断线后重试的用户，我希望**断点还在**（这是可续下载的全部意义），
   以便我不必从 0 重下 765 MB。
4. 作为用户点了取消的用户，我希望取消**不**触发清理，以便我下次能接着下。
5. 作为维护者，我希望这条分界只用既有的分类单源（`error_kind` / `is_retryable`），
   以便「哪种错误该留断点」永远只有一个答案。
6. 作为维护者，我希望这条修复有单测 + 反向注入探针 + 真机复跑，以便不会在下次改下载链时
   被悄悄改回去（它踩的正是「失败一律留断点」这条过宽的分支）。
7. 作为维护者，我希望它与同批的「连续 N 次内容不符转终态」天然兼容——那条新增的终态错误
   也归 `verify` 且不可重试，因此自动落进这条清理规则，不需要各写一遍。

## 实现决策

### 接缝：任务层的失败分支

- 位置：任务层共享的那段「一卷：下载 → 校验 → 记账」的异常路径（两条链路——完整包与资料库
  ——共用它，所以只改一处，两条链路同时正确）。
- 判据（伪码，单一出处仍然是 `download_resume`）：

  ```
  except 非取消:
      若 error_kind(exc) == "verify" 且 not is_retryable(exc):
          清掉半成品 + 边车        # 重下不会有变化
      否则:
          写边车                   # 断点：谁留下的、期望多大
      raise
  ```

- 取消路径**不动**（取消不算失败：半成品保留、不写额外边车）。
- 「长度已到点 → 直接进校验 → 本地算出的哈希不符」那条分支本来就已经清掉再抛，保持不变。
- 两条链路各自的 `_download_one` 只是壳（一行转发），因此本单**不动它们**。

### 为什么不是改下载器

下载器（`resumable_download`）的职责是「把一卷下到盘上、按策略重试」，它并不知道
「半成品留着还是删掉」这件事——那条分界在任务层（既有注释与结构测试都钉着这个方向：
下载域不许知道任务层的记账）。而且**同一个不可重试异常在两条路径上语义相同**，
放在共享的任务层原语里就只写一遍。

### 验收

- 单测（在既有 `tests/test_task_download.py` 里）：注入的假下载器分别抛
  「不可重试的 verify」「可重试的 verify（内容不符）」「截断（网络）」「取消」四类，
  断言盘上与边车的四格状态；不可重试那一格必须**文件没了、边车没了**，
  网络与取消两格必须**文件在、边车在**（反向判据：防「一刀切全删」）。
- 反向注入探针（`.scratch/update-verify-failure-leftovers/probe-guard-strength.py`）：
  把判据改成「一律不清」（回到改动前）、改成「一律清」（连断点也删）两处注入，
  对应用例**必须转红**；跑完复原并复核 sha256。
- 真机复跑（`.scratch/update-verify-failure-leftovers/run-real-machine.py`，drill-02 **零改动**）：
  先把工作树里修好的源码放进沙箱（＝用户机上跑着的那一代；这是 harness 步骤，
  在证据里显式记账），再跑
  `python .scratch/verify-gate-drills/drill-02-degraded.py --only verify-size`，
  判据 = 该格 `checks` 全为真（尤其「半成品被清」「边车被清」）+ 判红 0；
  再跑 `--only cut-retry`，判据 = 「失败态留边车 / 成功后边车已清」仍成立（证明没把断点删掉）。

## 测试决策

- **好测试**：只断言外部可观察量——盘上文件在不在、边车在不在、异常类与分类字段。
  不测私有分支、不数调用次数（观测面另有既有用例）。
- **既有先例**：`tests/test_task_download.py` 已经有「注入假下载器 → 断言盘面/边车」的一整组；
  本单在同一文件、同一组里加格，不新开测试文件。
- **夹具**：假下载器（既有的三参/带关键字两种形态都已被覆盖）+ 临时目录，不碰真仓库、
  不碰沙箱。
- **真机**：drill-02 是冻结的量具（本轮一个字不改），偏离（换沙箱源码）写进我们自己的包装脚本。

## 范围外

- 不改「网络失败无上限重试」这条策略（那是内容不符那张决策单的事，且网络失败本就该无限重试）。
- 不改下载器的重试退避、分卷策略、边车格式、快照格式。
- 不新增状态面字段、不改前端话术（终态与 `error_kind` 都已存在，本单只影响盘面）。
- 不动资料库那条链路的差异部分（它共用同一段原语，自动被覆盖）。
- 不清理**历史**已经留在用户盘上的整卷半成品（升级包不负责扫盘；那条边界由
  `update-orphan-files` 的 spec 明确否掉）。

## 补充说明

### 真机原始证据（B2 场景三）

| 判据 | 实测 |
|---|---|
| 终态 | `failed`（不重试，`retry_count=0`）✅ |
| 话术 | `下载失败（卷 firstep-full-v1.2.1.zip）：发布信息不一致：清单说 1048576 字节，服务器说 3961701 字节` ✅ |
| `error_kind` | `verify` ✅ |
| `updating.lock` / `pending-update.json` | 都没留下 ✅ |
| 旧版本 | 服务还在、版本没变、工具根 `VERSIONS.md` 逐字节未变 ✅ |
| **`updates/full/` 残留** | 整卷 3,961,701 字节 + 边车 73 字节 ❌（本单要修的） |

### 一处刻意的保守

清理只发生在**任务层承认这是终态失败**的那条路径上。若将来有调用方在任务层之外捕获这些
异常并自行恢复（例如有人写「自动换源重试」），它会发现半成品已经被清掉了——这是刻意的：
「不可重试」的语义就是**这份本地数据没有价值**。要改这条语义，改的是分类表（单源），
不是这里加例外。
