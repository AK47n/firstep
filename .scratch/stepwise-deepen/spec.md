# 逐步深化（Stepwise Deepen）— spec

> 用户原话要点（语音转文字，已澄清）：修订与深化中间的「深化」过程要优化成逐步流程；UI 要清晰显示哪些做完了、哪些没做完、正在做什么；每步要有「让 AI 执行这一步」按钮；每步能和 AI 商量；上板后能向 AI 反馈；每一步 AI 要告诉我「需要做什么、做了什么」，比如上板时应该把哪个引脚接到哪个模块；全部要详细明确，UI 清楚表达。
>
> 澄清结论：统一成一套「逐步深化」流程（任务推进为主入口，直接深化保留兜底）；每步执行结果里由 AI 带出「做了什么 + 你接下来要做什么（含接线/上板指引）」；顶部加进度总览；需人工上板的步骤单独列出。

## 问题陈述

用户完成「修订」（确定性 diff + 覆盖式重生成）后进入「深化」阶段。现状的深化是一次性调用：AI 把 main.c 里所有 TODO 一次填完、统一编译验证——中间无法纠偏，某一步做坏要整树回滚重来；用户看不到「哪些功能点做完了、哪些还没做、正在做哪个」。任务推进（逐任务执行）虽然拆了步骤，但每步执行后用户只看到代码 diff 和编译徽章，AI 不会告诉用户「我这一步做了 / 改了哪些逻辑」「你现在需要做什么物理动作（比如把 PA0 接到 LED 模块的 DIO、烧录后观察什么）」，用户可以做到的「上板验证、向 AI 反馈」环节缺少前置指引，整体过程不透明、不明确。

## 方案

把「深化」的用户旅程统一为一套**逐步深化**流程（任务推进为主入口）：

1. AI 拆解任务清单（沿用现有拆解）；入口标题与文案改为「逐步深化」。
2. 用户逐任务点「做这一步」执行；每步执行完成后，AI 额外产出一份**步骤报告**：`我做了什么`（本步改了什么逻辑/函数、编译结果如何）+ `接下来你要做什么`（用户侧动作：接线引脚 → 模块、烧录、观察现象，附预期现象）。
3. UI 顶部显示**进度总览**（进度条 + 汇总文案）：已完成（编译绿）/ 未验证（待上板）/ 失败 / 进行中 / 待做 / 已跳过，全部状态一眼可见。
4. 任务卡上持久显示「接下来你要做什么」（最新一步的用户侧指引），直到该步被上板确认（人工改标已验证）——用户随时知道当前卡在哪个物理动作上。
5. 需要人工上板的步骤（verify=manual 或编译过但未上板确认）在总览与卡片上明确标注「待上板」，与「通过编译」区分开。
6. 每步执行结果面板新增「步骤报告」区块（AI 做了什么 + 下一步做什么），与现有 diff、编译摘要并列。
7. 直接深化（跳过修订后一次性填全部 TODO）保留为兜底入口，不参与逐步流程的状态展示（其产物会被任务清单覆盖时作废，沿用现有作废机制）。

## 用户故事

1. 作为用户，我想要深化入口显示为「逐步深化（任务推进）」，以便我知道现在走的是可逐步执行的流程。
2. 作为用户，我想要顶部进度条 + 汇总文案一眼看清：完成 / 待上板 / 失败 / 进行中 / 待做 / 已跳过，以便判断整体还剩多少。
3. 作为用户，我想要每个任务卡有「做这一步」按钮，以便逐个执行并随时中断。
4. 作为用户，我想要每步执行后 AI 告诉我「我做了什么」（改了哪些逻辑、编译结果），以便确认这一步符合预期。
5. 作为用户，我想要每步执行后 AI 告诉我「接下来你要做什么」（上板接线：哪个引脚接哪个模块；烧录；观察什么现象），以便我知道怎么动手。
6. 作为用户，我想要任务卡上始终显示最新一步的「接下来你要做什么」，直到该步被上板确认，以便我随时知道当前卡在哪个物理动作。
7. 作为用户，我想要「和 AI 商量（关于这一步）」「上板反馈」按钮在逐步流程中继续可用（沿用现有能力），以便每步决策前能讨论、上板后能反馈修复。
8. 作为用户，我想要需要人工上板的步骤在状态上明确区分「编译通过但待上板」与「已上板确认」，以便我按真实完成度推进。
9. 作为用户，我想要每步结果面板除 diff 外还有「步骤报告」区块，以便不改代码也能看懂这一步发生了什么。
10. 作为用户，我想要直接深化按钮保留但明确为「快速兜底」，以便偶尔仍想一次填完时可用。

## 实现决策

- **步骤报告来源**：新增 LLM 操作 `report_task_step`，在每步编译验证完成后调用一次（输入：任务描述/验收方式、编译结果、代码 diff 摘要、模块接口清单）；输出 JSON：`{what_changed, user_action}`（均为字符串，`what_changed` = AI 本步做了什么与结果，`user_action` = 用户侧动作含接线/上板/烧录/观察指引）。报告调用失败**不阻断**流程：降级为空字符串，结果面板显示兜底文案，任务仍正常落盘完成。
- **数据模型**：任务轮次记录（TaskIteration）新增两个可选字段 `what_changed` / `user_action`（缺省空串，向后兼容旧清单）。
- **事件**：新增进度事件 `task_reporting`（AI 正在总结本步），后端在报告调用前发射；SSE 已通用透传，前端仅需监听显示状态文案。
- **前端纯函数**：新增进度总览渲染（按状态分段的进度条 + 汇总文案）、步骤报告渲染（含空值兜底）、卡片「接下来你要做什么」粘性摘要；轮次历史每行追加「做了什么」摘要（截断显示）。「进度 N/M」旧文案保留（口径不变，避免破坏既有测试与习惯）。
- **口径**：总览「已完成」= 编译已验证（verified）；「待上板」= unverified（含 manual 原因）；「已跳过」单列不计入完成；进行中 = doing；失败 = failed；待做 = pending。
- **入口文案**：任务推进区标题改为「逐步深化（任务推进）」并更新说明文字；直接深化按钮文案补「（快速兜底：一次填完）」，保留原功能。
- **不做**：不改造直接深化内部为逐步；不新增数据库/文件格式版本迁移（字段可选即兼容）；不改任务状态机转移表。

## 测试决策

- 沿用既有最高缝：pytest（llm / task_progress / webapp）+ Node 测试（`tests/js/task.test.mjs`）+ fx-guard。
- llm 层：`report_task_step` 的输出解析、空/坏 JSON 处理、json_mode 与既有 discuss_task 同款断言。
- task_progress 层：`run_task` 成功后轮次记录带两个新字段；报告调用失败（LLM 抛错）时降级为空且任务仍落盘为终态；旧轮次数据（无新字段）读取兼容。
- webapp 层：`/api/tasks/execute` SSE 事件序列含 `task_reporting`，done 载荷含新字段。
- 前端：新增/更新 `task.test.mjs` 断言（进度总览文案与分段、步骤报告渲染、卡片下一步摘要、轮次历史摘要、兜底文案）；`tasksProgressText` 既有断言保持绿。
- 不新增测试缝。

## 范围外

- 直接深化内部改为逐步执行（保留一口吃胖子兜底）。
- 任务状态机（ALLOWED_STATUS_TRANSITIONS）变更。
- 任务清单文件格式大版本迁移。
- 上板门禁（强制上板后才能继续）——不做强制约束。
- 硬件板卡的接线自动检测/图形化接线图（仅文本指引）。

## 补充说明

- 进度总览是新增组件，旧「进度 N/M」文字保留（测试兼容），两者并行显示。
- 步骤报告文本由 LLM 生成，不承诺确定性；降级路径必须有兜底文案（中文）。
- 前端所有新增文案用中文，术语（status 值、字段名）保留英文。
