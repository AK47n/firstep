# bfcache 后退回来补登记（启动器模式）

## 问题陈述

用户双击 `start-app.vbs` 用应用（启动器模式：最后一个页面离开 = 服务自己停）。他在同一个标签页里
从应用导航到站外（点了一个外链、或直接改了地址栏），随后按**后退**回到应用——看到的是**死页面**：
页面本身还在，但每一个请求都连不上，界面上什么都不动。

用户不知道发生了什么，也不知道要做什么；只能关掉浏览器重新双击启动器。

## 方案

让「被浏览器放进 bfcache 冻结」的页面在**恢复时自己重新报到**：回到应用这一下就撤销那次在途退出，
服务继续活着、页面照常用。

如果回来得太晚、服务确实已经退出（用户离开超过宽限窗口），页面要**说人话**：告诉用户应用已经随
最后一个页面关闭、给出重新启动的那一步，而不是留一片什么都不响应的死页面。

## 用户故事

1. 作为用启动器打开应用的用户，我想要在同标签导航走后按后退回来时应用还能用，以便不必重新双击启动器。
2. 作为同一个用户，我想要在服务确实已经退出时看到中文说明与下一步，以便知道该做什么而不是对着一片死页面发呆。
3. 作为维护者，我想要这条路径有真机证据与守卫，以便以后改登记/注销逻辑时不会把它悄悄改坏。
4. 作为维护者，我想要「关最后一个页面 = 停服务」的既有语义保持不变，以便不为了修一条后退路径而留下常驻进程。

## 实现决策

- **修在前端，服务端零改动**：服务端注册表的「登记即撤防」语义已经够用（同一 `tab_id` 再登记一次
  就撤销在途退出），本特性不新增端点、不改状态机、不动宽限常量。
- **bfcache 恢复靠 `pageshow`**：恢复的文档不会再执行任何脚本，登记的内联脚本与模块图都不会重跑，
  因此只能由事件回调补发。文档实例令牌沿用 `performance.timeOrigin`——它是每文档恒定的值，
  bfcache 恢复的是同一个文档，所以令牌天然对得上注册表里的记录，无需另存。
- **注销那一半保持原样**：导航离开仍然照常告别（否则「离开就停」失效，还会留下常驻进程）。
- **第二层是可见态**：服务已经退出时任何补登记都必然失败，必现形态是「页面还在、请求全失败」，
  因此需要一条明确的用户可见路径（中文说明 + 重新启动的指引 + 至多一次自动重试）。
- **不动的东西**：宽限窗口数值、心跳/长轮询式的存活检测、启动器 `.bat` / 服务端 launcher 一侧。

## 测试决策

- **红证优先，且要真 Chrome**：headless 与真 Chrome 的 bfcache 行为可能不一致，浏览器门禁又模拟不了
  真关窗口，所以红证走真 Chrome + 既有 CDP 夹具，读数落本目录。
- **判据走既有缝，不新造**：① 结构判据（`tests/js/tab-register-guard.test.mjs` 同族）——补「恢复时补登记」
  与「令牌同源」两条腿，含"端点字样只在注释里"这类假绿反例；② 装载根契约（`tests/js/boot-contract.mjs`）
  的登记/注销同源判据；③ 真浏览器行为契约（`tests/browser/launcher-reload.spec.mjs` 同族，启动器模式夹具）——
  导航走 → 后退 → 服务仍在。
- **只测外部行为**：断言"后退回来页面还能拿到数据 / 服务进程还在"，不断言具体回调名或请求次数。

## 范围外

- 心跳 / 长轮询式的"标签还在不在"重设计（`launcher-exit-race` 已列未做项）。
- 宽限窗口 `_EXIT_GRACE` 的数值调整。
- 浏览器门禁自身"模拟不了真关窗口"的限制（另一条已记事项）。
- 非启动器模式（手动跑 `webapp`）下的任何行为——那条路径根本不自动退出。
