# bfcache 后退回来补登记（启动器模式）

## 问题陈述

用户双击 `start-app.vbs` 用应用（启动器模式：最后一个页面离开 = 服务自己停）。他在同一个标签页里
从应用导航到站外（点了一个外链、或直接改了地址栏），随后按**后退**回到应用——看到的是**死页面**：
页面本身还在，但每一个请求都连不上，界面上什么都不动。

用户不知道发生了什么，也不知道要做什么；只能关掉浏览器重新双击启动器。

## 方案

让「被浏览器放进 bfcache 冻结」的页面在**恢复时自己重新报到**：回到应用这一下就撤销那次在途退出，
服务继续活着、页面照常用。

如果回来得太晚、服务确实已经退出（用户离开超过宽限窗口），页面要**说人话**：告诉用户应用已经随
最后一个页面关闭、给出重新启动的那一步，而不是留一片什么都不响应的死页面。

## 用户故事

1. 作为用启动器打开应用的用户，我想要在同标签导航走后按后退回来时应用还能用，以便不必重新双击启动器。
2. 作为同一个用户，我想要在服务确实已经退出时看到中文说明与下一步，以便知道该做什么而不是对着一片死页面发呆。
3. 作为维护者，我想要这条路径有真机证据与守卫，以便以后改登记/注销逻辑时不会把它悄悄改坏。
4. 作为维护者，我想要「关最后一个页面 = 停服务」的既有语义保持不变，以便不为了修一条后退路径而留下常驻进程。

## 实现决策

- **修在前端，服务端零改动**：服务端注册表的「登记即撤防」语义已经够用（同一 `tab_id` 再登记一次
  就撤销在途退出），本特性不新增端点、不改状态机、不动宽限常量。
- **bfcache 恢复靠 `pageshow`**：恢复的文档不会再执行任何脚本，登记的内联脚本与模块图都不会重跑，
  因此只能由事件回调补发。文档实例令牌沿用 `performance.timeOrigin`——它是每文档恒定的值，
  bfcache 恢复的是同一个文档，所以令牌天然对得上注册表里的记录，无需另存。
- **注销那一半保持原样**：导航离开仍然照常告别（否则「离开就停」失效，还会留下常驻进程）。
- **第二层是可见态**：服务已经退出时任何补登记都必然失败，必现形态是「页面还在、请求全失败」，
  因此需要一条明确的用户可见路径（中文说明 + 重新启动的指引 + 至多一次自动重试）。
  **← 这一句已按实况修订，见文末「落地回填」第 3 条（改成"只发一次、不重试；靠探活自动接回"）。**
- **不动的东西**：宽限窗口数值、心跳/长轮询式的存活检测、启动器 `.bat` / 服务端 launcher 一侧。
  **← 「心跳/长轮询式的存活检测」指的是"用轮询重做标签在不在的判定"（判据⑥ 那套协议），
  不含可见态自己那条 2 秒探活（只为了让用户重启完不用手点，见文末「落地回填」第 3 条）。**

## 测试决策

- **红证优先，且要真 Chrome**：headless 与真 Chrome 的 bfcache 行为可能不一致，浏览器门禁又模拟不了
  真关窗口，所以红证走真 Chrome + 既有 CDP 夹具，读数落本目录。
  **← 本机没有独立安装的 Chrome，改用 playwright 真 chromium；做法与四组配置矩阵见文末「落地回填」第 1 条。**
- **判据走既有缝，不新造**：① 结构判据（`tests/js/tab-register-guard.test.mjs` 同族）——补「恢复时补登记」
  与「令牌同源」两条腿，含"端点字样只在注释里"这类假绿反例；② 装载根契约（`tests/js/boot-contract.mjs`）
  的登记/注销同源判据；③ 真浏览器行为契约（`tests/browser/launcher-reload.spec.mjs` 同族，启动器模式夹具）——
  导航走 → 后退 → 服务仍在。
  **← ③ 实际落成**：门禁里 bfcache 根本不会发生（playwright 默认关它），所以用**合成
  `PageTransitionEvent` 重演同一条时序**；真 bfcache 由 `.scratch/bfcache-return-register/probe-00-bfcache-red.mjs`
  负责（见文末「落地回填」第 2 条）。判据本体是 `boot-contract.mjs` 的**判据 ⑦**。
- **只测外部行为**：断言"后退回来页面还能拿到数据 / 服务进程还在"，不断言具体回调名或请求次数。

## 范围外

- 心跳 / 长轮询式的"标签还在不在"重设计（`launcher-exit-race` 已列未做项；**可见态那条 2 秒探活
  不属于它**——探活只在可见态亮着时跑，用来把用户重启完的页面自动接回来，不参与"标签在不在"的判定）。
- 宽限窗口 `_EXIT_GRACE` 的数值调整。
- 浏览器门禁自身"模拟不了真关窗口"的限制（另一条已记事项）。
- 非启动器模式（手动跑 `webapp`）下的任何行为——那条路径根本不自动退出。

## 落地回填（2026-09-24，实施后按实况修 spec——**以这一节为准**）

实施下来与上面三处措辞不同，逐条写清（工单里有更细的读数与理由）：

1. **红证不是"真 Chrome + CDP"**：本机没有独立安装的 Chrome。改用 playwright 的真 chromium
   （`channel: "chromium"`）+ `ignoreDefaultArgs: ["--disable-back-forward-cache"]`——playwright
   **默认**就传那条 flag，不摘掉它 bfcache 根本不发生（所以门禁里那套 `goto → goBack` 只会得到
   整页重载）。四组 launch 配置的矩阵在 `probe-00-bfcache-red.{txt,json}`，修前红 / 修后绿
   的前后对读在 `after-fix/`。
2. **浏览器门禁那一层用合成事件，不用真导航**：门禁默认关 bfcache，"后退"必然是整页重载
   （内联登记重跑、服务活着）——拿它写 bfcache 用例是**假绿**。所以行为契约用
   `new PageTransitionEvent("pagehide"|"pageshow", {persisted: true})` 重演同一条时序
   （产品监听器、端点、服务端退出调度都是真的），真 bfcache 由上面那支探针负责。
3. **不加"自动重试"，改为"探活 + 自动重载一次"**：补登记失败只有一种成因（回来时服务已经退出），
   几百毫秒后重试必然也失败；真正的恢复来源是用户重新双击启动器。所以可见态里每 2 秒探一次
   `/api/health`，服务一回来就自动重新载入**一次**（不构成自动无限刷新）。
4. **服务端确实零改动**（含 `_EXIT_GRACE`）：`register()` 的「登记即撤防」语义本来就够用。
   前端改动落在三处——`index.html`（内联脚本 + 标记 + CSS）、新 `ui/service-stopped.js`、
   `boot.js`（接线）。补登记刻意留在**同一个内联块**里，以维持判据⑥那条"登记点单源"。

## 双轴评审整改（2026-09-24，Spec + Standards 两轴并行；逐条处置见工单 Comments）

评审提了 11 条（Spec 7 / Standards 4 硬 + 5 判断），**除"闸门里没有真 bfcache"一条按有意取舍保留**
（理由同上面第 2 条：门禁开了 bfcache 会依赖完整 chromium 与浏览器版本行为，而真 bfcache 由探针
覆盖且可复跑），其余全部改掉。与本节上面四条相关的三处补充：

5. **失败判据收窄**：只有"到不了服务"才算失败——网络错（服务已退出时 `fetch` 直接 reject）或 5xx；
   **4xx 不算**（那是我们自己的载荷问题，不是服务停了），不该报「服务已停止」。
6. **失败要留可回读的落地态**：只广播一次性事件不够——"模块图装载途中被冻结再恢复"这条时序里，
   广播发出时 ui 层还没装载，事件会丢、可见态永远不亮。所以内联脚本同时写
   `documentElement.dataset.serviceStopped = "1"`，ui 模块装载时回读同一个键（判据 ⑦⑤ 两侧对账）。
7. **可见态文案不假定启动方式**：改成「重新启动 firstep：双击 `start-app.vbs`（或你平时启动它的方式）」
   ——非启动器模式（手动跑 `webapp`）下这句话同样成立。
