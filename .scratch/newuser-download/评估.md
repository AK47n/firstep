# 方案评估：新用户下载体验优化（newuser-download）

> 结论先行：**最痛的不是下载速度，是「README 让人下一个已经不存在的文件」和「解压后没有任何说明」。**
> 这两条都能在本轮解决，而且**大部分收益不需要发新版本就能拿到**。

## 1. 一次自我更正（先说清楚，避免你被我误导）

我在初步侦察时根据 `gh release view --json assets` 的 MB 读数（四舍五入显示 0.0）判断
「v1.1.1 有三个 0 字节资产、发布流程有缺陷」。**复核精确字节后确认这是误读**：

| 资产 | 精确字节 | 我最初的错误结论 |
|---|---|---|
| `firstep-full-v1.1.1.sha256.txt` | 91 | 「0 字节，校验缺失」 |
| `firstep-full-v1.1.1.removed.txt` | 30 | 「0 字节」 |
| `firstep-update-v1.1.1.sha256.txt` | 92 | 「0 字节」 |

它们本来就很小，内容完整（本机 `firstep-pack\` 里有同名原件可对照）。
**发布流程这一块没有问题，本方案不含任何「修发布流程」的工单。**

## 2. 现网事实（全部实测，写工单时按这个口径）

```
最新 release  v1.1.1（8 件资产）
  firstep-full-v1.1.1.zip        821,352,026 B（783 MiB）  ← 新用户该下的就是这个
  firstep-full-v1.1.1.manifest.json  3,719,305 B          ← 程序读的
  firstep-full-v1.1.1.removed.txt           30 B          ← 人工核对
  firstep-full-v1.1.1.sha256.txt            91 B          ← 人工核对
  firstep-update-v1.1.1.zip      310,369,185 B（296 MiB）  ← 已装用户走的
  firstep-update-v1.1.1.files.txt      317,156 B
  firstep-update-v1.1.1.removed.txt         30 B
  firstep-update-v1.1.1.sha256.txt          92 B
下载计数：full.zip 3 次、update.zip 3 次、manifest.json 5 次  ← 新用户在两个 zip 之间真的会犹豫

README「获取方式」写的是：firstep-full.7z.001~004 / 约 6 GB / 需 7-Zip
实际存在的 7z 包：只在 v1.0.0 那个 release（4 卷 6.2 GB + HOW_TO_EXTRACT.txt）
```

**→ README 把新用户指向了一个在最新 release 上不存在的文件形态，并把体积说大了约 8 倍。**

## 3. 逐项评估

严重度 = 新用户撞上的概率 × 卡住的代价；工作量 = 需要动代码/流程的程度。

| # | 项 | 严重度 | 工作量 | 要发版才生效？ | 风险 |
|---|---|---|---|---|---|
| 1 | README 说下 6 GB 的 7z（实际不存在） | **致命** | 极小 | **不要**（仓库主页即时生效） | 极低 |
| 2 | Release 页 8 个文件无「给谁下」说明 | 高 | 极小 | **不要**（改 Release 说明即可） | 极低 |
| 3 | 解压后包内没有「从这里开始」 | 高 | 小 | **要**（只在下次完整包里） | 低 |
| 4 | 两套完整包形态并存（6 GB 7z / 783 MB zip） | 中 | 极小 | 不要 | 低 |
| 5 | 资产名不解释自己（`firstep-full-*`） | 中 | 小 | 要 | **中**（见 §5） |
| 6 | `install.bat` 收尾没讲「以后双击桌面即可」 | 低 | 小 | 要（小发版即可） | 低 |

## 4. 建议的落地顺序（价值/成本比从高到低）

**第一梯队（本轮就做完，不发版，立刻对新用户生效）**
1. README「获取方式」只说事实：一条主路径 + 哪个文件给谁下 + 标明「Windows 自带解压」。
2. 7z 渠道口径下线：`releasing.md` 与 README 同步，历史 release 资产不删。
3. Release 说明加一段固定模板：第一行「新用户只下这一个文件」。

**第二梯队（随下一次完整包生效）**
4. 包根目录 `START-HERE.txt`（≤30 行，记事本可读）+ 白名单登记 + 守卫。
5. 资产改「人话名」（可选，见 §5）。
6. `install.bat` 文案小修。

**第三梯队（本轮不做，但数据留给你将来决策）**
- 「先下 300 MB 就能跑」：完整包里 `sources/materials` 占 **688.3 MB / 总 802.2 MB（86%）**，
  `library`（模块库 + 母版库）只有 258.0 MB。若做「轻装包（工具 + 四库）」，首下可从 783 MiB 压到约 300 MiB，
  资料库交给既有的增量链路（那套已经在跑）。**代价**：发布侧多一套资产的打包/上传/命名，用户侧多一条路径分支，
  Release 页从「下一个文件」又变回「选一个」——**与新用户路径收敛的目标相冲突**，故本轮不做。
- 安装器 / 自解压 EXE：你已明确不要；且当前「zip + install.bat」已经满足「双击就能装」，新增 SFX 要动发布链与杀软白名单，收益不抵风险。

## 5. 需要你拍板的三处取舍

1. **资产改名（工单 03）做不做？**
   收益：新用户一眼知道下哪个。风险：改的是**发布产物的文件名**，必须同步改写清单里的 `zip_name`
   并重新生成校验和，否则用户侧的「任一资产缺失 = 整体判不可下」保护会把整条链路判死。
   我的建议：**做，但排在 README 之后、并在工单里写明「宁可降级也不能在发版夜里动打包器」**。
2. **README 顶部固定链到哪个 URL？**
   建议指向 `/releases/latest`（永远指向最新正式版），**不写死某个 tag 的深链**——否则下次发版又失效，
   这正是本次问题的成因类型。
3. **7z 历史 release 怎么处理？**
   建议只改文档口径、保留资产（不动已发布的东西）；不建议删除 v1.0.0 那个 release。

## 6. 不做什么（明确写下来，避免范围爬升）

- 不改任何下载行为与下载器代码（`full_*` / `webapp` 路由一行不动）。
- 不改包内容边界（第三方安装包仍不进包）。
- 不做体积优化、不做安装器、不做自动/静默下载。
- 不动 `firstep-update-*` 资产名与更新协议。
- 不删任何历史 release 资产。
