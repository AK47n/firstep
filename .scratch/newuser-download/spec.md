# 新用户下载体验优化（newuser-download）spec

> 范围经用户确认：**A（GitHub 落地页第一眼）+ B（下完到能用）**；
> 用户明确**不要 C（首下体积/速度）与 D（做安装器）**；
> 完成判据含**8020 沙箱真机演练**；本轮只出方案，不写代码。

## 问题陈述

一个从没见过本工具的人，从 GitHub 开始到「网页里能贴赛题」为止，撞到的是三处**指令与事实不符**，
而不是下载速度慢：

1. **README 让人下一个已经不存在的文件。** README「获取方式」表把「完整包」写成
   `firstep-full.7z.001~004` 四个分卷、约 6 GB、需 7-Zip——那是 **v1.0.0 那个 release** 的资产形态
   （实测 4 卷 6.2 GB + `HOW_TO_EXTRACT.txt`）。当前最新版 v1.1.1 的完整包是
   **`firstep-full-v1.1.1.zip` 单卷 821,352,026 字节（783 MiB）**，Windows 自带解压即可。
   照 README 做的新用户会在 Releases 页上找不到 `firstep-full.7z.001`。
2. **Release 页给新用户 8 个选择，且名字不解释自己。** v1.1.1 共 8 件资产：
   `firstep-update-*`（4 件，给**已装用户**）、`firstep-full-*`（4 件，其中 `manifest.json` 3.7 MB
   是给**程序读**的、`removed.txt`/`sha256.txt` 是给**人工核对**的）。新用户没有任何线索知道
   「只要下那一个 783 MB 的 zip」，更不会知道 `firstep-update-v1.1.1.zip` 对他没用。
   当前下载计数也印证这一点：`full.zip` 与 `update.zip` 都在被下（各 3 次），`manifest.json` 被下了 5 次。
3. **解压之后包内没有「从这里开始」。** 用户面对的是 `install.bat` / `start-app.bat` / `start-app.vbs` /
   `stop-firstep.bat` / `stop-firstep.vbs` 五个入口文件，包内**没有任何一份面向使用者的说明书**
   （`README.md` 要自己想起来去点，`CLAUDE.md` 写给 AI、`CONTEXT.md` 17 万字节是给开发者的）。
   「以后双击桌面快捷方式、不要再点 install.bat」这条关键信息只写在 README 的 FAQ 里。

结论：**新用户下载体验的主要摩擦是「哪一个是给我下的」「下完该点哪个」**，
不是带宽，也不是缺一个安装器。

## 方案

把新用户的下载链路**收敛成一条**，并且让每一处只说事实：

1. **落地页（A）**：README 的「获取方式」不再出现 `7z` / 7-Zip / 6 GB；
   只有一行直链「下载 `firstep-完整包-<tag>.zip`（约 790 MB，Windows 自带解压）」
   + 一张「哪个文件给谁下」的三行表；Release 说明模板第一行就是「新用户只下一个文件」。
   **7z 完整包渠道正式标注下线**（用户已确认不要它），`docs/agents/releasing.md` 同步。
2. **包内交付（A+B）**：完整包根目录新增 **`START-HERE.txt`**（UTF-8、中文、≤30 行、
   记事本双击可读），解压后第一个就是它。它只回答前 20 分钟：
   双击 `install.bat` → 装完双击桌面 `firstep` → 网页里配 key。
   另附预期行为与常见误解（没有 `.venv` 是正常的；可重复运行；失败看哪里）。
   为此 `START-HERE.txt` 必须进 `full_pack` 的顶层白名单（否则按现有规则根本不进包）。
3. **资产可读性（A）**：之后的 release 里，新用户要下的那个文件叫
   `firstep-完整包-<tag>.zip`；`firstep-update-*` 资产名**不动**（工具内更新协议按前缀发现资产，
   改名即断链路）。同时装一条守卫：新名在、旧名不在同名 release 里同时出现两份 zip。
   *（此条为可选优化，见「范围外」的取舍说明。）*
4. **安装收尾（B）**：`install.bat` 收尾提示与失败提示已经基本到位，只做小幅人话化：
   完成提示明确「以后再启动就双击桌面 firstep，不用再跑本脚本」；
   `need_python` 分支补一行「也可以直接到 https://www.python.org/downloads/ 下载」。

## 用户故事

1. 作为完全没听过 firstep 的新用户，我想要在 README 第一屏就看清「我该下哪个文件、多大、要不要装解压软件」，以便不用读完 123 行也敢点下载。
2. 作为新用户，我想要 README 里写的东西在 Releases 页上真的存在，以便照做就能成。
3. 作为新用户，我想要 Release 页上除我该下的那一个文件之外，其余文件都有「给谁用」的说明，以便不会误下 296 MB 的已装用户包。
4. 作为新用户，我想要解压后第一眼就看到「从这里开始」，以便知道该双击哪个文件、不要点哪个。
5. 作为新用户，我想要在动手之前知道「装几分钟、需要联网、要填什么」，以便不会装到一半以为卡死了。
6. 作为新用户，我想要在忘掉说明书之后仍能自己找回来（桌面快捷方式 + 常见问题一句话），以便第二次启动不用翻文件夹。
7. 作为新用户，我想要下载页上不再同时存在两套互斥的完整包形态（6 GB 7z / 783 MB zip），以便不产生「是不是要下 6 GB」的犹豫。
8. 作为新用户，我想要安装失败时得到中文的下一步（装 Python / 复查网络 / 重跑本脚本），以便不卡在一个黑窗口。
9. 作为发布者，我想要「哪个资产给谁」这件事在各处只有一个说法，以便下次发版不会又漏改一处产生第 4 处不一致。
10. 作为发布者，我想要这些改动只靠**已有发布流程**就能落地（不发新包也能改一部分），以便不必为一个文档不一致专门造一次大版本。
11. 作为维护者，我想要有测试守卫钉住「README 不再出现已下线渠道」「START-HERE 在包内」这两条，以便它们不会被下次改动悄悄退化。

## 实现决策

### 交付物分层（决定工单怎么切）

| 层 | 改动 | 要发版才到用户手上？ |
|---|---|---|
| 文档层 | `README.md` 获取方式章、`docs/agents/releasing.md` 7z 下线、Release 说明模板 | **不需要**（README 是仓库主页，改完即时生效） |
| 包内容层 | 根目录 `START-HERE.txt` + `full_pack` 顶层白名单 | **需要**（只在下次完整包里出现） |
| 资产命名层 | 新用户包的资产名 | **需要**（下次发版时生效） |
| 脚本层 | `install.bat` 文案人话化 | **需要**（小发版一键更新即可，与完整包无关） |

因此本特性**不是**一个「等 v1.1.2」的整体，而是「文档立刻见效 + 包内容随下次发布生效」两段。

### 具体的接口与契约

- **`START-HERE.txt` 是包内文件，不是仓库专属文件**：`full_pack` 只有一份顶层白名单
  `TOP_LEVEL_ENTRIES`（目录与根级文件同表，如 `README.md` / `install.bat` 就在里面），
  新增后必须登记进它；否则 `scan_tree` 直接跳过、`_exclude_reason` 给出「顶层不在白名单」——
  这正是「清单与包一致」不变量的保护。
- **编码**：`START-HERE.txt` 用 **UTF-8 无 BOM**（Win10 1903+ 记事本默认支持，且不引入 BOM 争议）；
  `install.bat` 维持 **GBK 无 BOM**（`tests/test_onboarding_docs.py` 已钉住）。
- **资产命名契约（可选条）**：新名 = `firstep-完整包-<tag>.zip`；
  `firstep-update-<tag>.zip` 与所有 `manifest/removed/sha256` 附件**原名不动**；
  不允许同一 release 同时存在 `firstep-完整包-*.zip` 与 `firstep-full-*.zip`（守卫断言）。
- **README 单一事实源**：下载体积与形态只允许在「获取方式」一处写；其余章节只允许引用该处，
  避免下次再出现「6 GB」这类第二处口径。
- **Release 说明模板**：模板放 `docs/agents/releasing.md`，两行固定开头——
  ①「新用户：只下 `<文件名>`（约 XXX MB，Windows 自带解压）」；②「已装用户：走工具内更新，不用看这里」。

### 明确不碰的东西

- 不碰 `firstep-update-*` 的资产名与工具内更新协议（改名即断链路）。
- 不碰增量/全量下载代码（`full_task.py` / `full_apply.py` / `webapp` 相关路由）——
  本次不改任何下载行为，只改「用户在下载前后看到什么」。
- 不碰资料库增量机制与包内容边界（第三方安装包仍不进包）。

## 测试决策

沿用既有缝，**不新增跨层新缝**：

- **文档守卫（最高既有缝）**：扩 `tests/test_onboarding_docs.py`：
  - `README.md` 不再出现已下线渠道串（`firstep-full.7z` / `7-Zip` 作为**要求**出现即失败）；
  - README 的「获取方式」章必须含当前资产名形态与「Windows 自带解压」口径；
  - `START-HERE.txt` 存在、UTF-8 无 BOM、含三步链路 needle（`install.bat` / 桌面 `firstep` / API key）；
  - Release 说明模板存在且含「新用户只下」「已装用户」两行。
- **打包守卫**：`tests/test_full_pack.py`（既有）扩一条——
  `scan_tree(仓库根)` 的结果**必须包含 `START-HERE.txt`**，
  且 `excluded_paths` 里**不得**出现它（防白名单漏登记导致「清单有、包里没有」或反之）。
- **真机演练（本次的完成判据，不是单测）**：`.scratch/newuser-download/E2E-8020.md` 定义
  一次「把自己当新用户」的全链路：拿**线上真实 v1.1.1 资产**（本机 `firstep-pack\` 已有一份，
  免重下）→ 用 **Windows 自带解压**（不是 7-Zip）解开 → 只照 README/START-HERE 做 →
  在 **8020 沙箱**里跑 `install.bat` → 桌面快捷方式 → 浏览器进页面 → 配 key 前停住 →
  核查日志与配置落点。
  *注意*：沙箱当前 `install.bat` 是**旧版（2582 字节，无第 5 步）**，演练前须用真身 v1.1.1 的同步一次，
  否则演练的是历史版本。
- **不做**：真造 GB 级资产、自动化浏览器对新用户文案做视觉回归。

## 范围外

- **C（首下体积/速度）**：用户明确不要。已知候选（供将来取用）——
  完整包内含 `sources/materials` 688.3 MB（占总 802.2 MB 的 86%），
  理论上可做「工具+四库 约 300 MB 先跑起来、资料库走既有增量」；
  代价是发布侧多一套资产与一条「轻装用户」路径，本次不做。
- **D（安装器 / 自解压 / EXE）**：用户明确不要。
- 7z 完整包渠道的下线动作**不含**删除历史 release 资产（只改文档口径 + 停止维护该形态）。
- 不改下载器行为、不改包内容边界、不做自动下载/静默下载。

### 一次自我更正（留痕，避免下次又写错）

初查时把 `gh release view --json assets` 的 MB 四舍五入读数（0.0 MB）当成「三个资产是 0 字节、发布流程有缺陷」，
写进了给用户的初步判断。复核精确字节后确认**资产都是非空的**，那三件本来就很小。
本 spec 与工单不再引用该结论。
