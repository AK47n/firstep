## ①（**已撤回**）点掉 chip 后已选清单「显示过期展开结果」——是我的判据误报

**我当时看到的「证据」（C2 单点时间线，expand 注入 700ms 延迟）：**

```
t+  15ms start        chip已选[ir_beam,motor] 清单「ir_beam 说明 STM32 已验证 …」
t+ 109ms expand→req   chip已选[motor]         清单「已选（未展开依赖）：pid、motor」 body={"slugs":["pid","motor"],…}
t+ 139ms frame        chip已选[motor]         清单「已选（未展开依赖）：pid、motor」
t+ 892ms expand←resp  chip已选[motor]         清单「已选（未展开依赖）：pid、motor」   status=200
t+ 905ms frame        chip已选[motor]         清单「motor 说明 … 移除 TB6612 …」
```

**我错在哪：** 判据写成「清单里**看不到** ir_beam = 过期写回」，可
`已选（未展开依赖）：pid、motor` **正是正确的占位**——它逐字列出了当前选择
（`pid` + `motor`），被点掉的 `ir_beam` **根本不在里面**。我把「没有它的行」误读成
「显示的是旧结果」，而那一帧里其实**没有任何过期内容**。

**怎么证伪的（三步，缺一不可）：**

1. 把 `renderSelected` 临时改回**原实现的两行分支形状**（`if (!expanded.length) …`
   + 占位文案），真机时间线**照旧**：那一帧仍然只有
   `已选（未展开依赖）：pid、motor`，从未渲染出 `ir_beam` 的行 → 说明「旧结果被画出来」
   这个现象**不存在**；
2. 注入反例（点掉后**无条件**按 `expanded` 渲染）：清单变成**空**（不是过期行）——
   因为 `reRenderAfterSelectionChange` **已经先清了 `expanded`**，
   `renderRecommendResult` 里那次 `renderSelected()` 拿到的就是空数组；
3. 读码确认时序：点击路径（chip 移除 / 组卡换选）都是
   `expanded = []; warnings = [];` → `renderSelected(); renderWarnings();
   renderRecommendResult(lastRecommend, false)`——**清在前、渲染在后**；
   `addModule` / 切平台同样先清再渲。`renderSelected` 能拿到的 `expanded`
   只可能是「空」或「本次（上次）请求已落地的新结果」，**不存在「上一个选择集的产物」**。

**处置：** 撤回结论；工单 08 作废（`Status: wontfix`，附证伪过程）；为它写的
`expandedSelectionHTML` 守卫与那批单测**全部回退**（不留下为假 bug 服务的代码——本仓
口径是「不为想象中的未来写代码」）。只保留两条**描述既有行为**的判据进
`tests/js/module-intro-detail.test.mjs`：占位文案逐字等于当前选择；点击路径
**清 expanded 必须早于渲染**。

**为什么这次误报值得记下来：** 真机 + 时间线 + 请求体三条线都在，**判据本身写错了**
照样得出「铁证如山」的假结论——证据充分 ≠ 结论正确，**判据必须先被质疑一次**。
第一版判据（「chip 说已选、清单里没这行」）报 3 帧、第二版报 2 帧、第三版报 0 帧，
三版看的是**同一段真机输出**。

## ② expand 失败 → 自激重试 + 按钮永久禁用（真 bug，最高优先级）

**证据（D 节，`/api/selection/expand` 恒返回 500）：**

```
常败：3s 内 32 次 → 再 3s 内共 63 次（约 10.5 次/秒）；按钮 disabled=true；msg=「」   ← 无任何提示
```

**根因（源码确认）：** `runExpand()` 的收尾：

```js
} catch (e) { $("expand-msg").textContent = e.message; }
finally {
  expandEnd();
  if ((expandPending || !ok) && chosenPlatform && selectedSlugs.length) {
    expandPending = false;
    void runExpand();            // ← ok=false（**失败**）与「结果被作废」共用一个条件
  }
}
```

`!ok` 把两种语义完全不同的情况并到了一起：
* **结果被作废**（令牌过期 / 快照不符）——重跑是对的；
* **请求失败**（500 / 超时 / 断网）——重跑会**立刻以同一参数再打一次**，失败 → 又跑，
  没有退避、没有次数上限、没有熔断。请求越慢频率越低，请求越快频率越高（实测
  ~10 次/秒），对本地后端就是**持续打满**。

三个放大伤害的细节：
1. `expandBegin()` 每次都 `$("expand-msg").textContent = ""`——**报错信息在被看到之前
   就被自己清掉**（实测 msg 恒为空串，用户完全不知道为什么没反应）；
2. `expandBusy` 恒为 true → `btn-expand` **永久 disabled**，用户连手动重试都做不到；
3. `expandBtnLabel` 记的是原始文案，所以按钮停在自己的正常文案上——**看起来没坏**。

**对照：** D2 用例（先失败后成功）证明**失败本身不粘滞**（手点一次就恢复）——坏的只有
「收尾无退路重跑」这一段。修法见工单 09。

## ③ 模块说明弹窗缺「弹窗无障碍三件套」（真 bug，但是全仓口径）

实测：打开说明后 `document.activeElement` = **触发它的那个说明按钮**；按 Tab **焦点
跑到弹窗外的元素**；Esc 关闭后焦点落在 `BODY`；`role` / `aria-modal` 均为 `null`。

**这不是本单独有的欠账，而是本弹窗漏抄了全仓既有范式**——同一个仓库里：

**口径建议：** 修在 `openModuleInfo` 一处（三处入口共用它），照 `confirm.js` 的写法抄；
`role="dialog"` / `aria-modal` 若全仓都没有，就别只在本弹窗加一个孤例——单开一条
「全仓遮罩补 role/aria」的账，别混进本单。工单 10 里已按此拆好（必做 = 三件套，
可选 = role/aria 是否本单做）。

**几何/内容一节全部通过（无需改动）：** 1280×720 / 1366×768 / 900×800 三档视口下

`[object Object]` 渲染事故；`ir_beam` 段序严格是「这是干什么的 → 怎么接线 → 怎么用

## ④ 认知纠正（不是 bug，但必须改文档）

工单 07 与 `tests/browser/module-intro.spec.mjs` 的并发用例把「清单塌陷」描述成：
*点回 chip 后 120ms，已选清单变成只剩 `motor`*（暗示「过期 expand 响应的旧集合」）。

本轮真机帧序列显示，同一个症状在**点击路径**上的形态是**另一回事**：

* 那一帧的**请求体是新集合**（C2 实测 `{"slugs":["pid","motor"]}`，不是旧集合）；
* 那一帧出现在**响应回来之前**（t+71ms vs t+840ms）；
* 它显示的是**正确的占位**（`已选（未展开依赖）：<当前选择>`）——不是旧展开结果。

换句话说：**「点掉之后清单里没有那个模块的行」是正常且正确的**（`expanded` 被清、
回落到占位），**不要**把它当成 07 那个竞态的症状去修。07 真正的症状只在
**响应落地**那一刻出现（令牌 + 快照守的是那里，用例盯的是中间帧），两者别混。

**建议：** 把这段写进 07 的「没做（如实记录）」段或本报告，别改历史工单的结论。

## 方法记录（本轮最值钱的四条）

1. **判据必须先被质疑一次**：同一个症状，我的判据三版分别报 3 帧 / 2 帧 / 0 帧
   「违规」——看的是**同一段真机输出**。前两版都在把**正确行为**（回落占位逐字列出
   当前选择）当成 bug。真机 + 时间线 + 请求体三线齐全，也只是「证据充分」，
   **不代表判据写对了**；撤回结论比留住一个假 bug 更值钱。
2. **失败路径要点两次**：只测一次失败会得到「能自愈」的假绿（D2 就是绿的）。
   恒失败 + 两个 3 秒窗口，才把「自激」与「重试一次」分开。
3. **同一症状要能区分「哪条路径」**：工单 07 的竞态症状在**响应落地**那一刻
   （令牌/快照管那里），点击路径的「清单先变占位」是**正常过渡**（清在前、渲染在后
   的必然结果）。两条路径长得像，修法完全不同——混了就会去修一个不存在的 bug（本轮
   正是如此）。
4. **playwright 的 `click()` 超时日志本身就是证据**：B1 第一次不是脚本写错，而是
   「全屏遮罩挡住第二个入口」——`openModuleInfo` 里「重复打开 = 替换」那段
   **鼠标根本走不到**（死分支）。这条不改行为，但别再把它当防线。

**本轮脚本自身的失误（如实记录，全部留在脚本注释里防重犯）：** ① 第一版把 `pid`
当推荐 chip 点（进了功能组的模块在推荐区渲染成**组卡成员行**，没有 chip）→ 点空超时；
②③ C / C2 判据两版都把合法占位当成「过期视图写回」（见上「误报撤回」段）。
