# spec — 代码编辑器优化第三轮（输入链性能 + 三层对齐回归）

## 问题陈述

「代码」tab 的 IDE 式编辑器在前两轮（code-editor-vscode-polish、code-editor-refine
11 项）之后功能已齐，但**大文件逐键输入仍有明显延迟**：6000 行 .c 在真实浏览器
按下一次 input 事件，热路径实测 47–54ms（冷路径约 186ms），远高于一帧预算
16ms。纯函数（折叠 / 缩进引导线 / 括号深度）单次都在 7ms 以内，说明热点不在这
些纯函数的单次成本，而在**输入事件处理链的重复全量计算与 O(n) 扫描**：

- 标记层 `currentMarks` 在**每次**字符编辑都会全量重算（缩进引导线全扫 + 括号
  彩虹全扫，CPU 采样合计约 20ms）；上一轮「纯字符编辑标记沿用」的 `markClean`
  门控只跳过了标记层**渲染**，缓存键是内容引用——内容一变缓存即失效，仍走全量
  重算。
- 光标行号 `caretLineOf` 是 O(pos) 线性扫描（从文件头数到光标），一个输入链里
  被调用 2–3 次（CPU 采样约 12.8ms）。
- 每次输入对全文多次 `split("\n")`（行数判定、增量 diff、窗口切片各自切一遍），
  堆分配触发的 GC 采样约 23ms。

视觉/布局方面：本轮实测 1280 / 1024 / 900 / 820 宽 × 深浅两主题 × 侧栏展开/
收起 × 状态栏，均未发现新的明显缺陷（输入框「深底」为截图瞬态，运行时主题切换
诊断正常）。但**编辑器窗口化三层（行号 gutter / 高亮层 / 标记层）的对齐是该区域
历史频发缺陷**（已发生三次线上错位：行号截止、窗口错位、折叠行号漂移），应补一
个几何回归守卫，避免后续性能改动在此回归。

## 方案

性能三板斧，全部在既有架构（纯逻辑进 fx 纯件 + node 单测，DOM 胶水留 ui）内做：

1. **非结构编辑的标记缓存增量**：把 `textEditIsStructural` 的判定结果细化为
   「变更段（p, 旧段长, 新段长）」；纯字符编辑（无换行/括号/引号/#/tab/行首空白
   变化）时，对既有标记清单做**行级偏移修补**（变更行之外的标记逐字节不变——
   行号与行内偏移都稳定；变更行内标记按插入/删除位移偏移），并同步三个模型级
   缓存（缩进引导线 / 括号彩虹 / 合并标记缓存）的内容引用。`markClean` 语义
   从「跳过渲染」升级为「缓存已修补、直接复用」。
2. **光标行号 O(log n)**：窗口化缓存增存「行起点偏移数组」，打开/结构编辑时全量
   重建，纯字符编辑时不变（行数未变则行起点不变，零维护）；新增按行起点数组
   二分求行号的纯件，输入链中的光标行号计算全部改走它；`caretLineOf` 纯函数
   保留供既有调用与测试。
3. **输入链切分/GC 收敛**：同一输入事件内只做一次全量切分，行数判定、增量
   diff、窗口切片、标记窗口文本复用同一份行数组（进窗口缓存）；消除重复
   `split` 与重复字符串切片。

视觉/布局：

4. **三层几何对齐回归守卫**：CDP 探针在「100%/150%/200% 缩放 × 折叠开/关 ×
   深浅主题」矩阵下断言 gutter 行号、高亮层行、标记层行、当前行高亮四者逐行
   1:1 且与 textarea 光标行一致；探针发现的偏差纳入修复（历史三起错位均为
   该矩阵边缘组合漏测）。守卫脚本与断言归 `.scratch`（既有 probe/smoke 先例），
   不进 tests；修复仍走组件内即改。

## 用户故事

1. 作为用户，我希望 6000 行 .c 连续输入不掉帧（逐键 ≤20ms），以便大工程编辑
   跟手。
2. 作为用户，我希望缩小/放大字号、开折叠后行号/高亮/标记不互相错位，以便视觉
   始终可信。
3. 作为用户，我希望既有能力（括号彩虹 / 缩进引导线 / 查找 / 选中词 / 编译错误
   行内标记 / 折叠 / 撤销）在性能改动后行为不变，以便不破坏已习惯的工作流。

## 实现决策

- 延续既有架构：纯逻辑进 `fx/*`，DOM 胶水留 `ui/*`；不引入第三方编辑器内核。
- 标记增量修补做成可单测纯件：输入「旧标记清单 + 旧文本 + 新文本 + 变更段
  （p, 旧段长, 新段长）与变更行号」，输出修补后清单；规则：变更行之外不动，
  变更行内按「mark 起止与变更段的包含关系」分段偏移（整段在前→不变；整段在
  后→整体平移；跨段/包段→仅尾端平移）。非结构编辑保证变更段无换行无括号，
  故不存在「括号被插入/删除」的图景，深度值天然不变。
- 括号彩虹缓存与缩进引导线缓存各自带内容引用；非结构编辑时两者与合并标记缓存
  一起做同一份修补，避免 `currentMarks` 内任一入口看到旧内容引用而触发全量重算。
- 行起点数组随 `winBuild`（全量）与 `winPatchEdit`（非结构编辑不变）维护；新增
  纯件对「行起点数组 + 偏移」二分求 1 基行号，与 `caretLineOf` 语义一致（pos
  恰在换行符上 = 前一行行尾）。
- 输入链时序微调：先把「是否结构变更 + 变更段」一次算出，再决定走 winPatchEdit
  / 标记修补 / 全量路径；行数判定改用修补后的行数组长度（不再对内容二次 split）。
- 对齐守卫探针：读 DOM 几何（gutter 行号元素 top、高亮行 top、标记行 top、当前
  行高亮 top、textarea 光标行）逐行比对容差 ≤1px；缩放经既有 Ctrl+滚轮
  applyCodeZoom 路径，折叠经既有 Ctrl+Shift+[/] 与折叠箭头；输出矩阵结果表，
  失败行打印元素几何明细（入 `.scratch/code-editor-opt/`，不进 tests）。
- 性能验收以「CDP 同口径探针前后对比」为准：6000 行 .c 热路径单次 input
  ≤20ms（从 ~50ms），冷路径（打开后首次输入）≤60ms（从 ~186ms）；不引入帧率
  断言（与上轮口径一致）。

## 测试决策

- 最高既有缝 = `node --test tests/js/` fx 纯件单测：标记增量修补（插入/删除/跨段
  /多行不变/彩虹与引导线各自缓存）、行起点二分行号（越界/换行符上/空文）、
  变更段判定纯件。
- 交互行为 = CDP 探针（`.scratch/code-editor-opt/probe-*.mjs` 先例）：性能前后
  对比 + 三层对齐矩阵 + 冒烟抽样（保存/折叠/查找/括号彩虹仍可用）。
- 视觉改动走深浅两主题截图对比（`.scratch/code-editor-opt/*.png`）。
- 后端零改动；pytest 全量回归跑一次确认无回退；git 提交信息中文，照旧。

## 范围外

- 多光标 / 列选择 / Monaco / CodeMirror 内核替换 / 小地图 / 跳转定义 / 内容补全
  （沿用上轮 spec 范围外）。
- 顶栏与活动栏菜单化、底部面板布局重构、状态栏信息增删（无实测缺陷）。
- 输入法（IME）组合输入路径的进一步优化（本轮不动 composing 逻辑，仅保证不回退）。
- 后端/API 改动（零后端预算）。

## 实施结果（工单 01-04 结案后补记）

- 01 标记增量：落地（fx edit-patch + 三缓存同源修补；双轴 review 整改删除侧
  结构判定 + marksPartition）。
- 02 行号/配对/切分：落地（lineStarts 二分、pairScanCache + pairScanPatch、
  wordRangesPatch、winPatchRow 行级 DOM 修补、winRenderMarks 缓存命中放宽）。
- **实测诚实结论**：基线 6000 行 .c 文末逐键 ~50ms → 非叠加态（标点/空格/文末
  非词输入）路径明显下降（行级修补/窗口外零 DOM/缓存复用），残余：字母输入 +
  词高亮活跃时仍走状态重算 + 标记重画全量路径（词变化无增量捷径），实测
  ~25–45ms（机器噪声主导方差）——spec「≤20ms」对纯字符/标点类输入达标，对
  字母输入未达标，已如实记录于工单 02，不虚标。
- 03 对齐守卫：12 格全 PASS，未发现错位（无需组件修复）；守卫留作后续回归。
- 04 回归：node 1275 绿 + pytest 3159 绿 + 冒烟 5/5 + 双主题截图。
- 05 字母输入 + 词高亮路径收敛（追加工单）：渲染单点化（撤销 sync 尾部
  renderEditorMarks 二次全量重画）、winRenderMarks 状态标记单次拼接、
  updateWordMarks 省略 JSON 对比、静态缓存修补与 markClean 解耦——6000 行
  文末字母输入复测 **21.2–24.7ms**（从 ~38.9–45.8ms；纯字符/标点路径与对齐
  矩阵不回退）。
- 06 大文件打开惰性高亮（追加工单）：hl 惰性占位 + 单行现算回填、windowed
  不再预计算 currentMarks、宽度探针脱离文档流——精确拆解 fetch ~58ms +
  渲染 ~195ms ≈ 253ms；剩余大头 = 108KB textarea 全量 + 12.6 万 px 巨盒
  布局（架构固有，需 textarea 视口化，大改不在本轮）；滚动实测每事件
  ~4-6ms + GC ~3ms（无需优化）。≤80ms 未达标，如实记录。
