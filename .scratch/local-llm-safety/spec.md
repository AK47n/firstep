## Problem Statement

本地 LLM 路由已经承担多类低风险调用，但当前生产边界和运行过程不可观测：本地端点可能收到远程 API key；单次调用缺少统一的路由、耗时、重试和解析结果记录；不同错误类型的重试策略未充分区分，复杂工作流也没有统一的累计预算。结果是凭据边界不清、成本和质量无法量化、不可恢复错误可能被重复请求。

## Solution

建立第一批 LLM 稳定性安全带：本地请求默认不携带远程 API key；为每次调用提供不含敏感内容的结构化观测记录；按错误类别实施明确的重试策略，并为工作流提供累计尝试/时间/成本预算，预算耗尽时以明确的业务错误终止。

## User Stories

1. As a 本地模型用户, I want 本地请求不携带远程凭据, so that 配置本地服务时不会发生不必要的密钥传播。
2. As a 需要本地兼容网关的用户, I want 本地认证策略与远程认证策略分离, so that 我可以显式配置本地认证而不是复用远程 key。
3. As a 开发者, I want 每次 LLM 调用都有统一的结构化记录, so that 我能定位慢请求、重试、解析失败和路由选择。
4. As a 维护者, I want 观测记录不包含题面、源码和 API key, so that 日志可用于诊断而不泄露用户素材。
5. As a 用户, I want 不可恢复的认证和参数错误立即失败, so that 系统不会浪费时间和额度重复请求。
6. As a 用户, I want 网络错误、限流和服务端错误采用不同重试策略, so that 暂时性故障可以恢复而永久性故障能尽快暴露。
7. As a 用户, I want 复杂操作有累计预算, so that 多轮推荐、提炼或解析失败不会无限消耗时间和模型额度。
8. As a 用户, I want 预算耗尽得到明确的中文错误, so that 我知道应减少输入、调整配置或稍后重试。

## Implementation Decisions

- 本地 LLM 默认使用无认证请求；不新增本地 API key 设置项，兼容网关认证需求另立后续工单。
- 旧配置文件继续可读写；本次不破坏既有配置字段和默认路由行为。
- 观测记录采用仓库现有日志/本地结构化 JSONL 能力可承载的形式，不引入外部 tracing 服务。
- 记录 operation、provider、model、耗时、尝试次数、HTTP 状态、错误类别、解析状态、请求字节数及可用 usage；严禁记录完整请求体、题面、源码、Authorization 或完整端点密钥信息。
- 重试分类至少区分：不可恢复的 400/401/403/404、不含重试的其他客户端错误、429、网络错误、5xx、空内容/JSON 解析错误和领域校验错误。
- 保留现有调用接口与错误契约；新增能力通过薄层接入，不把 provider 细节扩散到业务域。
- 工作流预算以可选对象/上下文传递，缺省保持旧行为；预算字段至少支持累计尝试次数和累计耗时，成本/token 在 provider 有 usage 时记录并为后续限额留下扩展位。

## Testing Decisions

- 在最高现有 seam 测试：LLM transport/request 层锁定 headers、重试分类、观测字段和脱敏；业务层锁定预算终止与错误映射。
- 使用 Fake HTTP/LLM 响应验证不可恢复错误不重试、429/5xx/网络错误按策略重试、解析错误按独立上限重试。
- 测试本地请求不含远程 Authorization，远程请求行为保持兼容。
- 测试日志记录只含元数据，不含题面、源码、API key 和完整敏感 URL。
- 测试缺省预算不改变既有成功路径，预算耗尽在落盘或副作用前明确失败。
- 以全量 pytest、mypy 及既有 Node 测试作为批次验收。

## Out of Scope

- SSE job_id、断线恢复、取消与后台任务查询。
- Prompt caching、完整 OpenTelemetry、远程日志平台。
- 继续扩展 LOCAL_LLM_METHODS。
- 新增本地 API key 设置项和 UI。
- 真实工具链编译矩阵与 golden 赛题评测集。

## Further Notes

三个工单按依赖串行：01 凭据隔离 → 02 调用记录 → 03 重试分类与累计预算。每个工单独立 TDD、评审、验收和提交。
