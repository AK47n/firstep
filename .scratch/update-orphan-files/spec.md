# spec — 更新后盘上的文件与「官方包该有的」对不上：两个打包器的口径收成一处，删除清单改累计

> 缺陷单：`issues/01-orphans-after-multi-version-update.md`（发现于沙箱真机演练 B1，`sandbox-drill/01`）。
> **本 spec 的第一件事是更正那张单子的根因与判据**——它写的「删除清单只覆盖上一版 →
> 落后两版留下 1483 个孤儿」与本轮重新量出来的证据不符（见「补充说明 · 更正」）。
> 量具：`.scratch/update-orphan-files/measure-sets.py`（只读，可复跑）。

## 问题陈述

用户在**旧版**上点「检查更新 → 一键更新」（小发版路径）之后，工具根会进入一个
「完整包永远不会给的」状态，两个方向同时出问题：

1. **多出一批官方包里没有的文件（实测 1482 个）**：`library/revise-backups/**` 1481 个
   （本机库修订备份）+ 1 个 `*.exe`。它们**不是旧版留下的残渣，而是这次更新包自己写进去的**
   ——完整包按排除规则刻意不收本地备份目录与安装包，小发版包却照发。
   附带后果：开发者机器上的库修订备份（含被删模块的快照）随每次小发版发到每个用户盘上。
2. **少发新版新增的文件（实测 1 个）**：`00-START-HERE.txt`（面向新用户的那份说明）在完整的
   白名单里，却不在小发版手抄的那份白名单里 —— v1.1.1 的用户**升级后永远拿不到它**，
   而全新安装的用户有。

第三条是**潜在**的（本轮演练没演到，但机制成立）：删除清单
`removed.txt = 上一版清单 − 本版清单` 只覆盖一个版本区间，**跨版升级**的用户会永久留下
被跳过的那个版本删掉的文件；且**未被 git 跟踪但完整包发过**的文件（`sources/contest/**` 下的
构建产物）从不出现在任何小发版清单里，因此小发版路径永远清不到它们（完整包路径的删除清单
在这些文件从工作树消失后才会覆盖一次）。

**共同根因**：「哪些文件算产品文件」这套判据被实现了两遍——完整包是
`扫描工作树 ∩ 顶层白名单 − 排除规则`，小发版是 `git ls-files ∩ 手抄的顶层白名单`
（`tools/pack-update.ps1` 里那份数组）。两遍必然漂移，已经漂移了三处（白名单少一条、
排除规则整套没抄、删除清单的基线语义不同）。

## 方案

**把「产品文件集合」收成一处判据，两条更新路径的输出都以它为基准。**

- 判据本体（顶层白名单 + 排除规则）**只有一个家**，两个打包器都问它；小发版侧不再手抄白名单。
  于是小发版包与完整包对「哪些路径算产品文件」给出同一个答案：本地备份目录、安装包、
  缓存/日志/构建产物的判定一致，新增的顶层文件（如 `00-START-HERE.txt`）两条路径同时带上。
- **删除清单改成累计口径**：发布时写出的删除清单 = 「历史任一已发布版本发过、而本版不再发的
  产品文件」。判据仍然只有一条（本版清单里没有），但输入从「上一版清单」扩成
  「上一版清单 ∪ 上一版删除清单 ∪ 上一版完整包清单」。于是：
  - 跨版升级的用户也能清掉被跳过版本的删除项（潜在缺陷一并关掉）；
  - 老用户**不需要**换更新器：删除清单是数据驱动的，旧版更新器照单执行；
  - 仍然只删「发布过的名字」——用户自己补录的模块 / 归档的参考文件从不出现在任何发布清单里，
    因此**不可能被删**（这条是本方案与「按本版文件集合扫盘清理」那条危险修法的分界）。
- `library/revise-backups/**` 与同族的 `library/fix-backups/**` 对齐：移出 git 索引
  （盘上文件保留），本地备份不再进仓库、也不再进任何发布包。

用户可观察的结果：**任何升级路径走完，工具根里的产品文件与全新安装该版本完全一致**
（不多、不少、内容一致），而用户自己的库内容与素材一个字节都不动。

## 用户故事

1. 作为从旧版升级的用户，我希望升级后的盘面与全新安装一致，以便「我这台机器上是不是少了/
   多了什么」不再是一次性的谜题。
2. 作为从旧版升级的用户，我希望**新版新增的文件真的到我手上**（例如面向新用户的说明文件），
   以便我不必重新下一整包才能看到它。
3. 作为从旧版升级的用户，我希望升级不会往我盘上写**别人机器上的库备份**，
   以便我的工具根里只有产品文件和我自己的东西。
4. 作为跳版升级的用户（例：v1.2.0 → v1.2.2），我希望中间版本删掉的文件也被清掉，
   以便我不会留下永远不会再被使用的残留。
5. 作为在新版里自己补录过模块 / 归档过参考文件的用户，我希望升级**绝不**动这些内容，
   以便我的劳动成果不会因为「不在本版清单里」被当成废弃文件删掉。
6. 作为维护者，我希望「哪些文件算产品文件」只有一处判据，以便下一次新增顶层文件时
   不会只改一边（`00-START-HERE.txt` 就是这么漏掉的）。
7. 作为维护者，我希望这条修复**有静态守卫 + 本机可复跑的离线演练**（不依赖发版），
   以便它在没人盯着的时候也不会退化。
8. 作为维护者，我希望仓库里不再挂着本机库备份（1481 个文件），以便 clone / 打包 / 发布清单
   不再被这些与本产品无关的东西污染。

## 实现决策

### 判据单源：产品路径谓词

- 顶层白名单与四类排除规则（目录名 / 文件名 / 安装包通配 / 后缀）本来就都在
  `src/contest_generator/full_pack.py`（完整包扫描用它们）。新增一个**公开的纯谓词**
  「这个仓库根相对路径算不算产品文件」，由既有 `_exclude_reason` 收口改造而来
  （返回原因的中文可读字符串 → 判据本体；`scan_tree` 与谓词共用同一份，不许各写一份）。
- `tools/pack-update.ps1` **不再手写顶层数组**：它只负责 `git ls-files`（取候选）与调 Python 核心。
  筛选发生在 `src/contest_generator/pack_update.py`（谓词单一出处），`.files.txt` 由核心写出
  ——「zip 条目 == 清单」这条既有自检因此仍然天然成立。
- 保留小发版的取源语义（**tracked 快照**，不是工作树扫描）：谓词只决定「哪些 tracked 路径算产品
  文件」，不改变「只发 git 里有的东西」。
- 结果：白名单漂移不可能再发生（`00-START-HERE.txt` 自动进来）。

### 删除清单累计化

- 单源函数：`累积删除(上一版发行集合, 本版发行集合) = 上一版发行集合 − 本版发行集合`
  （排序输出、跳过空行与 `#` 注释），两个打包器都调它，不再各写一段差集。
- 「上一版发行集合」= **上一版小发版清单 ∪ 上一版小发版删除清单 ∪ 上一版完整包清单的 `files`**。
  三项都由上一版发布产物提供，打包器在 `-Baseline`（小发版是 `files.txt`，完整包是
  `manifest.json`）旁边按同名规则找；**找不到就大声失败**（宁可不发版，也不写出一个
  比用户盘面短的删除清单），并给一个显式的「首次发布」开关绕过。
- 完整包侧的删除清单同样走这条（它现在也只看上一版清单）。
- 更新器（`tools/update-app.py`）**零改动**：它已经按清单删除、已有路径校验（落工具根内、
  非普通文件跳过、已不存在跳过）。这正是本方案的价值——老用户的更新器就能执行新清单。
  范围仍限「清单里点名的相对路径」，不引入任何「扫盘找多余文件」的行为。

### `library/revise-backups/**` 移出 git 索引

- 与 `library/fix-backups/` 对齐：加忽略规则 + `git rm -r --cached`（**盘上文件保留**，
  本机工作流不变）。发布包的两侧口径此时已经独立成立（谓词排除），这一步清的是**仓库**。
- 顺带把「本机库备份不该入库」这条判断写进忽略规则的注释里（与 fix-backups 那行同款）。

### 验收（无发版依赖）

- **静态守卫**：谓词的真值表（含 `00-START-HERE.txt` 真、`library/revise-backups/**` 假、
  `*.exe` 假、缓存/日志假）；`pack-update.ps1` 里**不得**再出现手抄的顶层数组；
  小发版核心确实用谓词筛（夹具树里放一个被排除项 → 不进 zip、不进清单）。
- **累计删除清单**：单元测试覆盖并集语义 / 跨版删除 / 「删了又加回来不算删除」/ 注释与空行 /
  缺少上一版产物时大声失败。
- **本机离线演练**（可复跑，一条命令）：用既有重建脚本把沙箱还原成真 v1.1.1 → 用**本机打出的
  修好的小发版包**（不出网、不发版）走产品自带的更新器（`--no-stop --no-restart --skip-pip`）
  → 复算构成，判据 = **`not_in_official == 0`**（盘上不存在完整包不会给的产品文件），
  且 `sources/materials`、用户数据目录零触碰。
- 演练脚本与量具落在 `.scratch/update-orphan-files/`，原始输出落 `.txt`/`.json`。

## 测试决策

- **好测试**：只断言外部可观察量——「某路径算不算产品文件」「清单里有哪些路径」
  「盘上最终多出了哪些文件」。不断言实现细节（不测 PowerShell 内部变量、不测函数私有分支）。
- **接缝**（沿用既有，不新造）：
  - 谓词与打包核心 → `tests/test_pack_update.py` / `tests/test_full_pack.py`（两个既有文件的
    同族判据里加），夹具用临时目录手工搭树，不碰真仓库；
  - 真仓库口径的守卫（白名单漂移、包内路径预算）→ 既有 `tests/test_pack_update.py`
    的「跨包一致性」一组；新守卫放在同一文件，避免又多一个测试文件；
  - 离线演练 = `.scratch/update-orphan-files/drill-offline.py`（真机级，不进 pytest——
    它会清空沙箱、跑真解包，像 B1 一样属于演练面）。
- **判据强度**（本仓纪律）：每条新守卫都要有反向注入（把谓词放宽 / 把累计改成上一版差集 /
  把清单来源换回手抄白名单），注入后对应用例**必须转红**；探针落
  `.scratch/update-orphan-files/probe-guard-strength.py`（照
  `.scratch/update-restart-stale-service/probe-guard-strength.py` 先例：改坏 → 跑 → 复原 → 复核 sha256）。
- 既有守卫一个都不许动：`tests/test_pack_update.py` 的跨包逐字节一致性、
  `tests/test_full_pack.py` 的路径预算与清单形态、`tests/test_update_app.py` 的删除清单语义。

## 范围外

- **不做**「更新器扫盘清理」（按本版文件集合遍历工具根删多余文件）：它的边界无法安全划定
  （用户会往 `library/` 里补录模块、往 `sources/` 里放素材），而累计删除清单已经用
  「只删发布过的名字」拿到同样的收益。
- 不改更新器的停服 / 锁 / 重启协议（`update-restart-stale-service` 已封口）。
- 不动资料库增量包（`materials-*` 那一族）与 `materials_manifest` 的语义。
- 不重写历史、不减小 `.git`（第 7.4 节已拍板不做）。
- 不改 `src/contest_generator.egg-info` 是否随包分发（工单 01 的「附带发现」，另议；
  本轮只如实记账：它是完整包发、小发版不发的那一类差异，且被 `pip install -e .` 重写）。
- **本轮不发版**：线上资产一个字节都不动（真机 drill-01 要下到修好的包，留给下一个版本号）。

## 补充说明

### 更正（三条，都推翻了原工单的口径）

1. **「落后两版以上留下 1483 个孤儿」——数字与归因都不对。** 重新量（`measure-sets.py`）：
   沙箱盘面与 v1.2.1 完整包清单的差集 = **1482**，其中 **1481 个是 `library/revise-backups/**`、
   1 个是 `.exe`**，两者**都在本轮那个小发版更新包的条目表里**（`firstep-update-v1.2.1.zip`：
   1481 + 1 条），且沙箱里这 1481 个文件的 mtime 全是解包那一刻（`updater.log` /
   `last-update.json` 记 `20260919-113411`）。**它们是这次更新写进去的，不是旧版留下的。**
2. **「落后两版以上」这个场景 B1 根本没演到。** 那次发布的 `-Baseline` 就是 v1.1.1 的
   `files.txt`（与用户起点同版），算出的 727 条删除项**正好等于**两个清单的差集
   （`removed == files(v1.1.1) − files(v1.2.1)` 逐条相等）——一个版本区间的洞都没漏。
3. **真正「旧版发过、之后不再发、小发版路径清不掉」的那一类只有 205 个**
   （`sources/contest/**` 下的构建产物 / `.vscode` 等**未被 git 跟踪**的路径：它们在完整包清单里
   出现过，却从不出现在任何 `files.txt` 里），其中 106 个已被 v1.2.1 **完整包**的删除清单覆盖
   （完整包路径能清、小发版路径永远清不到）。这一条是真的，但它**不是**那 1483 个。

### 判据为什么不换成「与本版小发版清单比对」

那会把「完整包发、小发版不发」的那一大类（`sources/materials` 5081、未被跟踪但完整包发过的
`sources/contest/**` 204、`egg-info` 6、`library/masters` 2）全部算成「缺」，量出来的东西
与用户可感知的「我盘上多了不该有的东西」无关。**判定基准取「完整包清单」是对的**——
它就是「全新安装这一版该有什么」的定义；要修的是**让小发版包不再多发**，
而不是把尺子改成顺着缺陷量。
