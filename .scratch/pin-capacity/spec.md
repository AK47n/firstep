# 引脚容量诊断（生成期引脚冲突门禁的可操作数字）

## 问题陈述

用户点「生成工程」，拿到的是一条 **400 中文**：

> mspm0 引脚冲突：落盘后的 mspm0.syscfg 有 7 个引脚被两只实例同时占用，SysConfig 会直接
> 编译失败（Resource conflict）：… 出路：在引脚配置里改绑上述角色（或点「自动配置」一键
> 解开），或去掉冲突模块中的一个后重新生成。

这段话**没有数字**，用户因此三条都答不上来：

1. 这个选中集在**这块板**上到底可不可能实现？还是只是默认脚撞了、挪一挪就行？
2. 「自动配置」我已经点了（或点了没用）——它是解法，还是这条路本来就走不通？
3. 要砍，砍几个？砍谁？

真机取证（`.scratch/pin-capacity/verify-01-measure.txt`，14 个真机推荐集，本轮重跑逐字一致）：
**8/14 物理不可解**（solver 解完仍有冲突组），mspm0 5 个样本里 3 个不可解；2026H 一支
12 选中集解完剩 3 组，且**解后占用 31 脚 = 板上全部可用 IO，真空闲 0 脚**。这类选中集
无论怎么点「自动配置」都编不过——而现在的文案把「改绑」「一键」「去掉一个模块」三条出路
并列摆着，等于让用户盲试。

## 方案

生成期引脚冲突门禁（`syscfg_pin_conflicts`）命中时，在现有 400 文案里补一段**可操作数字**：

- 选中集规模与落点：`N 个模块 / M 个引脚落点`；
- 板上容量：`板载可用 IO K 脚，本次已占 C 脚、剩余 F 脚`；
- 门禁发现：`检测到 X 组同脚冲突`（逐脚清单照旧保留）；
- 一键配置的真实能力：跑求解器后 `解开 Y 组，剩余 Z 组无法靠改绑解开`（列角色）；
- 结论与最低代价：`空闲脚已用尽 / 仍有空闲脚` + `至少要去掉 W 个模块（W = 剩余冲突组中
  可让位模块的并集，下界）`，或（落点 ≤ 可用脚却仍无解）`与引脚数量无关，卡在能力/实例
  分配，须去掉或替换冲突模块`。

**只升文案、不新增拦截**：门禁的触发条件、判据与产物一行不改；前端零改动。

## 用户故事

1. 作为拿 400 的用户，我想要在错误里看到「落点 / 可用脚 / 占用 / 空闲」，以便判断这是
   「默认脚撞了」还是「这块板根本装不下」。
2. 作为已经点过「自动配置」的用户，我想要看到求解器解开了几组、还剩几组，以便知道按钮
   还会不会再有用。
3. 作为决定砍模块的用户，我想要一个下限数字（至少去掉几个），以便知道从哪儿开始动手，
   而不是把 12 个模块全试一遍。
4. 作为看到逐脚清单的用户，我想要每组的**可让位模块**被点名，以便两步之内定位到要砍的
   那个模块。
5. 作为拿到「落点 ≤ 可用脚却仍无解」的用户，我想要文案直说「与引脚数量无关，卡在能力/
   实例分配」，以便不去徒劳地板级改线。
6. 作为维护者，我想要判定量与 `/api/bindings/auto` 的同源（同一 `_role_entries` + 同一
   `auto_assign_bindings(resolve_default_conflicts=True)`），以便文案里的数字永不与按钮
   行为脱钩。
7. 作为维护者，我想要平台面收窄（stm32 / 板数据缺失 / 产物复核形态一律不补数字），以便
   存量 400 文案与既有测试逐字不变。
8. 作为回归守门人，我想要一条钉住真机 2026H 组合判定量的用例，以便后续库/母版漂移或
   判定量改错时立刻变红。

## 实现决策

- **单一新落点：域模块 `pin_capacity.py`**。放这里而不是塞进 `generator.py`：① 「引脚容量」
  已被拍板立为独立领域概念（命名硬约束：不得用裸「预算」）；② 本仓库已把 `budget.py`
  （LLM 请求体字节预算）立为同类模块先例——容量/预算类的**判定 + 文案**各占一个域模块。
  - `PinCapacityReport`（冻结 dataclass）= 判定的唯一形状：`modules` / `slots`（落点）/
    `board_io`（板上可用 IO）/ `occupied`（占用脚）/ `free`（剩余空闲脚）/
    `conflict_groups`（门禁发现）/ `moved`（求解器搬动条数）/ `unresolved`（剩余冲突组数）/
    `unresolved_roles` / `unresolved_modules`（剩余冲突组内可让位模块并集，保序去重）。
  - `diagnose_pin_capacity(manifests, platform, board, bindings) -> PinCapacityReport`。
  - `render_pin_capacity_diagnosis(report) -> str`（纯渲染，输出注入 400 文案的数字段）。
- **判定量复用现成两件**（单源，不新造）：
  - 落点与占用脚 = `pin_bindings._role_entries`（绑定优先、缺省声明默认脚；与
    `_shared_groups` / 默认脚消解相共用同一推导，两处各写一遍必漂移）；
  - 可解性 = `auto_assign_bindings(..., resolve_default_conflicts=True)` 的 `shared` 中
    `kind == "conflict"` 的剩余组（与生成页「自动配置」按钮**同一个求解器、同一个开关**）。
  - 板上可用 IO = `board.pins` 里 `capabilities` 非空的脚数（mspm0 地猛星 = 31；与
    `_first_pin_without_conflict` 的候选脚域同口径）。
- **口径三条（用户拍板定稿）**：
  1. **可用 IO = 整板可用脚**（不是「扣掉默认布局已占的脚」），另报「占用 / 剩余空闲」；
  2. **以 solver 剩余组为准**：落点数只作背景（**上界**，合法共享会省脚），
     `至少要去掉 N 个` 由剩余冲突组推出；
  3. **落点 ≤ 可用脚却仍无解** → 另起一句，明说与引脚数量无关、卡在能力/实例分配。
- **判定量与门禁已在手的事实对齐**：门禁已解析该份写盘 syscfg；角色实测占用脚数 =
  「裁剪后 syscfg 模型里被角色落点覆盖的脚」。**上界用 `slots`（角色落点数）**，
  并把「占用脚数」如实并报——两者不是同一个数（2026H：42 落点 / 27 占用），
  只有并报才既不灌水也不误导。
- **「至少 N 个模块」的语义（下界，必须诚实标注）**：N = 剩余无解冲突组内**可让位模块的
  并集**大小（保序去重）。每个无解冲突组至少要去掉其中一方 → N 是下界；文案不声称这是
  精确最小值。**不要**用 `ceil(落点缺口 / 平均脚数)` 之类的推算冒充精确值。
- **门禁只加合成，不改判据**：`_check_syscfg_pin_conflicts` 的触发条件、`by_pin`/`conflicts`
  判定、逐脚清单与排序**一行不动**；只在 `raise` 前调诊断器，把渲染段插在逐脚清单与
  「出路：」之间。
- **两根降级分支（缺省文案逐字不变）**：`context.board is None`（板数据缺失）或
  `manifests` 为空（产物复核形态 `run_generation_gates(corpus, [], platform)`，无选中集
  知识）→ 不补数字，照旧抛。stm32 根本不到这里（门禁首行按平台早退，ADR 0010 不动）。
- **性能**：诊断多跑一次「裁剪 + 求解」。mspm0 选中集规模 ≤ 15 模块 / 40 脚量级，
  `_MAX_DEFAULT_CONFLICT_MOVES = 32` 已封顶迭代；实现时**实测一次门禁耗时**并记进工单。
  只在**即将抛错的路径**上调用，零冲突路径零新增开销。
- **不改动面（显式写死，防跑偏）**：`/api/bindings/auto` 端点契约不动；`webapp.py` 不动；
  `static/` 不动；`docs/adr/0010` 不动；`SyscfgPinConflictError` 的错误类别与 400 映射不动；
  不新增门禁、不改门禁表顺序。

## 测试决策

- **seam 取最高既有缝，不新开测试缝**：直接测门禁入口
  `_check_syscfg_pin_conflicts(corpus, manifests, PLATFORM_MSPM0, GateContext(bindings=…, board=…))`
  —— 既有用例已在此缝合上（`tests/test_generator.py` 的
  `test_syscfg_pin_conflicts_*` 系列，语料 = 真母版 `mspm0.syscfg` 文本、板 = 真
  `mspm0-dimx.json`），无新夹具、无新接口。
  另对 `pin_capacity` 的两个纯函数直测（判定量字段 + 渲染段含数字），**不 mock、不测私有实现**。
- **好测试 = 断言外部可见的文案数字**：测的是「用户能读到什么」，不是「函数怎么算」。
  数字断言用**本单实测钉死**的真机口径（2026H 组合），不写宽泛范围。
- **回归守卫用例（本单最有价值的一条）**：`2026H` 13 模块集（12 选中 + 依赖展开）→
  `slots == 42`、`occupied == 27`、`board_io == 31`、`conflict_groups == 7`、
  `unresolved == 3`；文案须含「42」「31」「27」「3 组」与三个无解角色对
  （`oled.OLED_SPI_SDA`、`motor.BIN2`、`motor.BIN1`）。库/母版漂移或判定量改错 → 立刻红。
- **三条反向守卫**（防「到处加数字」）：① 只选 `motor` + `servo` → 报告 `board_io == 31`
  且 `unresolved == 0`，文案说「可用自动配置解开」而**不**说「至少要去掉」；② `GateContext()`
  （无板无绑定）→ 文案逐字等于现状、不含「可用 IO」段；③ `manifests == []`（产物复核）
  → 同②；④ `PLATFORM_STM32` → 门禁直过（既有用例已钉，不动）。
- **既有用例不许改**：`tests/test_generator.py::test_syscfg_pin_conflicts_red_real_machine_combo`
  的逐脚计数断言（`message.count(f"{pin}：") == 7`）与新段不得互相干扰 —— 新段不得使用
  `"<PIN>："` 形态（否则计数被污染）。这条是实施时的硬约束。
- 既有测试先例（照抄形态）：`tests/test_generator.py` 的
  `_real_mspm0_syscfg_corpus` / `_real_mspm0_manifests` / `_mspm0_board` 三个夹具。
