## ① 桌面同名工程 → 覆盖确认不可达（真 bug，已修）

**证据（W 节，注入与 `webapp.GenerationConflictError` 模板逐字同形的 400）：**

```
注入闸门：命中=true（injected=1）；#generate-msg=「请求失败（HTTP 400）：桌面上已有同名工程「W-inject」：…」
确认弹窗 = 0                      ← 修前：根本没有弹窗
```

**根因（源码三处对齐）：** `app.js` 的 `handle()` 抛 `parseHttpError(...).text`；
`fx/errors.js` 的 `parseError` 给**所有**带状态码的错误加 `请求失败（HTTP N）：` 前缀；
而 `fx/generate.js` 的 `isConflictError` 判的是 `indexOf(CONFLICT_MSG_PREFIX) === 0`
（打头）。于是 `generate-core.js:663` 的分支恒假 —— **识别冲突 → confirmModal →
重发 `overwrite:true`** 整段是死代码。

**为什么测试没拦住：** 单测把**没前缀**的原始文案喂给 `isConflictError`（函数行为对，
但输入不是真机上那份）；原 headless 冒烟把 `apiPost` 整个 mock 掉，绕开了 `fx/errors`。
引入时点 `5d636400`（工单 11 评审整改统一错误前缀）—— 覆盖保护当时的 `handle()` 没有前缀。

**修法：** 判据从「打头」改「包含」（`includes`），一处改动；不改 `parseError` 的统一
前缀（那是刻意的展示口径，全站依赖）。

**修后实测：** 弹窗文案 =
「覆盖生成？ 桌面上已有同名工程「W-inject」：旧工程将先备份为「W-inject.bak」，然后
覆盖生成全新工程。如需找回旧工程，把桌面上「W-inject.bak」改名回「W-inject」（生成后
也可在结果区一键恢复）。」；取消支路不重发、原 400 文案留在界面。

## ② 文件树点文件名打不开（真 bug，已修）

**证据（Y 节 + `probe-tree-hit` 几何取证）：**

```
locator.hover: Timeout — 「✎ 重命名 … from <span class="code-tree-actions"> subtree intercepts pointer events」
行宽 225px；按钮正中央命中 = BUTTON.code-tree-act（✎ 重命名）
操作区容器 x=108 w=131 → 横向覆盖行宽 58%；可点区只剩左侧 0–108px
```

**根因：** 行操作区是绝对定位浮层（`right:0; z-index:2`）盖在 `width:100%` 的文件名按钮上，
两区几何完全重叠。「行右预留 46px」只做在按钮 `padding-right` 上，不构成命中测试屏障。

**走过的弯路（留痕）：** 先试「收窄容器宽度」（`width:fit-content`）——**治不了根**，
实测容器仍 131px（绝对定位盒 + `inline-flex` 被块化，宽度由包含块决定）。
根因是几何重叠，所以修法必须让两区**不重叠**：文件行改 flex 兄弟
（按钮 `flex:1 1 auto` / 操作区 `flex:none`），事件委托一字未动。
修后：按钮 170px、操作区 55px，**按钮正中央命中 `SPAN.code-tree-name`**。

## ③ 认知纠正（不是 bug，但必须写下来）

**「手动输出目录二次生成不弹覆盖确认」** —— 审计脚本第一版把它判成 FAIL，
理由是「同名工程应该给覆盖选择」。**判据错了**：

源码（`webapp._resolve_generation_output_dir:1097`）写得很清楚 —— 手动目录的 verdict
**恒为 `"manual"`**，覆盖确认分支只对**桌面模式**的 `verdict == "exists"` 生效；
手动目录非空由 `generate_project` 的非空检查兜底 400「输出目录已存在且非空，拒绝覆盖」。

所以：**「拒绝 + 不静默改名 + 说明原因」才是手动目录的正确行为**，弹确认是桌面模式的事。
（本轮实测手动目录二次生成确实是「拒绝 + 说明 + 原工程完好」，桌面模式的确认弹窗另由
W2b 注入验过 —— 见 ①。）

这条与上一轮「把正确占位当过期视图」是同一类错误的另一个面孔：**判据只该描述「绝不该
出现的事实」，不该描述「我以为应该出现却没出现」**（脚本文件头第 ③ 条）。

## 方法记录（本轮最值钱的三条）

1. **「唯一真实入参」必须进判据**：`isConflictError` 的单测一直在给函数喂**没前缀**的
   文案 —— 函数行为没错，但真机上它拿到的是 `handle()` 加过前缀的那份。**守卫要喂
   生产路径真实产生的那份输入**（要么走 `parseHttpError`，要么把形态钉进用例）。
   这类 bug 的共同形态：**mock 或直调绕过了中间一层**。
2. **判据要「对着几何量」而不是「对着感受量」**：②修的时候我先试了「收窄容器」
   （听起来对症），实测宽度根本没变；只有把 `elementFromPoint` 沿行横扫、量出
   「谁在什么 x 上」之后，才看清根因是**两区几何重叠**而不是容器太宽。
   **先量，再改**。
3. **`hover` 超时日志本身就是证据**：playwright 的
   `… subtree intercepts pointer events` 直接点名了肇事元素 —— 它比「点了没反应」
   这种描述精确得多，值得在报告里逐字保留。

**本轮脚本自身的失误（如实记录，全部留在脚本注释里防重犯）：**
① 把「手动目录」按「桌面同名工程」判（见 ③ 认知纠正）；
② 点完错误行**立刻**读 DOM（跳行是同步的、但编辑器加载是异步的）→ 误报「跳错行」；
③ 判 `led_instances.h` 里有没有界面选的脚，用了 `txt.includes(pinned)`，而盘上写的是
   `GPIO_C` + `Pin_13` 两列（mspm0 更是只写进 syscfg 的 `$assign`）；
④ 在视口外（行 y=1517 / 视口 900）做 `elementFromPoint` → 全返回 `null`，
   据此得出过一条假「命中元素」（**先 `scrollIntoView`，再量**）；
⑤ 文件行文件名字段用 `#new-files input` 撞上别的节点 → `collectFiles` 收空 →
   表单本地拦下（"至少需要一个源文件"），X1 变成假红（应按 `placeholder` 定位）；
⑥ **固定 `sleep` 读异步终态**：模块库入库 / 改简介走 LLM 一致性校验（`_retry_parse`
   会整次重试），固定 3s 会把「还在路上」读成「没有提示」——X1 / X3 因此各误报一次。
   修法：`waitForFunction` 等真终态（提示非空 / 按钮复位）；
⑦ 用 PowerShell 的 `Set-Content -Encoding utf8` 回写审计脚本 → 中文双重编码、
   脚本整份报废重写；用 `Tee-Object` / `>` 落日志 → UTF-16LE 乱码日志全废。
   —— **Windows 上别用 PowerShell 回写 UTF-8 文本**；已加结构守卫
   `tests/js/windows-text-encoding.test.mjs`（自有文本文件不得带 BOM / 不得是 UTF-16 /
   不得含 U+FFFD；白名单只有 `ui/files.js` 里那个「故意用来判 UTF-8 是否解坏」的字符）。
