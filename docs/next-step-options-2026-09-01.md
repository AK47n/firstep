## 二、用户已提过但未动的方向（.scratch 存量）

### 1. custom-peripherals：库外外设声明 + 任务多文件输出（spec 完整 draft，等拍板）
- **动机（用户原话要点）**：「任何一道题都能按照生成流程做出来直到做完」；「我们主要是做控制题的，侧重方向是控制题目」。2026D（多旋翼飞控）/2026E（机械臂）等控制题需要库外硬件（无刷电调、超声波、机械臂机构、电磁铁吸盘……），当前任务推进只能改 main.c，且 LLM 无库外外设接口可调 = 做不完。
- **方案要点**（`.scratch/custom-peripherals/spec.md`，114 行完整）：
  - C1 库外外设声明：输出目录 `.contest_custom_peripherals.json`（name/role/wiring/notes），用户任务推进区维护；拆解（plan_tasks）与执行（execute_task）prompt 注入外设段；无外设 = 现行为逐字节不变。
  - C2 任务多文件输出：execute_task 输出双态（纯文本 = 只改 main.c 旧契约；JSON 多文件 = main.c + `custom/<slug>.c/.h`），键名白名单防逃逸；新增文件经 `patchers.register_extra_files` 登记进 .uvprojx（Custom 组 + IncludePath）/ .cproject（sourceEntry + buildIncludePath）；备份/回滚/编译验证零改动复用。
- **价值**：直接解决「控制题做不完」的最大剩余痛点；同时解决复杂控制题单文件膨胀。
- **成本**：spec 已完整，估 4-5 个纵向工单；风险中低（LLM 双态解析 + 双平台工程登记是主风险面）。

### 2. task-feedback：任务反馈闭环（spec 完整，3 issues 未动）
- 痛点：任务推进执行后，学生实际编译/验证的结果与现象没有记录回路，AI 无法针对「跑偏/炸机/卡死」继续反馈；现状只有一元「已完成」note。
- 价值：控制题调试期的持续质量闭环；与 custom-peripherals 同属「做完 + 做好」。

### 3. handoff-prompt：交接提示词 + 生成工程 PDF 附件（1 issue，无 spec）
- 现状：步骤 11 交接提示词是纯文本（复制给外部 AI）；未提交对话无法随工程带走。
- 价值：小；体验收尾性质。

### 4. vision-eyes：GLM-4V 视觉通道（spec 4 issues）
- **注意：可能已被取代**——视觉图注已通过 DeepSeek 官方视觉端点落地（工单 topic-vision-notes/01-03 + vision-deepseek-native/01 + topic-vision-render/01-02，三级降级：渲染视觉优先 → 文字标注兜底 → 内嵌栅格图兜底）。vision-eyes 是更早的 GLM-4V-Flash 方案，**建议先确认是否废弃**再决定是否归档。

## 四、推荐

1. **先立 custom-peripherals** —— 它是唯一「用户自己提过、spec 已完整、且直接指向『任意控制题做完』」的方向；与「逐器件补录」互补而非竞争（通道先行，B1 随后按需补录）。

3. **B3 / handoff-prompt 顺手收** —— 低风险收尾。
4. **体验类维持不动**（C2 否决、C1/C3 非重点照旧），除非本清单让你改口。
