# 优化方向可行性深挖

> 日期：2026-08-18。配套文档：`docs/improvement-review-student-experience.md`（方向清单）。
> 本文逐个方向核实代码缝、评估工作量/风险/依赖，给出推荐实施顺序。所有结论基于当前工作区代码。

## 方向修正（2026-08-18 用户决策）

用户定调：**主要精力做"新题目"**——即提升工具对新赛题的支持能力（新题覆盖、快速出可用工程），体验类功能不是重点。据此：

- **C2 工程历史：否决，不做**（存储占用顾虑 + 非新题核心）。
- **C3 工程问答 / C1 离线模式：降级为非重点**（体验/环境类，排最后，除非有新题场景需要）。
- 优先级重排见文末「新题导向的实施顺序」。

## 先决事实（影响多个方向）

1. **评分表默认保留在题面里**：`topic_library.py` 确定性拆条的题面 = 「标题行起点到下一题标题行的原文段落（含评分标准表），零 AI 改写」；「修剪评分汇总」只是校对阶段的可选项（用户手动删）。→ A1 数据源天然可用，只要引导学生粘贴完整题面。
2. **写盘缝 = `generator.generate()`**：README 先例（`generator.py:890`，patcher 之后写、纯新增文件、逐字节契约不破）。→ A2/A3 的新产物照此模式加即可，不改任何既有文件。
3. **LLM 操作缝 = `llm.LLM` 抽象 + `RoutingLLM`**：新增操作 = 接口加方法 + DeepSeek 实现 + （可选）本地路由；JSON 解析已有 `_retry_parse` / `_unwrap_json_fence` 成熟底座。
4. **stm32 母版 ml_libs 已有 `ml_adc.c/h`、`ml_pwm.c/h`**；参考库已有 15 条 ADC12 例程、舵机例程（塔克R3-DB20-舵机角度控制）、定时器捕获例程。→ B1 的 adc/servo 素材现成，成本远低于预想。
5. **前端零持久化**：唯一 sessionStorage 用途是 tabId（`index.html:1074`），步骤 1-9 全部配置在内存。→ C2 是全新功能而非修补。

## A1. 评分标准 → 可执行验收清单

- **可行性：高。** 数据源在（评分表含于题面）；逐句编号机制（`selection._number_topic_sentences`）已能覆盖评分表句子；README（`readme.py`）与交接提示词（`index.html` 步骤 11 组装）都是确定性渲染，注入新段不动既有内容。
- **改动范围**：
  1. 新增 LLM 操作 `parse_score_points`（新 system prompt + 结构化输出 `评分点 {部分, 描述, 分值, 对应句号}`，域解析 + 校验放域层，照 `build_module_selection` 先例）；
  2. 前端步骤 2 或步骤 5 展示评分点清单（可勾选/对照）；
  3. README 加「评分点验收清单」章（复用 `render_readme` 扩展参数，缺省逐字节不变）；
  4. 交接提示词加评分点段。
- **工作量**：3-4 个纵向工单（LLM 操作+域模型 / 前端展示 / README+交接注入 / 回归测试），约 1-2 天。
- **风险与对策**：低。评分表格式多样（表格/文字），解析可靠性用收敛/重试兜底（先例现成）；对无评分表的题面优雅降级（空清单不渲染新章）。
- **依赖**：无。A3 依赖本方向（评分点清单是演示脚本的输入）。

## A2. 设计报告草稿生成

- **可行性：高。** 素材全在生成侧：题面、平台、模块清单、引脚表（`readme._pin_rows` 数据源可复用）、main.c 骨架。写盘缝 = `generate()` 内 README 同款位置。
- **改动范围**：
  1. 新 LLM 操作 `generate_report_draft`（输入 = 题面 + 模块摘要 + 引脚表 + 骨架摘要，输出 = 方案论证/软件流程章节）；
  2. 确定性模板组装（工程概览/框图/选型表/引脚表/测试记录模板 = 模板层，方案论证/流程 = LLM 输出层，隔离保证确定性部分稳定）；
  3. 写盘 `设计报告草稿.md` + 生成摘要展示 + 前端入口。
- **工作量**：2-3 个工单，约 1 天。
- **风险与对策**：低。LLM 生成的「方案论证」可能虚——定位为草稿 + 模板强约束章节结构；报告素材与工程数据一致性靠确定性模板保证（不吃 LLM 的部分绝不 LLM 化）。
- **依赖**：无。与 A1 可并行（建议并行，共享写盘缝但互不阻塞）。

## A3. 演示脚本生成

- **可行性：高（依赖 A1）。** 纯确定性渲染：评分点清单 → 步骤/操作/预期现象。
- **改动范围**：`render_readme` 或独立模板函数，输出 `演示脚本.md` 进工程根；前端零改动（随 README 一并展示）。
- **工作量**：1 个工单，约 0.5 天。
- **风险**：低。无评分点清单时降级为「按功能需求层生成演示顺序」。
- **依赖**：Blocked by A1（评分点清单）。也可先行用功能需求层做 v1。

## B1. 高频外设模块补齐（adc / hc_sr04 / servo / dht11）

- **可行性：高（adc、servo）/ 中（hc_sr04、dht11）。**
  - adc：stm32 内嵌母版 `ml_adc`（led/oled/delay 内嵌先例，files 空）；mspm0 参考库 15 条 ADC12 例程（单次转换/序列通道/电源电压监测等）→ 提炼驱动切片。
  - servo：stm32 有 `ml_pwm`（pwm 已类型级解锁），mspm0 有 PWM 跨族迁移底座；参考库有「塔克R3-DB20-舵机角度控制」→ 50Hz 角度映射封装，工作量最小。
  - hc_sr04：GPIO 触发 + 定时器输入捕获回波；mspm0 有「定时器捕获占空比与周期」例程，stm32 有 ml_tim。
  - dht11：单总线位时序读取（stm32 常用 GPIO 模拟），无现成素材，需新写 + 真机验证。
- **改动范围**：每模块 = manifest + 双平台代码（或内嵌母版）+ 编译矩阵验证 + 结构测试；补录流程现成（模块库 UI + AI 简介校验）。
- **工作量**：adc 约 0.5-1 天、servo 约 0.5 天、hc_sr04 约 1 天、dht11 约 1 天（含真机/编译验证）；可逐模块独立工单。
- **风险与对策**：中低。未上板验证的模块按现有惯例标记 `verified: false` + 平台警告（`selection.check_platform_warnings` 已展示）；推荐链路自动受益（库内命中后不再是「库外建议」）。
- **依赖**：无，各模块独立。

## B2. 题型决策骨架模板

- **可行性：中。** 素材已有（参考库「21F-巡线送药决策例程」「26H-滚球巡线决策例程」「car-1-1-巡线模板-mspm0」），但**机制不存在**：`skeleton.py` 是纯文本接口块 + LLM 现写，无题型概念；main.c 决策逻辑目前每次 AI 现写，质量波动。
- **改动范围**：题型声明（词表/库条目）→ 前端选题型 → 骨架 prompt 注入题型模板段（状态机骨架 + 调度结构）→ 双平台回归。涉及 `skeleton.py` / `llm.py` / 前端步骤 8 / 新素材组织。
- **工作量**：3-4 个工单，约 2-3 天。
- **风险与对策**：中。最大风险 = 「题型」的抽象设计（怎么定义、放哪、与 ADR 0009「决策逻辑不进模块」的关系）；需要先 spec 决策（建议题型 = 参考文件库条目的结构化引用 + prompt 模板，不新建库）。骨架静态自检（`sanitize_skeleton`）可兜底模板注入的幻觉调用。
- **依赖**：无，但建议排在 B1 之后（先扩大模块覆盖再谈决策框架）。

## B3. 可选配套落地（filter 之于 uwb_uart）

- **可行性：高。** CONTEXT 已记录立项；机制 = manifest 可选依赖声明 + 生成器条件编译宏 + 前端勾选。先例参考 `python_artifact`（manifest 能力块 + 渲染钩子）。
- **改动范围**：manifest 新字段（可选依赖）+ `selection` 展开/校验 + `uwb_uart.c` 条件编译 + 前端 UI + 测试。
- **工作量**：1-2 个工单，约 0.5-1 天。
- **风险**：低。但注意 uwb_uart 现在**必需依赖** filter（include + 调用写死），可选化要动模块代码并回归双平台编译。
- **依赖**：无。低挂果实，可随时收。

## C1. 断网 / 无 Key 现场模式

- **可行性：中。** 本地路由机制已存在（`LOCAL_LLM_METHODS`，现 6 个方法走本地；改常量即改派发），但有两个结构性约束：
  1. 本地失联策略 = 「大声失败，不自动回退远程」（`LOCAL_LLM_UNAVAILABLE_MESSAGE`）——离线模式需要新策略决策（显式切本地 vs 自动降级）；
  2. **纯确定性离线生成不存在**：骨架/修复/推荐全依赖 LLM；离线路径 = 默认模块布局 + 模板骨架（确定性），与「AI 生成」哲学并存需要 spec 决策。
- **改动范围**：本地集扩展到骨架/修复（试本地模型质量）；新增离线确定性生成路径（模板 main.c + 默认模块集）；前端模式切换 + 设置。
- **工作量**：2-4 个工单，约 2-3 天。
- **风险与对策**：中。本地 7B 模型做 `select_modules` 收敛循环质量存疑（不建议本地化）；骨架/修复可试（质量不足维持现状）；离线确定性路径是产品决策，需要用户拍板形态（完整性 vs 简单兜底）。
- **依赖**：无。

## C2. 会话持久化 + 工程历史

- **可行性：高。** 纯新增：前端 localStorage 序列化步骤 1-9 状态（题面/平台/模块/绑定/实例/输出目录）+ 恢复；后端新增「工程历史」记录（生成时写一条 JSON：输出目录/平台/模块/时间/状态）+ 列表/续修/打包 zip 端点。
- **改动范围**：前端状态保存/恢复（index.html 大量状态变量，需要统一序列化点）+ 后端历史存储（`entry_store` 先例）+ 历史页 UI。
- **工作量**：2-3 个工单，约 1-2 天。
- **风险与对策**：低。序列化要覆盖新状态（多实例/绑定）——建议状态快照 + 版本号，恢复失败静默降级为空白（不阻断）。
- **依赖**：无。

## C3. 工程问答助手

- **可行性：中。** 技术缝全在：目录文件读取（`treewalk.iter_project_files` + `budget` 预算先例）、SSE 流（先例多）、LLM 操作（新增问答方法）。但这是**新页面 + 会话式交互**，UI 与状态管理工作量占比高。
- **改动范围**：新 tab 或生成页内面板：选目录 → 装配上下文（题面 + 工程文件摘要 + 预算截断）→ 问答流（SSE）+ 会话历史（内存）。
- **工作量**：3-4 个工单，约 2-3 天。
- **风险与对策**：中。上下文预算（工程文件可能很大）用现有 `budget.py` 口径；首版只读 main.c + 模块头文件 + 题面，限制范围保质量。
- **依赖**：无。

## 新题导向的实施顺序（用户定调后）

**核心逻辑**：新题的痛点 = ①新题用到的外设库内没有（只能"库外建议"）②新题决策逻辑每次现写（骨架质量波动）③新题的评分表没被利用（丢分）。按痛点排序：

| 序 | 方向 | 解决的新题痛点 | 成本 | 风险 |
|---|---|---|---|---|

| 4 | 题库 + 参考素材补录（新题拆条入库、决策例程归档） | 新题入口与学习素材 | 0.5-1 天/批 | 低 |

| 6 | A3 演示脚本 | 现场演示（依赖 A1） | 0.5 天 | 低 |

| 8 | C1 离线模式 / C3 工程问答 | 非重点，仅新题场景需要时再做 | 2-3 天 | 中 |

## 决策点分析与结论（2026-08-18）

1. **A1 评分点解析位置 → 并入推荐链路输出**（`select_modules` 加 `score_points` 可选字段）。理由：功能需求层逐句对照机制现成（评分表句子可编号）；收敛核验轮顺带自检；推荐缓存直出 done 载荷时免费复用；零额外 LLM 调用。不并入步骤 2（纯文本契约、可跳过、跨调用透传难）；不做独立调用（多一次调用 + 两次读题可能不一致）。
2. **A2 系统框图 → 确定性生成文本层次图，不做 Mermaid**。理由：框图节点（模块依赖 `manifest.dependencies`）与连线（引脚表）全是结构化数据，纯函数渲染不吃 LLM、不会语法错、与工程数据逐字节一致；LLM 只写方案论证文字。Mermaid 渲染依赖学生本地工具且 LLM 生成易语法错，不做主图。
3. **B2 题型载体 → 参考库条目加 `topic_type` 标记 + 按题型结构化注入**。理由：决策素材已在参考库（21F/26H/car-1-1 三条例程），重复存储违背「库即数据库」；参考库有 `anchor_kind`/`platform` 字段先例，加词表字段是同一模式；注入机制需小扩展（框架代码段走确定性注入、学习说明走 LLM 段）。独立模板库留给素材量大了之后的 expand-contract。
4. **C1 离线确定性生成 → 值得做，先做确定性骨架**。理由：`/api/generate` 缺的只是 main_c 字符串；确定性骨架 = 模板 main.c（现成）+ 按 `resolve_dependencies` 依赖序机械生成 init 调用 + TODO 区，纯函数 + `sanitize_skeleton` 兜底，约 1 工单；无 key 编译链路现成，接上即闭环。本地模型扩展：骨架/修复可试，`select_modules` 不建议本地化（收敛正确性依赖模型自检，7B 质量存疑）。**注：此方向已因「新题导向」降为非重点，仅新题现场场景需要时再做。**
5. **C2 工程历史存储 → 已否决，不做**（用户决策，见文首方向修正）。
