# 完整包资产名保持 ASCII（`firstep-full-<tag>.zip`），不改中文名

新用户下载体验特性（工单 `newuser-download`）曾设想：把完整包资产改成人话名
（如 `firstep-完整包-v1.1.1.zip`），让新用户在 Releases 页上一眼知道该下哪个。
**决定：不改**，资产名继续用 `firstep-full-<tag>.zip`；新用户的可发现性由
Release 说明正文前两行 + README「获取方式」+ 包内 `00-START-HERE.txt` 承担。

**关键决策：**

1. **改名必然连带改机器清单，而清单是程序产物**：工具内「检查完整包」按**清单里的
   `zip_name` 去 Release 上找同名资产**（`full_update._parse_parts` → `resolve_part_url`，
   逐字匹配 `assets[].name`）；资产名与清单名不一致时返回空表 → **整条链路判「不可下」**。
   也就是说改名不是改个文件名，而是「改名 + 手改 2~4 MB 的 `manifest.json` + 重算
   `sha256.txt`」——在发版夜里手改程序产物，是把一个展示问题换成一次全量链路故障。

2. **上传侧对非 ASCII 名的可靠性没有证据，且有反向证据**：`docs/agents/releasing.md`
   记着「gh CLI 上传中文文件名会把附件名替换为 `default.txt`」（2026-09-13 发版时踩到）。
   要推翻它只能**真上传实测**，而实测本身有风险：在同一 tag 下上传第二个 zip 资产，
   会让「按名字找不到 → 整条链路判不可下」，即测试动作本身可能打断已装用户的更新，
   除非另开一个一次性 tag 的 Release 来试——成本与收益不成比例。

3. **收益已经被更便宜的手段拿走**：新用户真正需要的不是「文件名带中文」，而是
   「一眼知道该下哪个」。实测同样有效且零风险的做法：README 只指一个文件、
   Release 说明**前两行固定**写「新用户只下这个 / 已装用户不用看这里」、
   包内第一个文件是 `00-START-HERE.txt`（名字前的 `00-` 让它排序第一）。
   这三处已经落地并有守卫钉住。

4. **重新评估的条件（写给将来的人）**：若出现「在一次性 tag 上实测确认 GitHub 原样接受
   非 ASCII 资产名」+「确认 `gh` 版本不再做替换」两条证据，可以在**下一个大版本**（tag 与
   资产名可同步规划）按 `releasing.md` 的「附件命名注意」流程实施：改打包器产出名 →
   同步改清单 `parts[].zip_name` → 重算校验和 → 在**同一个 release** 里绝不同时存在新旧两种
   zip 名（否则新用户又面对二选一）。**不允许**在已发布 tag 上原地改名（老版本用户的
   工具按老名字找资产，改了它们就更新不了）。

**与既有机制的关系**：`firstep-update-*`（小发版四件套）的资产名同样**不得改动**——
工具内更新按前缀发现资产，改名即断已装用户的更新链路。这两条一起构成资产命名的不变量：
**机器按名字找的文件，名字就是接口。**
