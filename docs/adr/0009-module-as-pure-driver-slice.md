# 模块 = 纯驱动切片，逻辑归骨架（消灭"XX 题专用"模块）

模块库里的模块都是从旧工程直接提取的，天然带着原工程的内容：状态机（xunji 的 Control_AB/ABCDA/ACBDA/ACBDAx4、lock_control 的 zone/event）、调度（xunji_tick_50ms/10ms、pid_isr 10ms）、重复实现（PID/myabs/PWM_Limit 各模块各写一份）、以及头注释里整段"2024H 巡线题专用层——car xunji 真机工程移植，陀螺仪不同件需上板校准"的前工程记忆。后果：模块与具体赛题绑定（旧简介判据③ 甚至把这种绑定性合法化为"XX 题专用"标注），换题没法"拿出来就用"；库内重复造轮子；生成的工程带着旧题逻辑与注释，越用越"脏"。用户目标：**需要什么功能就选什么模块，模块不跟任何题有必然联系，即插即用**。

决策：**模块 = 纯驱动切片**——init + 服务函数（读传感器、控制外设、算质心），不自带状态机、调度、流程逻辑。逻辑全部归生成骨架（main.c 本来就是按题 AI 生成的）；跨题复用逻辑（巡线决策类）归参考文件库作 LLM 学习素材（只读不编译，已有 car-1-1 归档先例）。简介判据三要素改四要素：① 与代码一致 ② 硬件身份 ③ 能力方向（可用在哪类赛题功能，补录必填，允许多值）④ 无题绑定（禁题号/年份/题名/专用逻辑）。"XX 题专用"不再是合法模块类别。验证双轨：结构测试机械拦截（题号/年份/题名黑名单，词表单源，能力词白名单防误伤）+ AI 语义校验（判据③④）。

考虑过的替代方案：

- **模块内两层**（驱动层普适 + 决策层可裁剪，放大"可选配套"立项）——模块自持逻辑的本性没变，决策层仍然和题绑定，每个模块还要维护裁剪开关。
- **逻辑片段库**（独立可编译逻辑片段目录，生成时拼进 main.c）——新机制 + 新管线，片段与骨架的粘合方式未定义，收益（决策逻辑复用）参考文件库已能覆盖（AI 读到即可写出）。
- **仅立规范不动结构**——没解决存量模块已带记忆的问题，且无机械强制，规范会漂移。

**Consequences**: 题专用模块逐个瘦身或解散（lock_control 剩余 LED/蜂鸣器驱动与 led_beep 重叠 → 优先解散合并；zone 同理，解散与否实施时按代码定细界）；决策复用靠 AI 生成质量兜底（素材来自参考文件库，骨架 AI 校验链兜底）；补录必须声明能力方向；结构测试黑名单词表需单源维护，防误伤能力词（"巡线"是能力词，不能禁）。改造范围 = 5 个题专用模块（xunji / pid / ball_detect / lock_control / zone）+ 机制（判据 + 结构测试），工单 .scratch/module-universalization/。
